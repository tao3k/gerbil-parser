#+title: Scheme parser DSL design overview
#+date: 2026-10-06

* Research objective

Develop the syntax vocabulary underneath =deflanguage= so that language authors
can express intent, compose recurring grammar patterns and give the parser
compiler useful structural information. This is a design study of the existing
Scheme interface. Its questions concern expressiveness, semantics, authoring
quality and compiler analysis. A defect hypothesis is not the research premise.

Historical source baseline: =29dcb79dafcde202fc9818def3ac536cc20f47c4=.
Executable-study baseline: =783381f33fa1b309ac4cc4b0012696f24c852d93= plus
uncommitted local research fixtures. Receipts qualify their stated boundaries;
no single source-aware package implementing every proposal has been qualified.
The current =deflanguage=, =defgrammar-syntax=, canonical IR and three language
pack interfaces are the starting architecture. Proposed vocabulary examples
in the modules use current constructors. The local GQL implementation and its
open compiler-product gate are recorded separately; broader proposals remain
design work. Scheme remains the authoring and executable research language.

* Fixed user boundary: three DSL interfaces

The agreed author-facing architecture is =grammar.ss=, =parser.ss= and
=parser-test.ss=. DSL capabilities converge within these three interfaces;
implementation complexity belongs to the engine. This is the design constraint
for the integrated proposal, not an additional package interface to select.

| User interface | Author expresses | Engine implements and validates |
|----------------+------------------+---------------------------------|
| grammar.ss | Grammar, lexical/tree policy and declarative reusable vocabulary | Macro elaboration, helper identities, checked POO composition, canonical admission, binding and analysis |
| parser.ss | Public checked entry and declared services/products | Loader admission, dispatch, artifact loading, scanners and backend/FFI mechanisms |
| parser-test.ss | Independent semantic expectations, fixtures and benchmark cases | Test execution, event/span comparison, reporting and measurement infrastructure |

Reusable vocabulary is available through these DSL interfaces. A supported
Scheme declaration of new vocabulary can remain in grammar.ss; users are not
required to write a component factory module, source-map adapter or compiler
closure. Engine implementation modules may export facilities internally, but
that does not create a fourth required user interface. Optional library reuse
must preserve the same three-interface authoring model.

Native POO slot composition is the preferred author substrate; the existing
merge/append/override/remove normalization labels are not four new author
keywords. See [[file:scheme-poo-language-components.org::*Native POO substrate and parser operation labels][the native POO contract and matched controls]]. Parser-specific
reference, field and provenance constraints remain engine responsibilities.

The lower-level POO construction, canonical compiler and manual probe blocks in
this research explain engine behavior and provide experimental controls. They
are not mandatory steps for defining a parser. Public composition intent must
be expressible by supported DSL declarations; underlying row keys, receipts and
helper lifetime are engine responsibilities. Their inspectability supports
explanation and diagnosis without requiring authors to maintain them.

Scientific evaluation must therefore include whether a task can be completed
through these three interfaces. If a routine grammar change requires direct IR
assembly, a hand-maintained source map or knowledge of generated helper names,
the proposed DSL boundary is incomplete even when the resulting parser is correct.

* One objective and one representative language package

The objective is to let authors state a language's intentional choices once,
reuse grammar vocabulary through Scheme modules, and compile it through the
existing parser engine with explainable origins. Checked POO composition remains
an engine capability, not a required author protocol.

Use the existing small call/array language as the common running case:
=f(a,b)=, =[a,b]= and =f()=. It connects lexical declarations, component reuse,
public tree fields, composition, source origins and native qualification. The
expression-tier studies provide an additional binding-policy control; they do
not replace this package-wide narrative with another proposed entry API.

The complete explicit control is in
[[file:../../t/fixtures/language-pack-research/list-language.ss][list-language.ss]]. Its author choices include identifier rules, punctuation,
whitespace, the root, empty-container policy, rejection of trailing commas,
per-item fields, conflicts and case sensitivity. A shorter DSL must preserve
those choices or document a chosen default; a shorter form alone is not a
semantic justification for hiding them.

* The author-to-engine path

| Stage | Input and responsibility | Output / current status |
|-------+--------------------------+-------------------------|
| Package declaration | Identity, root, lexical policy, intended public tree and target products | Existing language declarations; combined component author syntax pending |
| Scheme elaboration | defrules forwards syntax; defsyntax handles context; ordinary Scheme functions share local contracts | Existing primitives or checked role construction; experimental vocabulary |
| POO composition | Combine named contributions using checked merge/append/override/remove | Canonical Grammar IR plus composition receipt; existing mechanism |
| Binding and analysis | Resolve references; use existing nullable/FIRST facts; keep tree and parsing policy explicit | Existing Bound IR and parser compiler; proposed author-facing obligations pending |
| Artifact publication | Admit canonical input through the existing compiler owner and preserve admitted metadata | Shared canonical compiler and emission now retain compositionDigest in the composed fixture |
| Execution and qualification | Parse through existing runtime; compare events, fields, spans, roundtrip and errors | Selected passing controls; combined source-aware package closure pending |

This is one compilation architecture. It does not require a parser per component,
a second Scheme compiler, or a new macro-specific grammar analysis engine.
The author syntax, checked role values and canonical IR are different interfaces
within that path; their phase and ownership must be specified together.

* Integrated implementation decision review

This review consolidates the paper-to-code argument. It prioritizes a complete
author diagnosis task over adding an explanation mechanism without a consumer.
The three-interface boundary is agreed. The first source-diagnostic slice below
is now implemented locally; broader internal choices remain recommendations with
explicit qualification work.

| Decision | Present basis | Recommendation and remaining qualification |
|----------+---------------+--------------------------------------------|
| Author vocabulary | Existing Scheme macros and complete package controls | Retain ordinary Scheme abstraction; add no contribution/owner protocol |
| Semantic admission | Existing canonical, POO, binding and catalog owners | Preserve one effective grammar and its origins through current owners |
| First diagnostic integration | Existing checks plus transient expression associations implemented locally | Twelve admission/diagnostic cases plus 47 existing semantic cases pass with fresh native owners; selected package IR parity checked; full provenance route remains open |
| Recursive fact explanations | Existing analyses plus a researched finite-cause model | Defer integration until a concrete existing consumer needs an explanation; no new nullable-item rejection |

| Portable source evidence | Current persistent Bound IR sources are declaration-level data | Keep initial live syntax transient; richer artifact projection requires a tooling task |
| Optimization admission | Recognition is only one observable contract | Require tree/field/span/policy parity and matched phase benchmarks |

* Integrated architecture decision and remaining boundary

The research question is now singular: can a developer declare a composed
language using native Scheme abstraction in grammar.ss, publish it through
parser.ss and state its expectations
in parser-test.ss, while the engine preserves semantics, effective ownership and
artifact identity without requiring manual metadata or compiler knowledge?

The working architecture is an extensible Scheme front end over one canonical
parser compiler and runtime. Hygienic syntax preserves host binding/context;
checked POO selects grammar contributions; existing inference, binding and
analysis establish effective grammar facts; existing publication supplies the
checked Loader. These responsibilities are one dependency chain. None is a
separate public feature justified by its own passing fixture.

| Connected design obligation | Why the next stage depends on it | Present boundary |
|-----------------------------+---------------------------------+------------------|
| Preserve authored syntax during elaboration | Diagnostics and contribution origins need the original declaration | Local syntax/origin controls; combined collection unresolved |
| Select effective contributions and ownership | Catalog derivation and binding must describe the selected rules | POO operations qualified; automatic effective-source integration unresolved |
| Derive catalogs and include explicit public obligations | Canonical publication must agree with observable trees | DSL variants and projection controls qualified separately |
| Admit the canonical grammar intact | Binding, Parser IR and caches must consume the same grammar | Canonical publication, direct composed emission and checked Loader controls qualified locally |
| Publish the descriptor/machine through the checked entry | User tests and runtime must exercise the admitted products | Expression package qualified; composed source-aware route not closed |

The combined rationale uses the papers together: Scheme syntactic abstraction
explains contextual elaboration; Fortifying Macros informs declaration checking;
scoped-context research informs cooperative diagnostics; compiled extensible DSL
research connects elaboration to a shared compiler. The pinned implementation
reading supplies concrete ownership examples. Actual Gerbil controls establish
only their stated boundaries. This chain is detailed in the
[[file:scheme-dsl-research-basis.org][research basis]], rather than used to justify unrelated vocabulary features.

The fixed decisions are the three user interfaces and engine ownership of
mechanisms. The contribution/owner/compose candidate is withdrawn: it imposed a
new author model without establishing a required language-package task. The
[[file:scheme-dsl-author-interface.org::*Native Scheme abstraction is the author baseline][author baseline]] is the existing complete declaration with native Scheme
abstraction. Existing POO roles and operations stay engine capabilities or their
current lower-level API; they are not a new required concise DSL protocol.
The [[file:scheme-dsl-engine-admission.org::*Source-grounded implementation route: one admitted package][source-grounded implementation route]] remains useful for consistent effective
facts, receipt sealing and runtime publication. Any future public extension must
follow a demonstrated limitation of the complete author package.

* Architectural delivery: thin author entry and focused engine owners

The implementation sequence now refactors the engine ownership boundaries as
one unit. The [[file:scheme-dsl-complexity-ownership.org::*Implemented internal owners: one author surface, explicit engine stages][implemented owner map]] records the extracted concise elaborator,
lexical expression compiler, lexer generator and retained nominal machine owner.
The public deflanguage entry delegates using real hygienic syntax bindings.
Both DSL surfaces enter one compile-time declaration record and direct compiler
function, without whole-declaration macro replay. Runtime assembly receives the
same canonical grammar used for binding, compilation and publication. Analyses
and cache/publication mechanisms retain their existing owners. Admission,
compilation/publication and hygienic emission are now separate named phases.
Normalized POO grammar and supplied context can use the same publication phase;
effective-origin selection and composed runtime/Loader controls are locally
qualified. A production public composition clause and full native runtime linkage
remain open.
No additional author clause or parallel analysis engine is introduced.

The actual GQL grammar.ss, parser.ss and parser-test.ss route remains the large
package control; call/array remains the small complete semantic control. Native
qualification is an acceptance gate for this architecture, not the research
agenda. Build troubleshooting must not displace the connected paper argument,
engine refactoring and complete author-package evaluation.

| Acceptance obligation | Evidence boundary | Required observation |
|-----------------------+-------------------+----------------------|
| Author semantics and hygiene | Existing complete controls run with current compiled declaration owners and source consumers | Same identity, catalogs, macro context, diagnostics, trees, fields and spans |
| Canonical products | Complete call/array Grammar IR and Parser IR comparison | Same serialized products; no second compilation authority |
| Native owner compilation | Three lexical/machine owners and four declaration owners compile in isolated output directories, exit 0 | Standard build discovery includes the new owners |
| Native consumers | Existing installed LR/machine closure is inconsistent; GQL native compilation still exceeds the genuine-output watchdog | Rebuild and qualify the complete dependency and consumer closure |
| Performance and application service | No speedup or concurrent-service closure admitted by this refactor | Matched stage measurements and queue/execute/cancel tests with qualified products |

Parallel cold verification attempts exceeded the existing process bounds; those
attempts are failures, even where assertion markers appeared. Source checks are
rerun sequentially to avoid conflating resource contention with semantic results.
Native module compilation, native consumer execution and GQL/Rust/AOT closure
remain separate claims.

* One package-level research and implementation sequence

1. Use the complete existing grammar.ss declaration, parser.ss entry and
   parser-test.ss expectations as the baseline. Identify a concrete author change
   or diagnosis task before proposing any additional public syntax.
2. Trace that declaration through existing elaboration, effective POO selection,
   origin association, catalog inference/projection, binding and canonical publication.
   Record the existing code owner at each boundary and any concrete extraction needed.
3. Qualify that same route with one intentional contribution replacement: selected
   rules, retained optional fields, effective origins, artifact reload and checked
   Loader observations must agree. Reuse the explicit language as semantic control.
4. Close the package's declared native products and bounded process-completion gates.
   Then measure author change/diagnosis tasks and separate compile/load/parse phases.

Progress means closing an edge in this complete path or resolving its public
contract. More passing local cases, new paper lists or new wrapper macros are
not independently package closure. Existing focused experiments remain supporting
controls; add an experiment only when it answers a named unresolved edge in this
sequence and state how its result changes the architecture decision.

Keep detailed work in its existing module. Update this overview only when the
architecture decision, evidence boundary or next package-level step changes.
Research drafts remain local until design and review boundaries are agreed.
