* Revision and consumed code

The Gerbil package declaration, Cargo workspace dependency and Cargo lockfile
now pin =gerbil-scheme-rust= PR 18 at
=9cd2604efe2a40d53554ee8ffe38d5a8eff4c79e=, replacing

The standalone parser fixture lockfiles do not contain this dependency.

The parser consumes the upstream Rust IR compiler through
=gerbil-parser-build-support=, and the Scheme UTF-8 encoder through
=src/ffi/language-abi-context.ss=. This revision advances the encoder's checked
output using a local cursor. The public encoder and caller-owned capacity
contract remain unchanged. Upstream rooted snapshots and numeric/identifier
bulk conversion APIs are separate capabilities; the parser's GPA1 byte-buffer
transport does not implicitly consume them.

* Tokio evidence and downstream ownership

At this exact revision, Tokio is a dev dependency of =gerbil-scheme=. Its Tokio
handoff tests and transport benchmarks qualify requests sent from async callers
to a dedicated Scheme owner thread. The safe production crate does not expose
a Tokio parser executor. The active performance benchmark retains bounded mpsc
and per-request oneshot responses. Receive batching and reused-response-channel
performance candidates were rejected; functional receive-batching tests do not
establish a production scheduling speedup.

The parser's =NativeSession= and borrowed language/results remain confined to
the initialized VM's original OS thread. Any downstream asynchronous adapter
must create and use them on that owner, bound admission, return owned products,
and qualify cancellation, shutdown and latency. Tokio worker concurrency alone
does not establish concurrent Scheme parsing or lower complete-parser CPU.

* Rust downstream integration at fbb43ca

This integration stage used the manifest and lockfile pin
=fbb43ca63d3740cb4e19b26fa2abd1ea3ee4ecdb=. Its additional upstream receipt
rejects an admission fast path; it does not change the production encoder.
The earlier qualification above remains historical evidence at its stated pin.

The optional =tokio= feature of =gerbil-parser-ffi= now exposes =TokioParser=.
It initializes the standalone bundle and retains a single language handle on
one dedicated OS thread. Bounded mpsc admission and per-request oneshot replies
follow the upstream qualified ownership design. Admission uses normal async
reservation; the rejected upstream fast path is not included.

The owner copies the completed GPA1 payload into independent Rust storage,
releases its C result before publication, and shares an immutable catalog.
=OwnedParsed= retains the exact source and supports normal artifact views after
VM shutdown. Native handles and GC-managed Scheme values never cross threads.
Queued cancelled requests skip execution. An in-flight cancelled request still
releases its C allocation. Explicit shutdown closes admission and releases the
language before normal SDK cleanup; dropping all clients drains the queue.

This is an async downstream ownership interface, not evidence of concurrent
Scheme execution or an incremental CPU speedup. The existing =qualify.ss host=
entry now includes a real Tokio consumer in a separate one-shot VM process:
32 concurrent requests, alternating ASCII/Unicode, 64 records per request,
642 events, syntax rejection, closed admission, and views retained after cleanup.
Transport unit tests additionally cover queue bounds, queued cancellation and
shutdown ordering. Rust lint and workspace all-feature gates cover the new API.

Local GCC qualification completed with =NATIVE-HOST-OK= and exit zero. The
Tokio process completed its 32 full requests, rejection and retained-view checks
with =RUST-TOKIO-HOST-OK= in 0.332 seconds total process wall time. This is a
functional receipt, not a matched CPU performance result. Native SDK linking
required the local OpenSSL library search path; no compiler was replaced.

* Complete Rust request CPU qualification

The Rust consumer now exercises the same independent former scanner/LR kernels
as the Scheme engine benchmark. A test-only factory prepares the reference
context, preserving the generated direct reduction step and descriptor identity.
Both handles live on the same Tokio owner; a benchmark-only routing wrapper
selects the handle without modifying the production parser or scheduler.
Both sides use the current upstream UTF-8 encoder and GPA1 row writer.

Every timed request includes Rust source ownership, bounded Tokio admission,
oneshot completion, C ABI parsing, canonical UTF-8 admission, scanner/LR,
complete semantic publication, a Rust-owned GPA1 snapshot, C result release,
full Rust artifact admission, event-count and root traversal and final Rust result drop.
The source contains 64 assignments: 256 ASCII or 320 Unicode bytes. Every
accepted payload contains 15,488 bytes, 642 events and 64 root children.
Complete byte parity also covers empty, rejected and Unicode quoted inputs.

CPU is process user plus system time from =getrusage(RUSAGE_SELF)=, including
the owner thread, Tokio caller and natural Scheme GC. VM/library startup and
producer compilation are outside timing. No timed GC is excluded, no sample is
dropped, and no per-request observer changes the runtime schedule.

The production fixture uses the workspace's release policy: optimization level
3, thin LTO and overflow checks enabled. The current workload has one owner and eight closed-loop async callers on one
Tokio executor, with a bounded queue of four. This measures concurrent admission
and complete requests, not parallel Scheme execution.
Each of the before, production and after phases has 20 groups. A group has eight
alternating ABBA/BAAB legs, 256 requests per leg and four legs per side, matching
the Scheme Benchmark protocol. Each batch must resolve at least one millisecond.
Nearest-rank P10/P50/P90 use every group. Before/after P10 must be at least 0.90
and P90 at most 1.10; production P90 must be strictly below 0.95.

* Single-pass admission and complete ASCII qualification (2026-10-12)

** Structural change

The Rust artifact consumer previously decoded every GPA1 event once to validate
it and again to construct its navigation index. Field validation also searched
the open-event stack backwards for its owning node. The production decoder now
builds navigation while validating the same event, retaining the current owner
and restoring it when a node closes. Field-owner lookup is constant time. One
open-event stack supplies both nesting validation and closing-row navigation;
the separate navigation pass and node stack are removed.

Identity, canonical record, vocabulary, UTF-8, field ownership, nesting and
coverage checks are retained. Invalid artifacts expose no navigation. Initial
index reservation is bounded to 1,024 rows; a malicious declared event count
cannot force a full index allocation before row admission. Larger valid inputs
grow with admitted records.

The former two-pass decoder is frozen under test support. The optional
=benchmark-controls= feature makes that independent decoder available to the
Rust qualification fixture. Normal consumers use single-pass admission. This
is a test control, not a production compatibility path.

A semantic test compares all navigation entries and admission errors against
the former implementation for all 20 real native-language fixtures. It also
corrupts every payload byte independently, tests truncation and mismatched
sources, and requires identical rejection reasons and event indices.

** Matched full-request evidence

The reference requests use both the independent former scanner/LR kernels and
the frozen two-pass artifact decoder. Production uses the prepared scanner/LR
kernels and fused admission. Both retain the same current upstream UTF-8
encoder, full row writer, source/catalog identities, bounded Tokio owner and
C allocation ownership. Therefore these results qualify the complete combined
engine/consumer path; they do not attribute the entire gain to decoder fusion.

P90 0.855386: before P10/P90 was 0.978785/1.050850, after was
0.980403/1.102040. Its failed control remains recorded. The fixed qualification
protocol now uses 256 requests per leg, eight balanced legs per group, 20
groups per phase and three phases. Warmup remains eight balanced legs of 256
requests. Thresholds, inclusion of natural GC, all-group admission and the
90-second process limit are unchanged.
