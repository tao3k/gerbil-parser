* Choice is part of the language contract

Tree-sitter's [[https://tree-sitter.github.io/tree-sitter/creating-parsers/2-the-grammar-dsl.html][official grammar DSL]] defines choice independently of argument
order. Ford's [[https://bford.info/pub/lang/peg.pdf][Parsing Expression Grammars]] instead defines prioritized choice.
These are different recognition semantics, even when their surface notation
looks similar. Lexical priority, parse precedence and operational dispatch order
also describe different decisions.

The current recursive emitter is restricted to a reviewed HCL grammar by exact
digest and lexical-contract admission. The following control therefore concerns
future admission expansion, rather than a demonstrated current public bug:

#+begin_example
start = sequence(choice(literal("a"), literal("ab")), literal("c"))
input = "abc"
#+end_example

CFG alternatives admit =abc=. A first-success choice consumes =a= and then
fails at =c=; it does not reconsider =ab= after the enclosing sequence fails.
This is a code-derived counterexample to qualify, not an executed test result.
It should first be tested at the appropriate character or token layer, with
lexical segmentation held identical across backends. Also exercise the helper
reference and enclosing-node versions and compare output fields and ranges.

Proposed admission rule: a specialized backend implementing first-success
choice may accept CFG choice only when a sound analysis proves its restricted
behavior equivalent, or when it implements the required alternative handling.
An unproved case produces a compile-time diagnostic explaining the unsupported
semantics. Generation must not silently reinterpret the grammar. Existing
Command branch dispatch remains operationally ordered and gets a distinct IR
meaning; it is not automatically an ordered grammar alternative.

* Analyze the effective grammar before target lowering

Krishnaswami and Yallop's [[https://www.cl.cam.ac.uk/~nk480/parsing.pdf][A Typed, Algebraic Approach to Parsing]] shows how
compositional Null/First/FLast information can justify a deterministic parser
for a restricted grammar class. The separability conditions matter: its FLast
equations are not valid for arbitrary CFGs. Use its discipline to establish
backend preconditions, rather than require every supported language to be LL(1).

Proposed pipeline:

#+begin_example
POO composition -> effective declarations -> resolved expression graph
 -> shared semantic analysis -> target admission -> lowering -> execution
#+end_example

The engine owns analysis; authors own semantic declarations. Internal named
analysis functions compute immutable facts. POO exposes extension values and
policies, not callback protocols for implementing the analysis.

- Resolve references after inheritance/override/extend, preserving source origin.
- Reuse fixed-point analysis for nullable and FIRST. Validate each original
  repeat/repeat1 operand against resolved nullability before helper expansion.
- Record productive versus empty-language rules separately from nullable rules.
  Diagnose unproductive cycles without rejecting ordinary LR left recursion.
- Track conservative field occurrences within the nearest node boundary using
  the existing count-domain proposal. Keep field membership and cardinality distinct.
- Describe scanner state reads/writes, deferred region obligations and result
  ownership as engine effects. Unknown effects prohibit speculative reuse.
- Preserve repeat, separator, delimiter and precedence origins in lowered IR.
  Target diagnostics refer to the author's declaration, not only generated helpers.

A resolved nullable repeat should fail with the reference path that makes it
empty. Runtime zero-width guards remain defensive checks for malformed admitted
programs. They do not replace declaration validation.

* Grammar transformations and runtime scheduling are separate work

Zimmerman's [[https://arxiv.org/pdf/2209.08383][Practical LR Parser Generation]] transforms intermediate helper
nonterminals to defer reductions until their surrounding rule is complete.
This suggests retaining EBNF origin and investigating targeted helper transforms
when measured conflicts originate in flattening. Its XLR bounds depend on bounded
branching; the paper does not justify unrestricted backtracking guarantees here.

A separate execution change is required by the current Source host recursion:

#+begin_example
Source tasks <-> Command tasks <-> Word/Region tasks
               explicit continuation stack
#+end_example

Proposed internal tasks include entering a compound, reading a list, assembling
a pipeline, awaiting a child result and completing a node. Each task has a typed
continuation and explicit input/state/output ownership. Nested commands suspend
the parent task instead of calling another host parser recursively. Task records
are private engine records; language declarations do not contain scheduler code.

Qualify this migration with deep alternating compound/list nesting, empty-list
rejection, ordered fields, exact source ranges and pending heredoc FIFO links.
Replace the fixed host-depth limitation only after full execution uses explicit
storage. Resource limits should describe actual frames/bytes/work and yield a
structured diagnostic; merely increasing 256 does not close the architecture.

* Scanner state is a prerequisite for safe incrementality

Tree-sitter's [[https://tree-sitter.github.io/tree-sitter/creating-parsers/4-external-scanners.html][external scanner contract]] requires complete state serialization
and restoration for edits and ambiguity. It also requires author-maintained C
functions for external tokens. Our design goal is to derive equivalent engine
state operations from declarations for common stateful constructs.

Proposed shared policies cover quoted regions, balanced delimiters, line markers,
deferred bodies and layout boundaries. The engine derives token/result catalogs
where unambiguous; authors specify exceptional language semantics explicitly.
Demonstrate reuse in at least two languages before adding a public abstraction.

A reuse candidate must establish grammar identity, source/edit mapping, parser
entry context, scanner entry context, exit-context compatibility and output
ownership. Scanner context includes pending heredoc markers, quote/escape state
and mode, not only an integer mode identifier. Hash equality alone is not proof:
compare canonical state or use interned identities with verified equality.
Checkpoint data must have explicit ownership across Scheme, Rust and C ABI.

Wagner and Graham's [[https://harmonia.cs.berkeley.edu/papers/twagner-parsing.pdf][Efficient and Flexible Incremental Parsing]] connects
sequence structure and context matching to incremental cost. Investigate balanced
private repeat storage with unchanged public CST order and field observations.
Their performance bounds rely on structural and grammar assumptions; a balanced
container alone does not establish those bounds for this engine. Delaying helper
reductions and exposing reusable sequence boundaries can conflict, so evaluate
both transformations together before adopting either universally.

* AOT and FFI must share semantic admission

Scheme remains the declaration/IR authority. Rust executes admitted immutable
plans; a language-independent C interface manages language, source and artifact
handles. POO extension is resolved before target compilation. No schema version
change is proposed here.

Target capability validation covers every effective construct. Complete parity
includes acceptance, rejection, diagnostics, ranges, ordered fields, deferred
links, source identity and artifact lifetime; event equality is one component.
The Rust Source implementation does not yet establish complete ParseArtifact/C
ABI parity merely by executing Command profiles.

Ford's [[https://bford.info/pub/lang/packrat-icfp02.pdf][Packrat Parsing]] motivates eliminating repeated work through memoization
under its assumptions. Warth, Douglass and Millstein's [[https://tinlizzie.org/VPRIPapers/tr2007002_packrat.pdf][left-recursion extension]]
can have superlinear cases. Any memoization proposal here must account for scanner
context and bounded memory; it does not warrant a wholesale PEG conversion or
an unconditional linear-time claim.

* Second study: admission, suspension and reuse

** Current revision and existing mechanisms

This study inspects =2577253f96b2b5993706c939dbe5088ae0d56a3a=. The original
observations above retain their historical scope. The following proposals are
not runtime changes or new benchmark results.

| Existing mechanism | Exact owner | Design consequence |
|--------------------+-------------+--------------------|
| Effective row owner, composition operation and contribution history | =src/compiler/normalize.ss=, =effective-grammar-row= | Extend expression origins from these selected rows; retain override history without admitting removed declarations |
| Immutable source state with owner, source, character/byte offsets and context | =src/runtime/source-scanner.ss= | Reuse requires edit mapping and semantic context comparison; a checkpoint API already exists |
| Command program counter, node frames and repeat/balance tasks | =rust/gerbil-parser-runtime/src/engine/command_program.rs= | Extend the existing VM suspension boundary; do not introduce an independent command interpreter |
| Synchronous Command/List host calls and depth guard | =rust/gerbil-parser-runtime/src/engine/command_source.rs= | Explicit Command tasks alone do not remove Source recursion |
| Explicit event traversal, private recursively owned recognition children | =command_source.rs=, =result_projection.rs= | Deep-input qualification must include destruction and error cleanup, not only recognition |

The last observation is a potential lifecycle risk inferred from the recursive
ownership shape. No stack-overflow reproduction or failure depth is established
here. =PreparedResultProfile::check_node= checks only the immediate child's
owner/source/span, so it is not a demonstrated recursive validation bottleneck.

** One effective grammar, several target obligations

The typed algebraic parsing paper's Section 3 defines separate conditions for
alternative apartness and sequence separability. Its concatenation facts require
those preconditions; they cannot be copied as universally valid CFG equations.
Our design inference is to keep common facts separate from a predictive backend's
proof obligations. A legal LR grammar may fail the predictive proof.

The existing nullable/FIRST analysis remains the common authority. A proposed
analysis result also records productivity, reference components, declaration
origins and conservative scanner effects. These are private records computed by
named engine functions. An unknown effect is explicit, not an empty effect set.

#+begin_example
Effective declarations + selected origin rows
  -> common resolved facts
  -> LR admission: supported constructs, conflicts and policy
  -> predictive admission: supported constructs + determinism proof
  -> scanner/Command admission: progress, state and result obligations
  -> Scheme / Rust emission from the admitted target plan
#+end_example

A failed predictive proof rejects that requested target with an author-local
reason; it does not change choice semantics, silently select another backend or
reject an otherwise valid LR target. Conflict witnesses and proof failures must
identify the target and relevant expression occurrence.

Productivity is distinct from nullability: =A -> A= has no finite terminal
word, whereas =A -> A a | b= is productive left recursion. Productivity may be
computed monotonically with terminals/epsilon productive, choice as any child,
and sequence as all children, with repeat/optional admitting epsilon. Admission
must separately reject repeat of a nullable operand. This is a proposed analysis,
not an additional implemented fixed point. Unreachable rule policy must remain
explicit; it is not a reason to label every reference cycle invalid.

POO override invalidation follows semantic dependencies. Editing only release
metadata must not reconstruct LR states; replacing a rule or scanner policy
invalidates its dependent analysis and target admission. Cached facts must bind
the effective grammar and policy identity. A semantic digest must include all
recognition-affecting declarations; a hash alone does not replace equality or
resolve ownership. No new public schema version follows from this proposal.

** Preserve expression occurrences through transformations

Langcc's Section 2.3 explains delayed intermediate reductions in terms of the
surrounding continuation. Section 2.4 bounds XLR execution by simultaneous
branches; unbounded branching loses its stated bound. We infer that helper
transforms need both origin records and measured conflict witnesses here; adopting
a numeric branch cap does not prove that our admitted grammar belongs to XLR.

Start from =effective-grammar-row= and assign each expression occurrence an
internal identity: selected rule, child path, selected contribution and available
reader coordinates. Equal expressions at two paths remain distinct occurrences.
Generated repetition helpers point back to that identity and their lowering
operation. This avoids exposing generated helper names in DSL diagnostics.

The proposed next origin test extends the current owner/operand diagnostic:
base role -> nullable override -> inherited repeated reference. Require the
selected override and reference path in the diagnostic; restoring a consuming
override must produce a fresh admitted plan. Source coordinates unavailable in
current syntax data remain unknown rather than fabricated.

** Resume Source through the existing Command VM

=execute_initial= currently holds local frames/tasks while =step= calls
=host.command()= or =host.list()= synchronously. Both Source host methods increment
=Cursor.depth= and re-enter Source parsing. The architectural change is to retain
the VM state across these calls and return a typed request to the outer engine.

Proposed private request/result vocabulary:

#+begin_example
Command execution -> Completed(node) | NeedCompound(field) | NeedList(field, until, allow_empty)
Outer engine      -> push Source continuation + suspended Command execution
Source completion -> resume Command execution with exactly one owned result
Failure           -> unwind all suspended state and pending result ownership
#+end_example

The actual names and representation remain open. Store program counters, repeat
progress checkpoints, ordered node frames and the target field in private typed
records. Command call/node/repeat/balance already have task semantics and should
retain them. Word/Region need suspension only if their actual call graph also
re-enters Source; do not turn every leaf operation into a scheduler request.

Source continuations own pipeline/and-or/list assembly and the stop trigger.
A single request-local cursor owns token position, byte position, pending heredoc
FIFO and links. Preserve today's deferred-body behavior before considering
scoped queues. Parent result publication happens once after child completion;
trivia and significant ranges retain source order. No state is shared mutably
between independent parses.

The scheduler must account for the entire live request: pending tasks, retained
frames/captures, deferred markers, consumed input and produced output. Removing
=256= alone is insufficient. Check actual storage/work limits with structured
failure; do not add a new user-written host callback or scheduler slot.

Private result storage may require an arena or iterative destruction. Decide
using a deep lifecycle test before changing the representation. A deep parse that
succeeds but overflows during artifact release is not a successful migration.

** Incremental reuse needs boundary validation

Wagner and Graham's Sections 4–5 reuse shiftable subtrees while validating their
right edge against lookahead. A parser-state equality check is sufficient but
can be overly restrictive. Their sequence bounds also exclude unbounded context
effects. The design inference is to separate scanner restart checkpoints from
parser subtree admission, and to test context-sensitive sequences explicitly.

Tree-sitter's scanner contract stores the complete lexical state so edits and
ambiguities can restore it. The corresponding engine proposal must include
pending deferred markers and parser-induced context changes, not only the
scanner's mode. Existing immutable Scheme checkpoints are the starting point.

An edit must map both byte and character offsets and preserve UTF-8 boundaries.
A candidate retains old source ownership until an explicit mapped result is
constructed for the new source. Reusing an old =ProjectedNode= directly violates
its current source-identity contract. Reuse diagnostics should distinguish
changed content, scanner context mismatch, parser boundary failure and unsupported
effects. Do not expose those internal states as required language author data.

** Implementation gates derived from this study

| Order | Work | Semantic gate |
|-------+------+---------------|
| 1 | Extend selected row origins to expression occurrences | Nullable override diagnostic names selected contribution/path; removed declaration cannot own the error |
| 2 | Suspend existing VM at Command/List requests | Existing Source corpus and exact diagnostics unchanged; mixed nesting exceeds former 256 boundary |
| 3 | Qualify the whole deep-input lifecycle | Recognition, events, artifact publication/release and failure cleanup all complete without host recursion failure |
| 4 | Account for request resources | Limit failure releases frames and markers; independent parse still succeeds; semantic gates keep their existing deadlines |
| 5 | Prototype scanner restart + subtree boundary admission | Full reparse parity for delimiter, quote, heredoc, multibyte and context-changing edits |

Ordinary correctness cases assert deterministic semantic properties and ownership.
ASP performance cases measure complete calls, allocations, peak live storage and
work; include both nesting and wide lists. No speedup follows from this design
alone. Language packs continue using their existing grammar/parser/test interfaces
and POO value extension points; scheduler and analysis implementation stay inside
the engine.


* Implementation: origins and Source continuation closure

The implementation extends the selected source map into repetition diagnostics:
rule, expression child path, selected POO contribution, and a finite nullable
reference explanation. It records both the referenced declaration and the
reference occurrence. Reader coordinates remain unknown where unavailable.
A queue visits each referenced rule once; the diagnostic does not expand shared
nullable derivations into an exponential tree. Nullable acceptance remains owned
by the existing fixed point. Generated helper origin serialization and broader
conflict witnesses are still separate work.

The real declaration compiler binds the diagnostic context only for its compile.
Complete declaration cache hits recheck current repetition admission using the
cached canonical nullable facts before publication. This performs no LR lowering,
fixed point or state reconstruction, and changes no public schema. Tests include
an old complete cache receipt that must reject without invoking either compiler
callback, selected nullable overrides, cyclic exits and a 32-level shared DAG.

Rust Source now drives the existing Command VM through private continuation
records. Command/List instructions suspend the VM; compound, pipeline, and/or,
list, prefix and assignment continuations resume through one outer request loop.
The synchronous Source host methods and recursion-depth guard have been removed.
Words, result profiles, token ordering and heredoc FIFO remain governed by the
admitted Scheme-generated product. Language author interfaces are unchanged.

The private resource gate counts pending Source tasks plus VM tasks/node frames,
including growth while a VM runs, with a limit of 16,384 live frames. It returns
=command-source-resource-limit= at an input byte boundary. This is a frame limit,
not a complete byte/allocation/work budget. It does not establish a complexity
bound for the whole parser.

Private recognition nodes now drain descendants iteratively during destruction.
A Rust control on a 256 KiB thread stack accepts 1,024 alternating group/subshell
levels, constructs events and a lossless Rowan tree, and releases the tree/results.
It also cleans up a completed deep child after a trailing-pipeline failure and
successfully parses an independent next request. A larger input exercises the
resource rejection path; a 6,000-form VM call chain also hits the same budget
without returning to Source. Scheme independently admits the identical deep input
as a valid lossless ParseArtifact. Deep input artifact/C ABI cross-target byte
parity has not been established by these separate controls.

Local qualification: 133 Rust runtime tests and strict Clippy; 18 resolved grammar,
12 artifact, 31 composition, 5 style, and 9 Source strategy Scheme cases. Scheme
qualification uses the existing native watchdog and GCC. The Source strategy
suite initially hit a loading silence failure because its native product helper
was missing; building that existing conformance helper resolved it without a
backend or timeout change. No end-to-end runtime speedup or cold full-package
build improvement is claimed. Exact rebased-head CI is a separate gate.

The next engine work is full Source ParseArtifact/C ABI ownership and diagnostic
parity, then scanner checkpoint/edit mapping and parser subtree boundary admission.
The proposed incremental mechanism remains unimplemented.

* Implementation: canonical Source publication and shared lexer preparation

Rust Source now publishes =CommandEvent= records through one iterative
=CommandParse::walk_events= sink: preorder node IDs, producer-order token IDs,
node boundaries, field boundaries and the complete trivia tape. The existing CST
API projects this same walk rather than maintaining a second traversal. A sink
receives a prefix if later validation fails and must commit only after success.
The result retains the exact source allocation and result-profile identity;
replacing its public root with a tree from equal bytes in another allocation is
rejected before the sink receives anything.

The Scheme Command Source generator also emits native fixture bytes through
=bind-native-language= and =native-parse-binary-payload=, using the public codec
consumed by the C ABI. CI regenerates both products and compares them to the
checked-in fixtures. The 54 controls cover the original declaration and a POO
extension changing the root projection, pipeline role and Unicode form keyword.
Rust compares every accepted canonical record with the decoded Scheme GPA1
record, including names, IDs, ranges, field scopes and trivia placement. Rejected
controls check acceptance agreement and the Scheme fallback token tape. Native
views borrow the original source slices, reject changed source digests, and
repeated Rust publication starts with independent identifiers. Deep publication
also walks 1,024 alternating compound/subshell levels on a 256 KiB stack.

This establishes canonical accepted-event parity against native codec bytes for
these controls. It does not implement a Rust GPA1 encoder or qualify live C
handle allocation/release through these fixture tests. GPA1 currently contains
status and events, not diagnostic records; diagnostic content parity and a
language-independent diagnostic transport remain open. No schema increment or
compatibility mode is introduced.

module's procedures into one C procedure and can make optimization of large

failure; Scheme semantic controls and local GCC compilation are separate evidence.
