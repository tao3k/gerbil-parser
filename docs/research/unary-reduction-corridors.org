#+title: Decorated unary corridors: rejected execution experiment

* Decision

The execution fast path is rejected for production. Three coherent variants
were tested: a named helper returning multiple values, a hygienic macro
publishing the stack heads directly, and that macro carrying its resolved next
action row into the outer loop. Allocation improved, but short-chain CPU
regressions remained and complete requests did not improve consistently.
The engine implementation remains unchanged. The retained code is the shared
derivation diagnostic and long-chain semantic/count regression control.

* Representation lifetime rather than rule deletion

Every unary reduction pops one state and one semantic value, applies its
original action chain, and pushes one state and one value. Consecutive unary
reductions keep the same stack suffix. The changing heads can therefore remain
lexical locals until execution reaches a non-unary action. The implementation
owner was =src/runtime/lr-parser.ss=; that candidate code has been withdrawn.

#+begin_src scheme
;; Conceptual engine kernel: base-state and suffixes remain unchanged.
(let loop ((state first-target) (value first-value) (actions first-count))
  (let (entry (lookup-original-action state lookahead))
    (if (admitted-unary-reduction? entry)
      (loop (goto-original-production base-state entry)
            (apply-original-actions value entry offset)
            (+ actions 1))
      ;; The caller publishes the final immutable heads once.
      (values state value actions))))
#+end_src

The candidate helper checked the original indexed LR action and goto at every step.
It executes the same prepared field/alias chain in declaration order, and
increments the action count for every reduction. It does not eliminate rules,
change production IDs, merge AST nodes, alter precedence, or change grammar
digests. A missing goto stops the helper before committing that reduction;
the original executor owns fallback at the reconstructed frontier.

Eligibility requires an existing non-EOF lookahead, no finite action budget,
no captured derivation stack, and no layout runtime/context. Generated reduction
steps retain their independent protocol. Action-budget checkpoints and captured
derivations preserve every original boundary. EOF remains in the outer executor
so streaming callbacks retain their existing invocation behavior. The helper
uses immutable semantic values and ordinary tail calls; no vector arena, global
cache, unsafe access, or grammar option is introduced.

Why does this improve the Scheme DSL design? The author describes syntax and
closed actions once. Canonical IR, prepared actions, and Scheme lexical scope
allow the engine to shorten the lifetime of private intermediate stack heads
while retaining the complete author-visible tree. POO composition and macro
expansion retain their current authority; authors need no optimization controls.
This ownership advantage does not prove the rejected runtime implementation
is faster.

Why is the design scientifically testable? Independent materialized GLR must
produce the same complete artifact for both recognition/event backends. Long
decorated chains must preserve every nested field/alias and the exact action
count observed after the following shift. A one-action checkpoint walk supplies
an independent count control. Complete requests then test whether eliminating
intermediate heads improves actual cost.

* Paper mechanism and boundary

[[https://arxiv.org/html/2304.05276][Yallop, Xie and Krishnaswami, flap (PLDI 2023)]] demonstrates removal
of intermediate representations while retaining modular definitions. This
motivates asking which internal values need materialization. Our kernel is a
runtime LR stack optimization, not their DGNF normalization or lexer/parser
fusion algorithm. Their assumptions and speed ratios do not establish ours.

* Matched native results and decision evidence

The final variant used a hygienic =defrule= to publish directly into the
outer loop, avoiding a per-corridor multiple-value return envelope. It also
carried the already-resolved final action row while the state and lookahead
were unchanged. Shifts and ordinary reductions discarded that private entry.
These changes reduced the first variant's overhead, but did not establish a
general win.

The baseline LR/sequence implementation was =c1237c5=, reused in an isolated
prepared native graph. Only the candidate LR executor was replaced. Parallel
Source/Fold commits are not measured by these LR comparisons.
The final native order was baseline/candidate/candidate/baseline, 20 samples
of 20 calls per workload and route. The table reports CPU batch P50 divided
by 20, in milliseconds/call. Allocation is admitted only for single-caller
samples without GC; GC-containing timing observations remain in the samples.

GQL 512 full-source allocation fell by 392448 bytes/call, about 9.1%.
FHIRPath 512 full-source allocation fell by 245280 bytes/call, about 4.4%.
Arithmetic's generated full-source route allocated the same bytes in both
variants. Short generic Arithmetic recognition still regressed in both
candidate trials. FHIRPath full-source did not show a consistent improvement.
GQL's larger request benefit therefore does not admit the implementation as
a general shared-engine optimization. No general P95 improvement is claimed.

The named-helper variant increased generic Arithmetic allocation; its
multiple-value boundary cost exceeded its saved stack cells. The macro
removed that increase, but retained a duplicated final action lookup until
the last variant. The last variant removed that duplicate lookup while
retaining all original semantic actions. CPU regressions persisted. These
are failures of the proposed cost tradeoff, not evidence that Gerbil/Gambit
or the language declarations are inherently slow.

* CPU attribution remains open

A separate complete-request sampling workload reported its own PID through
the official =std/os/pid= interface and verified the final artifact after every
50 calls. The macOS sampler produced an empty call graph, so it supplies no
usable CPU attribution. The workload completed 3500 calls before its existing
60-second total gate terminated it, without its required completion marker.
It is not admitted as a successful qualification. The gate was not widened.
Receipts: =/private/tmp/parser-gql-native-cpu-sample-supervision.log= and
=/private/tmp/parser-gql-native-cpu-sample.txt=.

An empty sampling report does not show that the parser has no hotspots.
Future sampling must first demonstrate actual thread/stack observations and
distinguish native parsing, publication, GC and driver work. Execution counts
alone cannot close this missing attribution.
