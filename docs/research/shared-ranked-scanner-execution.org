#+startup: overview

* Ranked literal publication experiment: rejected lowering

The current Coding Style research requires known private calls, checked
boundaries, and admitted ownership. Reading the pinned Gerbil SDK =2591dcd=,
=src/std/text/parser/ll1.ss=, shows =ll1-uint= accumulating its scalar result
while consuming digits. This motivates retaining a decision during traversal
and constructing an observable result only at the output boundary. It does
not establish that an additional accumulator is free in a compiled lexer.
The earlier rejected dense region-trie experiment remains rejected.

The shared ranked literal trie originally constructs a four-element result
for each admitted accepting prefix along the matching path. A prefix chain
can therefore allocate O(A) result spines for A accepted terminals even though
only one escapes. Three candidates reduced publication to O(1) per successful
call while retaining the same trie edges and terminal selection: an explicit
endpoint plus a named publication helper; a prepared terminal width with
publication after traversal; and an explicit endpoint with direct publication
at each exit. Traversal and terminal admission complexity were unchanged.
No language-specific rule, unchecked annotation, compatibility mode or schema
change was added. None of these runtime candidates is retained.

* Closed-start specialization of the shared regular DFA

The current Scheme Coding Style research favors binding-preserving syntax,
prepared decisions and small named loops. Reading the pinned Gerbil SDK
=2591dcd=, =src/gerbil/core/contract.ss= (=definline=) shows signature-aware
dispatch expansion rather than a promise that every abstract call is free.
The SDK's =src/std/text/parser/ll1.ss= likewise retains compact loop state.
The transfer here is to remove state that cannot occur, using a private
hygienic lowering whose expansion is inspected before measurement.

** State argument and implementation

A regular scanner's initial mask contains only the six declared run bits,
so it lies in 0..63. Number starts use bit 32. If an admitted initial mask
lies below 32, no transition can introduce a number state: the generic
number transition only advances already active number states. The other
five run families intersect their active mask with the current character
mask; they can lose bits but never gain them. Every surviving subset is
accepting. This path therefore needs neither pending fraction/exponent state
nor an accepted-subset/accepted-end rollback pair.

=make-ranked-regular-scanner= retains its prepared winner table and numeric
state machine. At matching entry, a nonnumeric initial subset selects the
existing monotone run algorithm, even when the grammar also declares a
number rule. Numeric starts keep their original rollback behavior. Modes
without number rules also use the same monotone lowering. The private
=scan-regular-run= syntax expands that algorithm at both call sites using
caller bindings and evaluates the initial offset once. No callback, table,
public scanner API, language metadata, schema version or compatibility route
is added. The final implementation adds no unsafe operation or type assertion.

instead of computing a bit intersection and then testing zero.

* First-character competition staging and callback ownership

** Source study and phase ownership

The pinned Gerbil SDK revision =2591dcd= provides a useful distinction in
=src/std/text/parser/ll1.ss=. The =ll1-bind= and =ll1-begin= combinators compose
procedures before reader execution, whereas =ll1-or/list= retains a named loop
where input-dependent failure determines the next alternative. The =peeker=
constructor resolves the specification's outer representation before the
resulting predicate sees input. These are concrete implementation patterns,
not evidence that every closure composition improves performance.

The existing [[file:scheme-dsl-research-basis.org][DSL research basis]] and
[[file:scheme-macro-binding-experiments.org][binding experiments]] retain
language declaration context and place derived execution mechanisms in the
shared engine. These experiments need no author macro, POO slot, grammar field,
unsafe assertion, or compatibility path. They investigate prepared dispatch
and callback ownership inside the existing ranked lexical algebra.

Previously, an ASCII table selected the nonregular candidate list, but each
token folded that list with a source/offset callback and checked whether regular
and literal scanners participated. The participation facts are derivable during
preparation. The experiments below show why derivability alone is insufficient
to admit a new execution representation.

** Historical execution candidate, withdrawn after the cross-language audit

The initially retained candidate kept the existing ASCII table, mode admission,
conservative non-ASCII path, regular/literal dispatch and mode-miss fallback.
The private =scan-ranked-candidates= hygienic macro preserves the stable
source, offset and candidate bindings at its sole call site. It applies the
existing =prefer-generated-match= in a named loop without a new procedure
argument boundary. It preserves
all candidate calls and their order, including no-match results. The caller no
longer constructs a source-dependent fold callback for each token. There is no
new prepared procedure catalog, nested composition graph or transient interning
cost. This isolates callback ownership from the rejected staging designs.

The original nonregular order, regular scanner and literal scanner order remain
unchanged. Token materialization and byte extents retain their existing owner.
No claim about eliminating all scanner allocation follows from removing this
one callback. The fixed GCC compiler owns ordinary procedure and sequence checks.

** Rejected nested-composition prototype

The first prototype composed a captured previous procedure and next scanner for
each ranked fold edge. The complete HCL lexer allocated 312,330.4 bytes instead
of 336,906.4 in both candidate blocks. Its CPU medians were 49.05 and 47.40
microseconds per call, against reference values 98.75 and 58.50; the reference
itself varied considerably. Each block used eleven samples of twenty lexer
calls and checked complete tokens against the independent direct HCL lexer.

That component result did not justify retention. Native complete requests use
twenty samples of twenty calls at sizes 64 and 512, with complete source-bound
artifacts admitted against independent materialized GLR output. The 512-item
GQL route regressed in both candidate blocks: 2.55185 and 2.50270 ms per call,
against references 2.29435 and 2.33710. Prepared LR allocation remained unchanged
while complete requests allocated fewer bytes. CPU improvements on some other

1,023,200 bytes per call; all eleven samples in each block were admitted.
Preparation CPU medians were 0.185 and 0.196 ms for the references, versus
0.407 and 0.406 for the candidates. Those calls execute the factory once per
sample and check its returned lexer against independent complete tokens after
timing. The two cost boundaries therefore exposed both request and setup risks.

A second staging prototype replaces nested composition with a named loop
and interns tuple keys before building procedure lists, so equivalent ASCII
classes do not repeatedly allocate those lists. It retains staged participation
and removes the per-token fold callback. Nested frames remain an investigation
hypothesis, not a proven isolated cause of the first prototype's CPU change.
The second prototype was also rejected, as recorded below.

* Engine-owned semantic representation of installed entries

The complete-route audit above identifies two independent axes: the prepared
LR runtime's captured semantic executor and the installed generated entry's
product. =src/compiler/machine.ss= now makes those obligations queryable through
=parser-machine-backend-representation=. This is an engine capability contract,
not another language declaration or a backend-selection policy.

| Entry query | Contract |
|-------------+----------|
| prepared | Captured recognition or event-program executor |
| drive | Installed whole-source driver returns recognition values |
| source | Installed source specialization returns ParseArtifact or declines with #f |
| step | Installed active reduction step uses the captured runtime representation |
| event-step | Separately installed optional event-program reduction step |

Missing optional entries return =#f=. Unknown kinds and non-machine values reject.
The =step= slot deserves an explicit distinction: on the base recognition runtime
it holds a recognition step; the selected event runtime captures the admitted
event step into its active step slot. The separate =event-step= slot describes
an optional installation on the base runtime, not a claim that every selected
runtime retains that installation slot. Backend installation admits the same
closed kind domain before any mutation; digest and duplicate-slot checks retain
their existing atomic admission behavior.

The representation review found an installation mismatch, not just a missing
label: recognition =step= declarations previously admitted an event machine.
The direct machine installer and the full-batch precheck now reject that pairing.
The batch precheck runs before all mutation, so a valid earlier drive remains
uninstalled when a later step has the wrong semantic runtime. Existing raw LR
step operations remain low-level active-step operations; the machine declaration
owner supplies this generated recognition-entry obligation.

#+begin_src scheme
;; Preference selects the prepared executor; it does not rewrite generated code.
(let* ((selected
         (parameterize ((current-lr-event-program-enabled? #t))
           (parser-machine-for-current-semantic-backend machine)))
       (prepared (parser-machine-backend-representation selected 'prepared))
       (drive (parser-machine-backend-representation selected 'drive)))
  ;; For an eligible machine with an installed recognition drive:
  ;; prepared => event-program, drive => recognition.
  ;; A later parameter change does not change either captured obligation.
  (values prepared drive))
#+end_src

** Question: why is this abstraction preferable?

The generated entry kind already expresses an engine responsibility. Deriving
its representation obligation there avoids another metadata annotation in
=parser.ss= and another POO wrapper around an ordinary procedure. Captured runtime
identity supplies the prepared representation. Named closed-domain algorithms
are appropriate here; the existing CLOS preparation protocol remains responsible
for backend/capability selection. No generic query, grammar scan or backend
selection occurs when describing a captured machine.

This slice makes an existing semantic obligation explicit. It does not enable
event generation for a recognition drive, change the default backend, clear a
generated entry, alter canonical IR or add another compatibility route.
