#+title: Scheme abstractions at the semantic reduction boundary

* One engine boundary, two semantic products

This study connects the [[file:engine-reduction-generation.org][shared reduction generator]] to the
generic runtime. The canonical operand action chain is shared by recognition
trees and event programs. Its order, empty-chain identity and preparation
contract belong to the engine. Backend-specific field and alias construction
belongs to each semantic product. Language declarations acquire no additional
operation or configuration.

The earlier [[file:unary-reduction-corridors.org][corridor experiment]] reduced allocation but did not establish
a consistent complete-request CPU improvement. This refactor addresses the
maintainability of the action interpreter without reviving that execution path.

* Official source evidence

The installed Gerbil source used for this study is revision =2591dcd=, shipped
with the locally qualified toolchain. Reproduction starts with the toolchain's
source tree rather than assuming that an online development branch matches it.

- =src/std/text/parser/ll1.ss=: =ll1-bind= expresses parser composition;
  =ll1-begin= and =ll1-case= stage control structure; =ll1-char?= uses the
  =BufferedReader= interface through =using=. The same file retains named
  =let= loops and conditional expressions in concrete execution algorithms.
- =src/std/iter/macros.ss=: =for1= validates declaration shape with
  =syntax-case= and generates callbacks or typed bindings; =for1-dispatch=
  selects an expansion appropriate to the iterator form.
- =src/std/vector/vector.ss=: typed procedure and vector arguments define
  contracts around vector algorithms, while =for= expresses index traversal.

These examples support separate abstractions for composition, representation
contracts and execution. They do not establish that higher-order calls are
always faster, or that named loops are poor Scheme style.

* Declarative action admission

The runtime previously embedded list-length checks and a callback in vector
construction. Preparation now names the two accepted shapes explicitly:

#+begin_src scheme
(def (operand-action? action)
  (match action
    (['field _] #t)
    (['alias _] #t)
    (_ #f)))
#+end_src

The action-chain boundary still requires a proper list. Names retain the
existing canonical IR contract; this change does not introduce a new name
restriction. Unknown operations, missing payloads, extra payloads and improper
chains fail during preparation. Validation remains outside the request loop.

* Stage the shared fold

#+begin_src scheme
(defrule (define-operand-action-fold fold-name action-step)
  (def (fold-name value actions offset constructor)
    (if (pair? actions)
      (fold-name (action-step (car actions) value offset constructor)
                 (cdr actions) offset constructor)
      value)))

(define-operand-action-fold apply-operand-actions apply-operand-action)
(define-operand-action-fold apply-operand-actions/events apply-operand-action/events)
#+end_src

The recognition step remains its existing procedure. The event step is a
hygienic rule that binds the selected action once before its dispatch, keeping
the previous inline event evaluation. The shared rule emits closed tail loops;
it does not install a backend callback or capture a request's offset.

* Question: why is this design preferable?

The source now states one action-chain traversal contract and two semantic
interpretations. Fixing action order or identity requires changing one fold
definition. The backend operations remain independently readable. Scheme's
advantage here is hygienic staging of an engine algorithm, beyond merely
representing declarations as lists. A runtime combinator remains appropriate
where a caller genuinely supplies a dynamic strategy; these two backend choices
are already known when the module expands.

This is a local abstraction inside the shared engine. It does not justify
turning every loop into a macro, adding POO objects to private scalar state, or
changing the three language-author interfaces.

* Question: why is the claim scientifically testable?

The invariant is =fold(step, seed, actions)= with actions consumed in declaration
order. Empty chains return the original seed. Existing negative preparation
tests exercise malformed action shapes. Decorated chains and widths
=0, 1, 2, 8, 32= compare complete canonical artifacts against the independent
materialized GLR interpreter, for both recognition and event backends.
Unary-corridor controls additionally compare bounded checkpoint action counts.

Native compilation verifies the macro expansion, while matched GQL, FHIRPath
and Arithmetic requests distinguish maintainability from performance. A
successful source test alone does not establish native request cost. No
end-to-end speedup is claimed from removing duplicated source text.

* Continue at cohesive engine boundaries

The remaining review follows the same canonical IR -> prepared runtime ->
execution -> artifact path, rather than a list of surface syntax substitutions.
Preparation should express admitted representations and backend capabilities.
Generated and generic reducers should share action policy while retaining
their independently testable execution strategies. Checkpoint and publication
ownership should be explicit where mutable lifetime actually matters.

The next performance transformation still requires CPU attribution and matched
complete products. This abstraction refactor does not resolve that evidence
gap, and a larger rewrite is not admitted merely because it uses more macros
or interfaces.

* Completion records and ranking ownership

The next boundary is the selective-GLR result retained by configuration memo
entries. Previously it was a six-element positional list. Ranking lived inside
the request executor, traversed token suffixes during comparison and constructed
a provisional result followed by another copy carrying the completion count.

Official =src/std/text/parser/base.ss= uses final structs for =token= and
=location= and destructures them with =match/with=. The official
=src/gerbil/core/contract.ss= =Using= module implements the lexical class binding
used below. Its syntax admits one typed binding per =using= form; two objects
use nested scopes.

#+begin_src scheme
(defstruct lr-completion
  (root rest score ambiguities winner-reason completion-count remaining-count)
  final: #t)

(def (ranked-candidate winner reason count)
  (using (winner : lr-completion)
    (make-lr-completion winner.root winner.rest winner.score winner.ambiguities
                        reason count winner.remaining-count)))
#+end_src

=src/runtime/lr-completion.ss= owns the private completion representation and
pure comparison policy. Its API exports construction and projections without
mutation. The executor retains chart ownership, exploration budget, diagnostics,
ambiguity rejection and request-local counters. =select-candidate= returns a
representative and an equivalent-merge flag; the executor updates its own merge
counter. No language declaration acquires another interface or policy switch.

The comparison order remains dynamic score, maximal consumption, then structural
product equivalence. Distinct equal-ranked products retain their ambiguity in a
representative so a surrounding higher-scored completion may still win. Total
completion counts are accumulated even when one candidate outranks the other.
Cached suffix lengths are copied from the selected record; the engine retains
immutable token suffixes throughout a parse.

** Question: why is this design preferable?

A named final record exposes the actual result contract and lets Gerbil resolve
typed slot accesses. A standalone policy can be reviewed without the chart,
continuation and observability machinery. One final construction carries both
ranking evidence and completion count. This applies Scheme's type and lexical
abstraction facilities to a private protocol; POO remains appropriate for the
extensible public grammar and parser models.

** Question: why is the claim scientifically testable?

Policy controls cover both exploration orders for score and consumption, equal
structural copies, unequal suffixes, accumulated ambiguity/counts, first-result
identity and outer-score resolution. Existing parser integration controls cover
the corresponding complete parse receipts and failures. A benchmark group runs
four complete prepared GLR requests: equivalent merge, dynamic ranking, fragment
interning and typed ambiguity rejection, requiring the same complete receipt.

Ordinary full-parse LR completions reach EOF, so their suffix length is zero.
Caching its length does not by itself establish a large request-time saving.
The extra record slot and multiple-value result also have a native cost that
must be measured. Deterministic request controls remain necessary because the
shared runtime imports the new module even when it does not enter GLR.

* Generic functions as preparation protocols

The available mechanisms have different owners. Gerbil =defmethod= associates
behavior with a receiver type. Upstream =clan/poo/mop .defgeneric= invokes a
receiver's prototype slot; it is a single-receiver protocol. The pinned
=core/poo-clos/interface= provides actual multiple dispatch, =eql=/class/prototype
specializers, method combinations and generic generations. Treating these as
one interchangeable mechanism would obscure the extension contract.

Source evidence is =gerbil-poo/mop.ss .defgeneric= and POO Flow Core's
=poo-clos/{syntax,dispatch,objects}.ss=. In particular,
=applicable-ranked-methods= computes applicability from an immutable generic
generation and sorts by =argument-precedence-order=; =compute-effective-method=
admits protocol hooks. The checked runtime is already a dependency. The parser
must not implement a second generic registry or method-combination evaluator.

The engine uses receiver protocols for grammar/context role access. The initial
audit found no CLOS preparation protocol for semantic backends; the LR migration
below now installs one. The dependency already provided the required mechanism.

** Separate selection from repeated execution

The executable control in =t/generic-dispatch-contract-test.ss= uses the actual
Core CLOS declaration syntax and ordinary Scheme values:

#+begin_src scheme
(.defgeneric test-select-semantic-plan (backend capability))
(.defmethod (test-select-semantic-plan (backend (eql 'event))
                                     (capability (eql 'plain)))
  (lambda (value) (list 'event value)))

;; Selection belongs to preparation; the returned kernel is reused.
(let (kernel (test-select-semantic-plan 'event 'plain))
  (kernel 'a)
  (kernel 'b))
#+end_src

The probe counts method-body selection separately from kernel calls and checks
that repeated execution does not redispatch. It is a design control, not an
installed event parser, an allocation benchmark or an implementation of a new
public grammar operation. Its unsupported-pair rejection is an explicit probe
contract; it does not change the existing optional event backend fallback.

| Engine boundary | Appropriate generic operation | Prepared result |
|-----------------+-------------------------------+-----------------|
| Admitted recognition dialect and semantic backend | Resolve a supported lowering strategy | Checked closed recipe plus derived executor |
| Result schema and publication target | Resolve encoding/publication strategy | Schema-admitted publication kernel |
| Open POO authoring role and compiler target | Elaborate inherited behavior | Canonical IR with source origins |

These are independent variation axes. The first migration should move strategy
selection out of nested runtime branches into one preparation owner, retain
the prepared runtime's identity, and keep each kernel's traversal explicit.
Grammar authors continue to use the existing three interfaces. Ordinary values
are sufficient for fixed strategies; POO/class specialization supports genuine
extension. A closed scalar algorithm such as completion score comparison does
not acquire a class hierarchy solely to increase generic usage.

Prepared products must bind the admitted generic generation or immutable method
snapshot; otherwise changing methods could silently change a retained parser.
Procedure-valued derived executors must not enter canonical, digest-bearing IR.
Reusing generic selection requires preserving both constraints before replacing
the current backend policy.

** Contextual conflict semantics remain an independent contract

Two applicable methods can be more specific on different arguments. Ordinary
CLOS chooses using argument precedence. Current contextual grammar selection
uses componentwise dominance: incomparable maximal methods with unequal results
are an error, while equal results retain both declaration origins.

The executable control tests both behaviors on the same =shell/command=
intersection. It shows why blindly substituting ordinary primary-method
selection could hide a grammar conflict. Core's existing generic-protocol and
method-combination facilities are the appropriate place to express the required
policy if that resolver migrates; parser-specific conflict admission remains
explicit. No new dispatch kernel is justified.

** Question: why is this design preferable and testable?

Multiple dispatch states which combinations the engine supports without making
each caller reproduce a decision tree. Hygienic declarations, POO extensions,
normal values and prepared kernels can cooperate: the generic owns selection,
the compiler owns admission, and the executor owns repeated work.

The controls demonstrate actual two-argument selection, fixed-kernel reuse,
unsupported combinations and the contextual conflict boundary. Production
migration additionally requires generation invalidation controls, complete
artifact/diagnostic parity, preparation cost and complete-request benchmarks.
These executable controls alone do not close that migration or establish its
performance.

** Production LR preparation: select admitted executors once

=src/runtime/lr-parser.ss= now separates the grammar's semantic capability from
the request's backend preference. =lr-prepare= validates reduction plans,
classifies the admitted grammar and selects both executors through the existing
Core CLOS implementation:

#+begin_src scheme
(.defgeneric select-lr-semantic-reducer (backend capability))
(.defmethod (select-lr-semantic-reducer (backend (eql 'recognition)) capability)
  reduce-value)
(.defmethod (select-lr-semantic-reducer (backend (eql 'event)) capability)
  #f)
(.defmethod (select-lr-semantic-reducer (backend (eql 'event))
                                     (capability (eql 'plain)))
  reduce-value/events)
#+end_src

The general event method denotes unavailable optional execution; the more
specific =event/plain= method supplies the executor. Layout, dynamic precedence
and branching grammars retain recognition execution. Unsupported semantic
actions still fail during reduction-plan validation. No public grammar syntax,
POO wrapper or alternate generic registry is introduced.

The prepared runtime stores the returned procedure or negative admission.
=lr-runtime-for-current-semantic-backend= performs constant-size preference and
identity checks, then obtains or constructs the cached event runtime. It no
longer traverses the LR action and production tables, including repeated
requests against an ineligible grammar. Generated step installation invalidates
future runtime selection while previously retained runtimes keep their executor.

This first protocol is closed and module-private. Core's lowering constructs a
lexical =poo-clos-generic-binding=; the parser exports neither that binding nor
the generic. Preparation captures the selected executor itself, so later
requests do not consult a generic generation. An open extension protocol still
needs explicit generation admission; this change does not implement one.
Executors remain derived runtime values, absent from canonical digest-bearing
grammar and parser IR.

*** Question: why is this abstraction preferable?

Support for a backend/capability combination is a method declaration owned by
preparation. Callers do not inspect grammar tables or reproduce support rules.
Ordinary Scheme values suffice for these fixed strategies; actual open authoring
objects retain their POO interfaces. Multiple dispatch resolves variation while
named pure algorithms perform capability classification and the fixed reduction
kernel performs traversal. This assigns each abstraction a concrete job.

*** Question: what makes the claim testable?

=t/lr-semantic-preparation-test.ss= checks preference-independent preparation,
runtime identity and cache reuse, generated-step replacement without changing
retained executors, and recognition fallback for dynamic, branching and layout
grammars. Existing artifact, GLR, empty-reduction and fragment tests supply
semantic controls. Two generic selections and eligibility scanning now belong
to preparation even when event execution is not requested. Preparation overhead,
cold native dependency loading and complete-request performance must therefore
be measured separately; removing request-time table traversal alone proves no
end-to-end speedup.

** Share executable configuration, preserve rule semantics

The implementation separates =lower-rule-matcher=, =prepare-rule-matcher= and
=decode-rule=. A private =contextual-matcher-plan= holds an admitted expression
and executor. One preparation-local equal?-table shares region/guard matcher
plans across modes and both source-size indexes. Their declaration keys begin
with opcode symbols; existing literal-trie keys are catalogs of strings. These
key domains are disjoint. Literal catalogs retain their established short-input
linear and long-input trie paths. Primitive opcodes retain the compiler's
existing configuration-free closures directly.

#+begin_src scheme
;; A hygienic local constructor retains lexical rule metadata without a closure.
(defrule (finish expression executor)
  (make-runtime-scan-rule name mode form expression executor rank action))
(let (plan (prepare-rule-matcher matcher matcher-cache))
  (finish (contextual-matcher-plan-expression plan)
          (contextual-matcher-plan-executor plan)))
#+end_src

The plan takes ownership of closed IR before interning. No process-global cache,
new grammar declaration, user-visible wrapper or runtime generic dispatch is
introduced. The preparation table is discarded after the completed indexes own
their executors. State, pending delimiters and source identity remain request
owned; rule name, form, rank and action remain distinct records. Canonical IR,
its digest and opcode meaning are unchanged.

** Question: why is this abstraction preferable?

Matcher configuration and contextual rule policy vary independently. Naming the
preparation product makes their sharing boundary explicit, while S-expression
data supplies structural equality and pattern-based lowering. A rule's parser
position and method origins stay with contextual dispatch. Existing CLOS
preparation protocols select independent backend/capability axes; this closed
opcode lowering uses structural =match=. Each mechanism has an identified owner
and does not impose another configuration interface on a language author.

** Question: how is the claim tested?

The native scanner suite adds a shared =<<= matcher under different ranks,
actions and modes, checking independent requests and short/long input plans.
Existing controls cover longest Unicode literals, guards, ambiguity diagnostics,
IR mutation, deferred delimiters, region nesting and source strategies.

The first all-matcher interning experiment exposed a negative control: primitive
=identifier=/whitespace executors already have compiler-hoisted closures.
Wrapping and caching them adds allocation without providing sharing. A second
experiment bypassed their cache but used a uniform multiple-value return carrier;
it still added 96 bytes per one-mode preparation and 1,536 bytes at sixteen modes.
Literal-catalog CPU results were mixed, including a regressed median in that
second run. The final implementation confines matcher-plan sharing to region
and guard lowering, preserves the established primitive/literal paths and uses
a local =defrule= to stage record construction. This is a measured selection
boundary, rather than an assumption that every Scheme value benefits from
interning or a uniform return protocol.

Preparation comparison uses exact =f3dff04= scanner source compiled under an
isolated temporary test namespace. The production package contains no baseline
or legacy executor. The existing =matched-scale.ss fixture-ir= now accepts an
optional declared word matcher, enabling the same mode/position fixture to
exercise identifier, literal-catalog and region configurations. Both native
implementations consume the same compiled IR and source. Each measured product
is scanned afterward and checked for equal token kinds, lexemes, byte boundaries
and final offset. Allocation is admitted only for intervals without collection.
Alternating ABBA order controls sample order; preparation timing excludes IR
compilation and scanning. These controls cannot establish whole-parser speedup.
