* Tokio evidence and downstream ownership

At this exact revision, Tokio is a dev dependency of =gerbil-scheme=. Its Tokio
handoff tests and transport benchmarks qualify requests sent from async callers
to a dedicated Scheme owner thread. The safe production crate does not expose
a Tokio parser executor. The active performance benchmark retains bounded mpsc
and per-request oneshot responses. Receive batching and reused-response-channel
performance candidates were rejected; functional receive-batching tests do not
establish a production scheduling speedup.

The parser's =NativeSession= and borrowed language/results remain confined to
the initialized VM's original OS thread. Any downstream asynchronous adapter
must create and use them on that owner, bound admission, return owned products,
and qualify cancellation, shutdown and latency. Tokio worker concurrency alone
does not establish concurrent Scheme parsing or lower complete-parser CPU.

* Rust downstream integration at fbb43ca

The current manifest and lockfile pin is
=fbb43ca63d3740cb4e19b26fa2abd1ea3ee4ecdb=. Its additional upstream receipt
rejects an admission fast path; it does not change the production encoder.
The earlier qualification above remains historical evidence at its stated pin.

The optional =tokio= feature of =gerbil-parser-ffi= now exposes =TokioParser=.
It initializes the standalone bundle and retains a single language handle on
one dedicated OS thread. Bounded mpsc admission and per-request oneshot replies
follow the upstream qualified ownership design. Admission uses normal async
reservation; the rejected upstream fast path is not included.

The owner copies the completed GPA1 payload into independent Rust storage,
releases its C result before publication, and shares an immutable catalog.
=OwnedParsed= retains the exact source and supports normal artifact views after
VM shutdown. Native handles and GC-managed Scheme values never cross threads.
Queued cancelled requests skip execution. An in-flight cancelled request still
releases its C allocation. Explicit shutdown closes admission and releases the
language before normal SDK cleanup; dropping all clients drains the queue.

This is an async downstream ownership interface, not evidence of concurrent
Scheme execution or an incremental CPU speedup. The existing =qualify.ss host=
entry now includes a real Tokio consumer in a separate one-shot VM process:
32 concurrent requests, alternating ASCII/Unicode, 64 records per request,
642 events, syntax rejection, closed admission, and views retained after cleanup.
Transport unit tests additionally cover queue bounds, queued cancellation and
shutdown ordering. Rust lint and workspace all-feature gates cover the new API.
