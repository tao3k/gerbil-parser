#+title: Engine, Common Library, and Language Interface Boundaries

* Decision and scope

The parser engine accepts language-independent declarations and executes generated
machines. Language-specific token mappings, source-format adaptation, corpus
contracts, and development services belong to language authors or common libraries.
All eight shipped language packages now expose ten production entries independent
of their corpora.
It does not establish complete ISO GQL conformance or a general ANTLR lexer compiler.

* Ownership and dependency direction

| Owner | Responsibility | Excluded responsibility |
|-------+----------------+-------------------------|
| src/compiler, src/grammar | Canonical IR validation, binding, compilation, generated machine | GQL token names and standard examples |
| src/runtime | Recognition, lossless events, generic diagnostics and budgets | ANTLR source-file parsing and corpus execution |
| src/language/entry.ss | Descriptor dispatch and generic policy execution | Loader service registries and fixture admission |
| language-support/entry.ss | Public POO entry declaration over an admitted descriptor | Corpus, test and build requirements |
| language-support/development.ss | Optional descriptor-bound corpus, scanner and build services | A separate recognition algorithm |
| language-support/antlr4-source.ss | Source catalog and explicit terminal lowering | Inferring a token category from a GQL naming convention |
| languages/gql/grammar.ss | Pinned source identity, explicit lexical profile, generated products | Runtime parsing implementation |
| languages/*/parser.ss | Production descriptor and language parse function | Embedded examples or development service registries |
| languages/*/parser-test.ss | Corpus, development entry and independent semantic expectations | Reimplementing the grammar compiler |

The common library depends on the engine. Engine dispatch does not depend on the
common fixture or development libraries. All shipped language packages follow this production/corpus split.
Bash keeps its declared source-parser receipt, HCL keeps its generated native
backend, and TLA+ keeps its layout and structured-proof policy descriptors.
Alignment does not replace these distinct language semantics.

* Explicit imported-source semantics

The ANTLR adapter formerly classified nonliteral lexer symbols by names containing
IDENTIFIER, CHARACTER_SEQUENCE, or UNSIGNED_DECIMAL. It also supplied fixed quote,
comment, and numeric scanner forms. Those assumptions described a GQL lexical
profile, rather than a language-independent ANTLR format contract.

GQL now declares exact lexical bindings and scanner expressions in grammar.ss.
The format macro receives that profile and lowers it to the same canonical
language-declaration route as other grammar surfaces. Literal derivation receives
the same profile; it cannot silently use an implicit second mapping.

#+begin_src scheme
;; A profile is language data consumed by the existing format adapter.
;; The full GQL profile also supplies its syntax kinds, terminals and extras.
(lexical-profile
  (token-bindings ("REGULAR_IDENTIFIER" token identifier))
  (syntax-kinds (LexicalIdentifier token (text)))
  (terminals (identifier LexicalIdentifier))
  (lexical-rules (identifier (identifier)))
  (extras))

;; Question 1: Why is this design better?
;; The token's language meaning has an explicit language-package owner.
;; Changing its spelling cannot silently change the imported grammar semantics.
;; Scheme lists preserve the expression structure and feed the shared compiler.
;; Native POO remains the entry and service composition substrate.
;; Question 2: Why does this design have a scientific basis?
;; Extensible surfaces lower into one compilation core with checked boundaries.
;; Missing bindings fail closed; an independently supplied binding determines
;; the nonliteral terminal, and duplicate keys fail before grammar lowering.
;; These are executable falsifiers, not a proof of full ANTLR/GQL equivalence.
#+end_src

The current profile deliberately preserves the previous scanner categories.
Several upstream numeric and quoted token classes still share engine token kinds.
Their full language equivalence is not proved by moving the mappings. Distinct
class acceptance and upstream lexer equivalence require further semantic controls.
Likewise, this refactor does not prove that the adapter's existing general
alternative-precedence projection reproduces all ANTLR adaptive decisions.

* Production and development entry contracts

#+begin_src scheme
;; parser.ss: production use requires no test corpus or build registry.
(deflanguage-parser-loader (gql-language :: self LanguageLoader.)
  (grammar gql-language-grammar)
  (parse parse-gql))

;; parser-test.ss: optional development facilities over the exact descriptor.
(deflanguage-development-loader
  (gql-test-language :: self LanguageDevelopmentLoader.)
  (grammar gql-language-grammar)
  (parse parse-gql-test)
  (slots fixtures: gql-official-fixtures))

;; Question 1: Why is this design better?
;; Parsing can load without fixture admission, hashing or fixture copies.
;; Development checks retain identity, source integrity and conformance guards.
;; Both entries execute the same admitted descriptor and engine dispatcher.
;; Question 2: Why does this design have a scientific basis?
;; The boundary test requires identical complete event streams for both entries.
;; It also checks that production has no fixture/test/build service slots.
;; Corpus expectations remain independently authored and can reject regressions.
;; The module split itself is our engineering decision, not a paper theorem.
#+end_src

The optional development contract retains owned fixture copies, effective POO slot
validation, descriptor-bound scanner/build capabilities and sealed dispatch.
The production declaration checks parsing identity, metadata and descriptor
products, and rejects development service slots in both keyword and method
forms. Binding also checks effective inherited slots: a POO parent cannot
introduce fixtures, tests, scanner workers or build strategies into production.
The development test dispatcher admits its development contract before reading
service slots. Invalid calls therefore fail at the contract boundary. Shared
private loader-identity utilities avoid duplicate identity rules.
No compatibility forwarding module remains in src/language/entry.ss.

The independent records consumer follows the same split. Its production parser
imports only its grammar; its test file binds an optional development entry over
the exact production descriptor and owns the corpus dependency. The shared
native conformance executable now includes this downstream sample under the
same ten-second child fence. The previous exact-head CI run passed the shipped
language gates on Linux and macOS, then exposed the records sample's missing test
service. That failure is retained as the regression motivating this extension.
The corrected local gate passes all twenty-seven bounded children and reproduces
all twenty native artifact controls byte for byte. The separate CI-shaped records
owner passes with explicit zero harness status, final GC and =OK=. These receipts
do not qualify a new remote head or establish a latency improvement.

* Paper-to-code relationship

[[https://www2.ccs.neu.edu/racket/pubs/icfp24-bgh.pdf][Compiled, Extensible, Multi-language DSLs]], section 1 and Figure 1, supports
an extensible elaboration surface feeding a compilation core with explicit
boundaries. Our adaptation is source-format and Scheme declaration front ends
feeding canonical admission, with runtime consumers using generated products.
The paper does not prescribe our directory names or prove our implementation.

[[https://www2.ccs.neu.edu/racket/pubs/icfp10-cf.pdf][Fortifying Macros]], section 7.2, demonstrates phased declaration processing
for dependent grammar/token clauses. Our profile and source catalog are collected
before terminal lowering and canonical validation. The paper motivates separating
these responsibilities; it does not establish equivalence of the imported lexer.

real import, translation, compilation and link boundaries.

* Language-wide native publication and root obligations

The production descriptor is the native publication authority for all ten
entries in the eight language packages. =parser-test.ss= supplies accepted and
rejected corpus values; the shared conformance owner generates GPA1 and descriptor
binary fixtures from these values. The artifact crate admits those fixtures without
language-specific Rust parser tables. Native CI regenerates the same bytes.

The alignment run exposed three independent contract gaps: HL7 rejection emitted
an engine-owned opaque token outside its published terminal directory; the shell
provider hardcoded a root that differed from its compiled command projection;
and the TLA+ proof product selected its root from catalog ordering instead of its
aliased entry rule. Publication now includes the engine rejection class, source
binding validates its derived root, and Parser IR compilation uses the entry
alias when present. Both generator cache contracts advance together, preventing\nunchanged grammar bytes from admitting outdated compiler semantics. No\nlanguage-specific ABI dispatcher is added.

** Why does this DSL reduce authoring complexity?

#+begin_src scheme
(deflanguage example
  (root document)
  (lex (name Identifier (identifier)))
  (rules
   (document (node Document (repeat (field name name)))))
  (syntax-kinds
   (Auxiliary node ())
   (Document node (name))
   (Identifier token (text))))
#+end_src

The root rule constructs =Document= even though =Auxiliary= appears first in the
published catalog. The language declares recognition and field associations
once. Macro expansion lowers the S-expression to admitted Grammar/Parser IR;
compiled plans supply runtime behavior and publication metadata. POO inheritance
can change an admitted declaration before binding, while ordinary values need
no object wrapper. These responsibilities belong to the engine and common DSL
implementation, rather than a language author's duplicate encoder or Rust grammar.

** Which executable invariants support the design?

For every accepted fixture, the borrowed root kind equals the same handle's
published root, and its text equals the original source. For rejection, there
is no accepted root, but ordered token spans cover the source exactly. Declared
node fields, product/source identity and UTF-8 boundaries are admitted before
navigation. The twenty cross-language controls independently check these rules;
the source-provider negative test rejects an undeclared root at binding time.
These are falsifiable semantic and ownership contracts. They establish neither
complete language-standard conformance nor a performance advantage.

The integrated local receipt covers all twenty native controls, all twenty-six
bounded Scheme DSL/development child processes and 130 Rust runtime tests.
The native admission test reads binary fixture data and has no language-specific
recognition dependency. The unchanged fences and rejected controls are retained;
one accepted and one rejected source per entry establish publication alignment,
not exhaustive grammar coverage. Native CI reproduces the fixture bytes and
qualifies each pushed revision independently.

* TLA+ declarative interface migration

The previous TLA+ interface retained generated IR aliases, manual syntax catalogs,
low-level reference wrappers and release constants in a 1,599-line grammar file.
The public =grammar.ss= now exports syntax descriptors and lexical profiles only.
Four private =syntax/= modules hold core, layout, proof and lexical declarations;
=parser.ss= owns pinned SANY source identity and release metadata. Consumers obtain
IR and machines through descriptor accessors. The topology contract permits only
declarative syntax modules behind the three public interfaces.

#+begin_src scheme
;; Representative declaration: recognition and publication share one source.
(module
 (node Module module-border "MODULE" (field name identifier) module-border
   (repeat (field item module-item)) module-end))

;; Question 1: Why is this design better?
;; Bare rule identifiers and literals preserve readable Scheme structure.
;; The engine derives node kinds, fields and terminals from recognition clauses;
;; authors no longer maintain a parallel publication catalog or generated IR API.

;; Question 2: Why does this design have a scientific basis?
;; Compare canonical recognition before and after elaboration, then independently
;; test accepted/rejected sources, field publication and source identity.
;; A shorter surface is justified by these invariants, not by its line count.
#+end_src

The migration compared seven canonical sections for each of the three TLA+
products: rules, lexical rules, extras, keywords, recoveries, conflict policy and
case sensitivity. All 21 comparisons passed. The proof token is explicitly
renamed =proof-step-name= to distinguish it from the =proof-step= rule. The old
manual catalog advertised =fact= and =definition= fields on =TerminalProof= that
recognition did not emit; the inferred contract correctly publishes =item=.
This is an intentional publication correction, not unchanged artifact identity.
The existing corpus and native lexical/source/snapshot tests qualify this change;
they do not establish complete SANY compatibility or a performance gain.
