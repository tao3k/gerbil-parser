#+title: LR request modeling before optimization selection

* Order of work

Research and current implementation establish the model vocabulary and its
hypotheses. Model qualification then identifies feasible optimization questions.
Only a candidate whose obligations can be established proceeds to an engine
change and complete-request Benchmark. This change extends the research and
model layers; it adds no runtime optimization or new performance result.

* Paper findings and transfer limits

Sperber and Thiemann's [[https://www.deinprogramm.de/sperber/papers/lr-essence-pepm.pdf][The Essence of LR Parsing]], sections 3.1 and 4.1,
separates grammar-static choices from dynamic input. Its binding-time work and
list-loop specialization motivate auditing repeated operations at their actual
binding scope. Constructor elimination must preserve computation order and
multiplicity. Their functional parser is not our explicit-stack executor;
the paper does not establish that our token metadata can be shared.

Wagner and Graham's [[https://harmonia.cs.berkeley.edu/papers/twagner-parsing.pdf][Efficient and Flexible Incremental Parsing]], sections 7
and 8, ties reuse to context/content obligations and discusses when matching
conditions cost more than the reconstruction they avoid. It motivates charging
admission and maintenance work rather than treating a correct reuse guard as a
speedup. Its subtree reuse theorem does not authorize metadata reuse here.

The following scope and cost definitions are derived from those principles and
our code. They are our model hypotheses, not claims made by either paper.

* Current code audit

| Owner | Current behavior | Model consequence |
|-------+------------------+-------------------|
| [[file:../../src/runtime/lr-parser/checkpoint.ss][LR driver]] binding | Runtime, widths, modes, action selector, reduction plans and goto index are bound at driver entry | Grammar-static binding is already present; repeated preparation is not inferred from a reduction count |
| LR input admission | Empty =rest= invokes =next-input= using lexical mode and optionally LR state | An extent starts at actual input admission, not at an offset or mode name alone |
| LR successful reduce | Both executor paths retain =rest= while updating states and values | A stable input can span several reductions, but action selection still depends on the new LR state |
| LR shift | Consumes =cdr rest= | The previous input extent ends; a cache cannot cross this boundary by pointer coincidence |
| [[file:../../src/runtime/lr-parser/recognition.ss][Capture reduction]] | Capture-enabled reductions project token kind/lexeme and construct a pair for nonempty input | Repeated metadata work is a question to measure, distinct from stack prefix work |
| [[file:../../src/runtime/token.ss][Token representation]] | A four-field vector with a string lexeme; no immutable token contract or mutation revision is enforced | Pointer equality and source identity do not prove projection stability |
| Checkpoint/failure/fork return | May pause execution or transfer into selective GLR | The proposed local scope is conservatively withdrawn; resumed and fallback execution need fresh admission |
| EOF | Empty input projects =#f= and may invoke the scanner again on a later iteration | No pair allocation can be saved at EOF; an empty-list sentinel is not an admission generation |

This audit identifies a missing implementation premise: the current token vector
and lexeme can be mutated, but they carry no revision that establishes the
model's stability key. No metadata-sharing implementation is admitted by this
model-only change. It also does not change scanner calls, action selection,
semantic callbacks or fragment pair identity.

* Lean responsibilities

[[file:../../formal/ParserEngine/Lookahead.lean][Lookahead.lean]] uses a logical key with =owner=, =source=, =contract=,
=extent= and =revision=. The contract must bind grammar, prepared plan and
lexical policy. Extent identity denotes actual admitted input. Revision denotes
metadata mutation; neither is an implemented hash or pointer address.

=admitted_projection= requires both key equality and an explicit producer
premise: the stored value equals the pure projection of its basis.
=extent_observations_equal= preserves the ordered sequence of those projected
values within one stable extent. Supersession and mutation reject the old key.
An included counterexample shows why equal keys alone cannot prove correctness.
Effects, mutable object identity, atomic snapshot construction, Scheme compiler
correctness and the producer premise remain implementation obligations.

For an extent with =r= capture reductions, projected metadata cost =M=,
per-reduction check cost =C= and scope setup cost =S=, define:

#+begin_example
Repeated metadata: r * M
Scoped metadata:   0                         when r = 0
                   M + r * C + S             when r > 0
Break-even:        r * C + S <= (r - 1) * M   when r > 0
#+end_example

These are weighted abstract operation costs in one chosen unit. Weights are
hypotheses to validate, not CPU samples. The scoped expression describes a
hypothetical demand-driven strategy and does not select a runtime design.
A singleton extent strictly regresses when =C + S > 0=. An EOF extent with
=M = 0= cannot pay positive admission overhead from saved materialization.
The model retains these negative regimes alongside a beneficial example.

=SharedWork= names preparation, scan, LR, other capture work, validation,
publication, FFI and scheduling. Each =ExtentWork= carries its own reduction count and materialization, check
and setup weights, so EOF and lexeme-dependent snapshot checks need not share
ordinary-token costs. Complete-request baseline/candidate costs add all extent
costs to the shared terms, including =failedAdmission= work. =complete_request_break_even= includes every
extent, so singleton losses cannot be discarded. Common work may cancel only
under the explicit equal-work assumption. =complete_request_with_extra_work=
charges additional work instead of silently canceling it. The equations are
conditional arithmetic statements, not complete parser semantics or CPU proofs.
Scheme-only measurements set consumer FFI/scheduling scope explicitly; they
cannot qualify an unmeasured Tokio request.

* Quint responsibilities

[[file:../../formal/quint/LookaheadScope.qnt][LookaheadScope.qnt]] models scope histories, not LR language acceptance.
=Bind= remains the atomic specification of a successfully established snapshot
and its producer premise. The additional =Observe=, =CommitObserved= and
=DiscardObserved= actions expose the interval between coherent observation and
admission. Commit requires the observed key to remain current; mutation, EOF
admission and supersession invalidate an in-flight observation. Retry requires
an explicit discard and a new observation. =Read= requires active scope and
exact basis/current key equality.
Reduction retains the admitted extent; shift, EOF admission and mutation change
its identity. Source/contract change, cancellation, failure, supersession,
completion, pause and fallback withdraw observations. A new scope starts cold.

Directed witnesses show that ignoring mutation revision or treating EOF as a
permanent sentinel permits stale observations. The finite coordinates are
=0/1= abstractions without wraparound. Each individual action is atomic;
=Observe= still assumes a coherent initial key/value observation. Torn field
reads within that observation, real reentrant callbacks, unbounded token
streams, queue fairness and liveness are not established by sampled histories.
A checked pre/post generation read or an exclusive immutable owner must be
established by a future implementation; merely adding a post-check is not a
proof of that producer premise.
The Lean producer premise and Quint =Bind= abstraction are a named assumption
bridge, not a checked translation between the tools.

* Model-derived decisions and remaining evidence

| Question | Model result | Next evidence before implementation |
|----------+--------------+-------------------------------------|
| Can repeated capture metadata be scoped? | Conditional on stable producer/key and request-wide break-even | Establish immutable admission or mutation detection, including callbacks and string mutation; count its overhead |
| Does the 64-record request benefit? | Not established; total production count/width histogram is insufficient | Record reductions per actual input extent, including singleton, zero-capture, EOF and fallback paths |
| Can EOF be treated like an allocated lookahead pair? | No; the current EOF materialization has no pair allocation | Separate EOF weights and scanner admission behavior |
| Can LR action selection be cached with token metadata? | No such theorem; action depends on changing LR state | A separate state/action equivalence model would be required |
| Can a local capture gain prove end-to-end CPU improvement? | No; every extent and changed common cost must be charged | Existing matched complete-request Scheme Benchmark, then a distinct Rust/Tokio consumer qualification |

The next step is an observation-only trace over existing complete requests to
populate the extent distribution and audit stable-value admission. If the
hypotheses or break-even condition fail, reject this candidate and use the same
cost decomposition to investigate another engine cost. Do not implement a
cache merely because some extents contain repeated reductions.

* Staged admission and failed-work accounting (2026-10-15)

Revisiting section 3.1.3 of Sperber and Thiemann and the actual token accessors
exposed a gap in the initial atomic =Bind= assumption. Construction cannot be
moved across arbitrary effects just because a later key check succeeds.
The current code reads a kind and a mutable lexeme reference; retaining that
reference is not the same as taking a stable content snapshot. The extended
Quint model makes changes between observation and admission explicit. Its
unchecked-commit mutation witness demonstrates stale publication when that
interval is ignored. It does not claim the Scheme runtime supplies revision
numbers or coherent immutable snapshots today.

Lean now records failed snapshot work for each extent, even when its reduction
count is zero. =retryWork= charges each failed attempt's materialization,
validation and discard. For a used extent, the refined condition is:

#+begin_example
r * C + S + failedAdmission <= (r - 1) * M
#+end_example

The earlier demand-driven =r = 0= formula applies only before failed or eager
admission work. =unused_extent_can_pay_failed_admission= formalizes that limit.
A retained counterexample has eight reductions and a favorable no-retry cost,
yet loses after five failed attempts. These are symbolic examples, not observed
request frequencies. Retry counts and lexeme-copy/hash work must be measured
before selecting an implementation. Unbounded retries have no proven progress
or latency guarantee; model safety does not justify a spinning retry loop.

Local validation passed Lean (43 jobs), the complete locked Quint package
(89 directed tests across ten modules and nine sampled invariant runs), and
source-input binding. The scope module contributes 23 directed tests and 1,000
sampled histories of at most 20 steps, seed 1. No runtime optimization or new
CPU claim accompanies this model extension.

* Pending input transport and the next selector boundary

The current [[file:../../src/runtime/lr-parser/checkpoint.ss][driver]] creates a singleton input list at admission, retains
it across reductions, and consumes it on shift. The [[file:../../src/runtime/lr-parser/prepare.ss][action selector]] takes
that list on every query, checks EOF, and projects its first token. Lexical mode
belongs to scanner admission; a later reduction can change LR state before the
same pending token is consumed. The source owner already retains that admitted
mode for post-shift publication.

The functional representations in Sperber and Thiemann motivate studying this
transport boundary; they do not justify replacing a list with a scalar while
silently recreating the list at every action query. Lean Lookahead now proves
that arbitrary ordered reductions preserve the pending token/mode pair and its
shifted publication. The representation must also retain unconsumed lookahead
on fork, failure and pause. No token-field caching or mutation epoch is admitted.

Count transport list cells with =A= actual admissions, =Q= converted nonempty
action queries and =E= escapes needing conversion:

| Representation | Transport cells |
|----------------+-----------------|
| Existing list input | A |
| Scalar with list conversion at each query/escape | Q + E |
| Scalar with native selector input | E, plus independent selector/guard costs |

=scalar_input_break_even= charges all conversions. =request_transport_regresses=
lifts the comparison to complete logical request work only under equality of
every shared term; this does not establish a physical CPU cost. The stronger
=per_query_conversion_regresses= rejects the adapter when queries exceed
admissions. For the logical 64-record action inventory, 192 shifts and 322
reductions already imply 514 nonempty queries when those reductions precede
nonempty lookahead; EOF queries themselves allocate no singleton and must not
be counted as nonempty conversions. The actual EOF/nonempty distribution needs
an execution trace before a numeric cell saving is admitted. The Lean example
with 514 conversions assumes those reductions have nonempty lookahead and is
explicitly a counterexample, not a measured trace.

The next candidate therefore needs an engine-level selector accepting token/EOF
directly, with list materialization only at existing external frontiers. It must
cover literal precedence, case folding, layout, generated direct steps, failure
and selective GLR before implementation. Current list-based selectors and
extension factories remain the semantic authority during this study.

Quint SparseCapture now independently tracks admitted modes and emitted modes,
requires the emitted sequence to be the exact consumed admission prefix, and
rejects another scan or trivia admission while lookahead is pending. Ten directed
histories include reductions changing lexical mode before shift and a fork with
unconsumed lookahead. The first control used =enabled=, which the pinned
TypeScript backend cannot execute; the executable shared admission guard now
owns that check. This is bounded protocol evidence, not an LR grammar oracle.
