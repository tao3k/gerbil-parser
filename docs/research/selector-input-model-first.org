#+title: Token input, captured owned stacks and prepared LR transition selection

* Baseline and completion criterion

This study starts at =7c184acd77b9fcdfec0537be11129b3a8df6616b=, after the
previous sparse-source capture improvement. Its complete 64-record reference
already contains that earlier improvement. The additional CPU result below is
relative to this starting point. Earlier =54746a3= results remain separate.

The workload is 64 ASCII =a=1= records, 256 source tokens, 192 significant
shifts and 322 captured reductions. Every measured request creates a fresh
capture-enabled incremental session, completes scanning and LR execution,
publishes the artifact, and checks complete artifact equality and source validity.
The independently replayed recognition projection is checked before timing.
No language grammar or Rust/C event format is specialized for these records.

The unchanged gate runs five groups of 32 alternating legs, 256 requests per
leg: 122,880 timed requests, with 256 startup requests in each worker. Before
and after reference/reference controls must remain in 0.90 through 1.10;
production P90 must be below 0.95. The fences remain 90 seconds total and five
seconds idle. CPU is worker user plus system time, including natural GC. There
is no forced GC, timed process startup, runtime binding replacement, adjusted
threshold or added warmup after an unsuccessful observation.

* Papers, upstream functions and existing implementation

Sperber and Thiemann's [[https://www.deinprogramm.de/sperber/papers/lr-essence-pepm.pdf][The Essence of LR Parsing]] motivates deliberate
representation and binding-time choices, constructor/selector elimination and
preserving ordered computations. Wagner and Graham's
[[https://harmonia.cs.berkeley.edu/papers/twagner-parsing.pdf][Efficient and Flexible Incremental Parsing]] motivates retaining sufficient
context for reuse and accounting for its maintenance. These sources motivate
the study; their performance results do not establish this implementation's CPU.

LeanPoo is pinned to its current open PR #13 revision
=8561a3ef8120101f956855d128d44ff9507c6703= in both Lake inputs. The review used
[[https://github.com/tao3k/lean-poo/blob/8561a3ef8120101f956855d128d44ff9507c6703/Examples/PrototypeFunctions.lean][PrototypeFunctions]],
[[https://github.com/tao3k/lean-poo/blob/8561a3ef8120101f956855d128d44ff9507c6703/docs/contracts/generalized-prototypes.org][the generalized Raw/Cooked protocol]], and
[[https://github.com/tao3k/lean-poo/blob/8561a3ef8120101f956855d128d44ff9507c6703/LeanPoo/Prototype/DictionaryBridge.lean][DictionaryBridge]]. Functions can be first-class prototype results, while
inverse-bearing representation conversion preserves their typed consumers.
Our model now reuses =DictionaryBridge= for token/EOF versus empty/singleton
input and proves state-specific selector transport. The runtime keeps its
existing Scheme POO preparation boundaries and retained functions; LeanPoo
supplies checked model contracts. No POO lookup is added per token or reduction.
The Lean toolchain remains 4.34.0, and model/library versions are unchanged.

The latest upstream revision also adds
[[https://github.com/tao3k/lean-poo/blob/8561a3ef8120101f956855d128d44ff9507c6703/docs/contracts/closure-lifecycle.org][closure lifecycle costs]] and
[[https://github.com/tao3k/lean-poo/blob/8561a3ef8120101f956855d128d44ff9507c6703/Examples/LifecycleAccess.lean][LifecycleAccess]]. These distinguish cold construction, optional selector
preparation, retained metadata and repeated solves. Minimum declared operation
ceilings do not establish minimum CPU time, and future reuse must not be assumed
to repay preparation. Here the goto plan has an explicit allocation ceiling;
its preparation belongs to runtime construction, while the measured complete
request includes scanning, LR execution, artifact publication and verification.
The CPU result below is therefore a prepared-runtime request result, not a
cold-construction or lifecycle amortization claim. Grammar replacement must
construct a new admitted plan; this change does not introduce cross-source reuse.
The latest library revision rebuilt all 56 model jobs successfully.

The code audit identified three boundaries:

- The selector consumed a transport list although it observes only token/EOF.
- Captured execution forced immutable state/value stack spines, despite existing
  private owned-buffer algorithms and sparse immutable snapshot publication.
- Each ordinary reduction read its production LHS and searched a goto row even
  though production identity and grammar transitions are prepared constants.

The buffer model proves that freezing the remaining active prefix after a pop
matches dropping the same width from the immutable frontier. Its entry-state
observation therefore remains exact. The new Quint counterexample deliberately
rewrites a retained snapshot as if it shared later-mutated buffer storage;
=SparseSafety= rejects that implementation. Model input identity binds the
real stack helper, source owner, selector, batch executor and their controls.

* Implemented engine changes

** Token/EOF selector protocol

The ordinary and layout selectors now take =(state, token-or-false)=. Literal
priority, Unicode case folding, first duplicates, EOF, rejected layout shifts
and original action-pair identity are retained. Batch/GLR callers project the
head of their borrowed suffix; streaming execution holds the token directly.
Capture reduction receives token/EOF and the already known post-pop entry-state.
It continues reading lookahead metadata at each existing capture operation.

One LR transition macro has two compile-time axes: stack storage and input
storage. Each of the four generated executors has a direct static call site.
Generated reduction steps retain their borrowed list-tail contract. The input
policy checks this capability once at entry so those steps can reuse one tail
across reductions, instead of constructing a list for every query.
Arbitrary five-argument shift observers retain immutable list frontiers.
Language declarations acquire no new worker, scanner or input-policy option.

** Captured owned state/value buffers

Capture-enabled execution can use the existing request-private state/value
buffers. Its recognition stack remains persistent. Only selected snapshot
boundaries copy the active buffer prefixes into immutable checkpoint lists.
Fork/failure/public checkpoint boundaries also freeze their state and values.
Owned arrays never become snapshot fields or observer arguments.

The capture owner receives the post-pop entry-state directly; it does not walk
a second state-list prefix. The physical-frontier control verifies that frozen
state spines are distinct after all later buffer writes, while their values,
complete grammar tree, modes, callbacks and artifacts equal the persistent
reference. This checks actual admission into the owned path.

** Bounded goto preparation

Preparation transposes each distinct LHS into a state-indexed target column.
Productions sharing an LHS share that column. Reduction then indexes by
production and remaining state. The original sparse row primitive constructs
each cell, preserving first-key and missing-target behavior.

Before allocating columns, preparation checks =states * distinct-LHS <= 65536=.
Above that budget it retains the sparse algorithm. The bound covers column
cells; production references and other existing grammar data remain separate.
The original goto index is built once and remains available to generated steps.
Runtime clones and semantic-backend preparation retain the same admitted plan.

* Generated-code finding and rejected measurements

The first procedure-valued dispatcher computed an =execute= binding. On the
selected SDK/GCC build, inspection of its emitted Scheme showed an unused
selector followed by a direct persistent-executor call. A physical state-spine
control then failed even though value comparisons passed. The generated-code
observation is scoped to this build; compiler-version coverage remains open.

Explicit static branches now emit all four intended executor calls. The physical
spine control passes. This is an executable admission condition, not an inference
from the presence of source branches or a successful artifact comparison.

* Reproduction and current ownership

The reference builder freezes all eight protocol owners, including runtime state,
layout, prepare, recognition, batch, checkpoint, transfer and source parser.
Each worker must load those native files from its requested image. Shared stack
storage helpers, incremental-session code and the records grammar must match.
The package lock, SDK and GCC are shared. Startup and IPC remain outside worker
CPU; complete artifact checks and natural GC remain inside.
