#+title: gerbil-parser

A programmable syntax engine in Gerbil Scheme, with declarative language packs,
lossless parse artifacts, and Rust integration.

Languages declare syntax and metadata; the engine owns scanning, grammar
normalization, LR construction, parsing and result publication. Hygienic macros
and POO prototypes provide constrained extension points. Gerbil remains the
compiler authority for generated Rust products.

This is an active implementation and research project. Supported syntax and
portable products are qualified per language and target; a shared authoring
interface does not imply complete language coverage or backend parity.

* Experimental Fold qualification (not accepted)

The engine-owned [[file:t/benchmarks/parser-throughput/README.org][parser throughput qualification protocol]]
defines hard 1000/10000/100000-request wall gates of 0.010/0.100/1.000 seconds
and a minimum 100000 requests/s. It reports per-request P95/P99 with explicit
units, fails inadequate candidates at preflight, and requires twenty batches
per load for full acceptance. Its included generated line fixture is NOT full
Org, Rust/Tokio or Python acceptance; real adapters must retain their own
compiled source identity and semantic oracle. No achieved Org speed is claimed.

The actual generated Org Fold now has upstream =real.ss= admission and a
separate diagnostic =profile.ss=. Both compare complete independent events;
neither uses an Orgize runtime or FFI queue. The real-Fold preflight remains
failed, and the source-fact reuse experiment was reverted. See the
[[file:docs/research/event-fold-whole-path-performance.org][whole-path evidence and optimization plan]];
diagnostic call counts are not uninstrumented performance claims.

The guarded idle-state experiment removes irrelevant mutable-state execution
without assuming read-only configuration is zero. Two sequential changing-input
preflights measure 102.591/103.150 ms per 1000 requests (P95 135/152 us,
P99 403/392 us, 9747.444/9694.619 requests/s, 30 GCs), versus same-source control
131.982/138.163 ms and 56 GCs. No-GC request allocation counter means decrease
36-44 percent, including observer overhead; peak RSS increases slightly.
The 10 ms gate remains failed. This is not twenty-batch, FFI, Tokio, Python or
baseline acceptance. Lean transition obligations and Quint lifecycle histories
are bound to actual AOT controls by the native ASCENT evidence owner; successful
models and conformance cannot fill the missing matched-performance requirement.

A single common-byte kernel adds necessary-byte classification without
generating a separate kernel for every byte region. Two subsequent matched
preflights measure 88.284/90.422 ms per 1000 changing requests, P95 112/113 us,
P99 312/356 us, 11327.081/11059.255 requests/s and 27 GCs; current-source control
is 122.040/120.904 ms and 56 GCs. No-GC allocation means decrease 38-52 percent
but process peak RSS increases about 1.2 MB. Real AOT complete-tape controls
pass; the 10 ms gate still fails. These opt-in experiments do not change the
accepted baseline or qualify Rust/FFI/Python/Tokio performance.

Subsequent active-state cofactoring and loop-local guard caching both passed
24 real AOT controls but regressed matched preflight wall time. Both were
reverted; modest RSS savings do not substitute for throughput acceptance.
The existing best experimental product and production baseline remain intact.

Direct-tape effect-only transitions remove private owner-return plumbing and
restore syntactic tail positions without adding a runtime cache. Two matched
1000-request preflights measure 72.575/73.322 ms, P95 96/96 us, P99 142/142 us,
13778.849/13638.471 requests/s, five GCs and peak RSS 29.64/29.67 MB, versus
the previous best experimental control at 96.537/90.398 ms and 27 GCs.
All 24 real AOT event-tape controls pass. This is additional preflight evidence,
not the still-failed 10 ms gate, twenty-batch acceptance or a production change.
Matched no-GC request allocation means decrease from 123/231/122 KB to
16/25/32 KB across plain-links/quote-heavy/doc inputs, including observation
overhead and excluding GC-interrupted requests. Lean, Quint and native Ascent
bind source controls to the actual AOT product; performance admission is open.

The next experimental =tape-pruned= product removes discarded pure branches,
including ordered cursor-derived scans only inside a validated byte loop.
Errors, future queries, unknown effects and frame changes remain barriers.
Matched sequential 1000-request preflights are 69.201/71.196 ms, P95 90/96 us,
P99 144/156 us, 14450.658/14045.733 requests/s and peak RSS 29.475/29.491 MB;
the retained tail control is 74.197/73.520 ms. GC remains five per batch.
All 24 real AOT tapes and four effect/range controls pass. The <=10 ms gate
still fails: no twenty-batch acceptance or production baseline promotion.
Removing the remaining named-helper owner results or reusing token offsets
regressed wall time and was reverted despite smaller static call graphs.

The next =tape-run= experiment coalesces overwrite-only ordinary-byte segments:
one segment scan, then the last byte's seven inline metadata overwrites. No
runtime cache; active modes, eventful/state-dependent bodies and special bytes
retain their original execution. All 24 real AOT tapes and five admission
regressions pass. Candidate 1000-request diagnostic wall is 62.059--103.421 ms,
P95 86--263 us, P99 96--575 us, 9669--16114 requests/s, peak RSS 29.426--29.458 MB,
with five GCs. Matched controls include major non-CPU pauses; one pair regresses
amid unrelated host CPU contention. These measurements do not qualify a stable
speedup, the <=10 ms gate, or the still-unrun 100000-request twenty-batch matrix.
The baseline is unchanged; the path remains an opt-in research candidate.

The rejected dependency/effect execution-plan experiment reused official list
utilities and the compile-time list builder. Its 1000-request matched preflight
is 216.313 ms (4622.931 requests/s), versus 218.790 ms for the control; both
fail the 10 ms gate. This single batch is not an accepted speedup or a full
twenty-batch result. Its lowering integration was rolled back; conservative
analysis tests remain. Shared source classification, typed state execution
and actual event-consumer integration remain open architectural work.

The combined frame/current-byte/dependency-ABI/event-buffer candidate was also

experiment did not qualify removal of consumer work. No twenty-batch or

=parser-actor-support.ss= is the public facade for explicitly created local
Gerbil actors. Applications own worker count and lifecycle; imports start no
background service. =spawn-parser-actor= accepts an already prepared machine,
=parser-actor-parse= returns the same lossless artifact as synchronous parsing,
and =parser-actor-stop!= joins the worker. Timeout bounds reply waiting rather
than preempting an active parse. Keep the shared machine immutable after
initialization; actor scheduling does not change the LR algorithm.
* Language authoring

A language pack exposes three Scheme interfaces:

| File | Responsibility |
|------+----------------|
| =grammar.ss= | Declarative syntax and pinned grammar resources |
| =parser.ss= | Production POO Loader, metadata and parse entry |
| =parser-test.ss= | Development Loader, fixtures and declarative conformance tests |

Grammar sources and corpus files remain resources beside these interfaces.
Versions, contracts and source digests belong to metadata, not versioned module
names. Scanner implementations, parser state and C/Rust bridge code belong to
the engine.

For example, a small identifier language declares its syntax in =grammar.ss=:

#+begin_src scheme
(import (only-in :gerbil-parser/language-support/grammar deflanguage))
(export example-syntax)

(deflanguage example
  (syntax
    (lexical
      (root name)
      (lex (identifier Identifier (identifier)))))
  (rules (name (node Name (field value identifier)))))
#+end_src

Its =parser.ss= publishes the entry through the Loader:

#+begin_src scheme
(import (only-in :gerbil-parser/language-support/entry
                 deflanguage-parser-loader)
        ./grammar)
(export example-language parse-example)

(deflanguage-parser-loader example-language
  (grammar example-syntax)
  (parse parse-example)
  (slots metadata: '((language . "example")
                    (version . "v1")
                    (contract . "example.syntax.v1"))))
#+end_src

The Loader is a POO object. Inheritance, value overrides and extension contracts
are admitted before publishing the parse entry. Fixture values are ordinary
slots; the engine owns evaluation, catalog construction and service binding.
=deflanguage-parser-tests= constrains test declarations and checks acceptance,
lossless source, identities and structural expectations.

See the [[file:languages/README.org][language authoring guide]] and
[[file:docs/architecture/0018-downstream-language-products.org][downstream product guide]] for development Loaders,
POO extensions, fixtures and product generation.

* Execution and integration

| Product | Execution boundary |
|---------+--------------------|
| Scheme library | Prepared engine parser returns a lossless ParseArtifact |
| Independent Rust AOT | Generated immutable scanner/parser tables run in the generic Rust runtime; no Scheme VM at request time |
| C ABI and Rust FFI | A reusable Gerbil runtime and language handle execute Scheme parsing; Rust owns result buffers and borrows indexed views |

Parse artifacts preserve source text, syntax structure and spans, with source
and grammar identities. The artifact is the shared publication boundary for
traversal and downstream tooling.

The language-independent C ABI initializes the runtime once and reuses handles
across requests. Its optional Rust Tokio integration queues requests to a
persistent Scheme owner thread. Applications own queue limits and lifecycle.
See [[file:rust/gerbil-parser-ffi/README.org][Rust FFI and Tokio ownership]] and
[[file:rust/gerbil-parser-artifact/README.org][Rust artifact admission and navigation]].

Independent AOT uses the same admitted Grammar/Parser IR through a separate
product gate. It does not automatically support every Scheme source parser or
POO policy. See [[file:docs/architecture/0006-rust-aot.org][Rust AOT design]] and the
[[file:t/fixtures/runtime-record-assignments/README.org][standalone record-language consumer]].

* Build and try

Use the repository's Gerbil SDK environment and dependencies pinned in
=gerbil.pkg=. Scheme compilation uses the SDK's GCC configuration.

#+begin_src sh
gxpkg deps --install
GERBIL_BUILD_CORES=12 gerbil build
GERBIL_BUILD_CORES=12 gerbil env gxi build-gparse.ss compile
.gerbil/bin/gparse help
.gerbil/bin/gparse check "1 + 2 * value"
#+end_src

The command is an optional consumer of the library. It does not own a separate
parser implementation. Rust workspace checks run with:

#+begin_src sh
cargo test --workspace --all-features --locked
#+end_src

Native Scheme, generated products and real C/Rust hosts have separate
qualification lanes. See the [[file:docs/architecture/qualification.org][qualification guide]] for their commands and
[[file:.github/workflows/ci.yml][CI entrypoint]] for the current job graph.

* Reference languages and implementation boundaries

The builtin packs are Arithmetic, Bash, HCL, HL7, FHIRPath, openCypher, GQL and
TLA+. All use the three-interface authoring boundary. Their syntax coverage,
source admission and portable capabilities differ; consult the
[[file:languages/README.org][per-language status]] before selecting a product.

Bash currently uses the shared Scheme source engine. Complete standalone Bash
Command/Source AOT remains open. Scheme-only CST policies also require a shared
representation and parity evidence before independent Rust execution.
