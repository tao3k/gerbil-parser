#+title: Semantic sequence representation and repeated validation

* Shared engine question

After the [[file:request-owned-lr-stacks.org][rejected vector-stack experiment]], this study examines
the semantic sequence boundary used by generic and generated reductions,
field/alias actions, source relocation, and artifact publication. The owner is
=src/runtime/funcs.ss=. Grammar declarations and parser metadata do not change.

The admitted internal sequence representations are proper lists of recognition
children, concatenation branches, position views, and event-program sequences.
List leaves come from engine constructors and the standard list builder. The
sequence visitor is not an arbitrary Scheme list validator; malformed or cyclic
lists are outside this internal contract.

* Repeated full-list scans

=recognition-sequence->list= previously called =list?= to classify an already
materialized leaf. =recognition-sequence-for-each= repeated this check, and
branch materialization classified its leaves again with =list?=. Validating a
proper list traverses its spine, although these sites need only distinguish
the outer representation. Repeated actions over a width-n materialized leaf
therefore paid an extra O(n) scan per classification.

The engine now recognizes empty/list leaves using the outer =null?=/=pair?=
tag. This makes classification O(1); actual publication still visits every
child. Endpoint lookup, field/alias construction, and event-program behavior
retain their original algorithms. No claim is made that all reduction work
becomes constant time or that this eliminates every quadratic construction.

#+begin_src scheme
;; Inputs are admitted engine sequences, not arbitrary external values.
(def (recognition-sequence->list sequence)
  (if (or (pair? sequence) (null? sequence))
    sequence
    ;; The existing branch/view/event materializer follows here.
    (materialize-sequence sequence)))
#+end_src

Why is this design preferable? Grammar authors declare rules and closed
field/alias actions. The engine establishes and preserves the semantic
representation invariant. Scheme's disjoint pair/record representations allow
the engine to exploit that invariant without introducing author-facing storage
annotations or backend-specific syntax.

Why is it scientifically testable? Returning an admitted list must preserve
its identity. Branch order, nested relocation contexts, source bounds, visitor
exceptions, and complete artifacts must remain identical. The existing sequence
controls cover those observations. Matched native full requests are required
for performance claims; removing a scan alone is a structural complexity result.

* Official source correspondence

The installed Gerbil =std/list/list.ss= uses =pair?= in algorithms whose inputs
are admitted lists, including =duplicates= and =length=?=. Its
=std/list/list-builder.ss= builds proper lists using one fresh cons per emitted
element and returns the head's cdr. Our materializer already uses this official
builder. These local source observations support responsibility for the input
invariant; they do not prove an end-to-end parser speedup.

* Continued cost attribution

The generic LR action lookup also performs case folding after an exact literal
miss in case-insensitive grammars. Several reductions may inspect the same
lookahead before its shift. Before changing that ownership, count actual case
folds and distinguish literal lookup, generic-token fallback, layout, and
contextual lexical modes. This is a research hypothesis, not an implemented
normalization cache or a measured dominant cost.
