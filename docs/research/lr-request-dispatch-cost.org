#+title: LR Request Dispatch and Official Inline Contracts

[[file:lr-owned-stack.org][Request execution research index]]

* Evidence and decision

The compact-child study reduced allocation but failed complete CPU admission;
its production changes were restored. An independent macOS native sample then
observed ten seconds of the retained baseline executing real representative
GQL complete source requests. The compiled workload performs 30000 requests
per invocation and checks the complete final product; ten invocations completed
with the original 120-second watchdog. Sampling is an attribution experiment,
never a performance-admission run.

The sample contained 8437 main-thread snapshots. Top-of-stack observations
included 1005 in the LR driver module, 529 in publication, 406 in tokens,
393 in reduction plans and 303 in the action index. These are module-level
observations, not exclusive Scheme-function timings. Gambit's generated module
handlers combine multiple procedures and tail calls obscure their Scheme
callers. GC, runtime primitives and unresolved frames remain in the report;
they must not be assigned to a parser subphase without further evidence.

This evidence supports studying hot checked access boundaries alongside action
selection. It does not prove that token access alone accounts for a particular
CPU percentage or that inlining will improve a complete request.

* Official implementation mechanism

Gerbil's =core/contract.ss= defines =definline= in terms of a lifted dispatch
rule and a normal contracted procedure. =std/time/precise.ss= uses it for
accessors; =std/text/parser/char-set.ss= uses it for small predicates. The
compiler exports inline rules through SSXI. The experiment follows that public
mechanism rather than introducing a parser-specific accessor macro framework.

#+begin_src scheme
(definline (token-kind (token : :t)) => :t
  (vector-ref token 0))

;; Both forms retain checked vector reads; neither caches a token's contents.
(token-kind source-token)
(map token-kind source-tokens)
#+end_src

The deliberately broad argument and return type preserves the original vector
protocol. The constructor still creates the same four-element vector; =token?=
still validates its complete original shape. This experiment changes direct
call lowering, not token admission, metadata, lexical modes or action priority.

** Question: why use this Scheme/Gerbil design?

A single procedure body supplies both first-class calls and compiler-staged
calls. The official expander and optimizer own lifting, hygienic argument
bindings and inline metadata. Parser consumers keep their existing names and
contracts; no extra runtime object or public DSL configuration is required.

** Question: why is the design scientifically justified?

The baseline sample supplies a concrete investigation boundary. Scheme tests
must compare direct and first-class reads, mutation visibility, malformed
vectors, constructor behavior and complete LR/GLR products. Compiler output
must show actual call lowering. These semantic and lowering observations remain
separate from the unchanged four target CPU margins and control gates.

* Qualification

The standalone inline candidate was rejected. Keep all four target CPU ratios below 0.95,
all original controls and tails, and the SDK repeat-band overlap. Bind measured
source and actually selected native images. Python uses the locked =uv= project;
Scheme computes statistical admission and native ASCENT reviews receipts.
CI retains its existing owners and budgets. No allocation-only or stage-only
claim can authorize a push.

* SDK repeatability: controlled measurement ownership

The rejected request-bounds trajectory remains rejected. Its raw SDK samples
allocate the same 4144336 bytes per 1000-call batch in both roles. Collections
occur only in sample 38 or 39; the median separation also appears in batches
without GC. The observed median separation therefore cannot be explained as
one role's P50 including a timed collection. Baseline heap sizes differ by
about one MiB, which is an observation rather than a causal explanation.

A fixed four-role diagnostic placed an identical source-level SDK probe before
and after the existing request workload. Probe medians changed within a role,
and substantial wall/CPU differences were observed. The probe's source closure
is not the original compiled control closure. These diagnostic samples cannot
replace admission samples or prove that heap state causes the original gap.
All four roles and their negative observations are retained.

Native identity inspection found another uncontrolled boundary: the original
roles selected different compiled images for both the SDK caller in
=record-access= and the shared sampler in =parser-stage-cost/benchmark=.
Identical source text does not establish an identical native caller. Build
metadata and code placement can differ even when the encoder primitive itself
is unchanged; binary differences alone do not establish a CPU cause.

The follow-up =parser-shared-control-study= freezes the baseline caller and
sampler images into both roles, including their phase-zero images. Each engine
keeps its own frozen runtime closure. The collector rejects differing selected
measurement-image digests and reference-image drift, in addition to candidate
source/product drift. Existing evidence tests exercise these rejection paths.
This changes experimental ownership, not parser thresholds or CI lanes.

The experiment retains the original reference/candidate/candidate/reference
order, 40 samples of 1000 calls, complete-product comparisons, four mandatory
CPU margins, control tail limits and SDK repeat-interval overlap. Import-only
preparation is symmetric and outside timing. A new result cannot convert the
previous failed trajectory into a pass. Measurement-image equality is a
necessary control condition, not a performance result or a remedy proven to
make SDK timing reproducible.

** Shared-image experiment result

The first shared-image four-role qualification also failed. Reference SDK
medians were 7.257 and 7.762 milliseconds per 1000 calls; candidate medians
were 7.063 and 7.115. Their aggregate ratio was 0.944004, outside the original
five-percent control bound, and the repeat intervals were disjoint. The
representative GQL prepared-LR conservative ratio was 0.967533, independently
below the required benefit. Native Scheme rejected admission and ASCENT
retained the missing CPU claim. Image equality therefore did not restore
repeatability or qualify the candidate.

An attempted native-call interception failed because changing an exported
binding did not redirect the compiled caller. Its complete failed receipt is
retained; no SDK closure was captured, so this is not a before/after result.
The replacement benchmark explicitly owns a compiled encoder closure:

#+begin_src scheme
(call-with-record-sdk-control
  (lambda (encode expected)
    (measure-parser-component '(sdk-native-before utf8) 40 1000 encode expected)
    (record-request-main)
    (measure-parser-component '(sdk-native-after utf8) 40 1000 encode expected)))
#+end_src

** Question: why use this Scheme ownership boundary?

A continuation receives one native encoder closure and its complete expected
result. Its payload remains live across both phases. The official compiler
keeps direct imports; the diagnostic does not depend on mutable-binding
interception or source-interpreted encoder bodies. The ordinary admission
entry still uses the same 4096-character input, 40 samples and 1000 calls.

** Question: what can this experiment establish?

The =record-repeatability= entry compares the same compiled closure before
and after a complete request workload in one VM. Each batch validates its
complete output. Shared caller/sampler digests remove native-image variation
between roles. Heap snapshots and no-GC samples remain observations; a time
change does not identify heap state, scheduling or hardware frequency as its
cause. Extra diagnostic phases cannot replace ordinary admission receipts.

[[https://kar.kent.ac.uk/33611/][Kalibera and Jones (2013)]] distinguish uncertainty between builds,
executions and iterations and motivate repetition at the level that varies.
[[https://users.elis.ugent.be/~leeckhou/papers/oopsla07-stat.pdf][Georges, Buytaert and Eeckhout (2007)]] separate startup and steady-state
measurement and discuss scheduling, locality and system effects. These support
separate diagnostics for native-image, VM and sample variation. Their Java/JIT
results are not evidence about Gerbil AOT, nor do they authorize changing the
fixed parser admission rules. Our two-repeat range is an admission control,
not a statistically calibrated confidence interval.

** Encoder-entry identity and output scheduling

The complete retained/fresh/retained contrast did not support payload age as a
uniform explanation. Most fresh medians were near the surrounding retained
medians, while the ordinary entry sometimes remained slower. Standalone Gambit
C lowering of the retained factory source showed two encoder closure entries:
one inside the exported factory and another copied into its same-module
=main= caller. Their instruction sequences perform the same primitive call;
this establishes duplicated entry locations, not a proven timing cause in the
previously measured binary.

The =sdk-control= module now owns the encoder factory separately from request
measurement. The request module's lowered Scheme contains no encoder primitive
body. The ordinary entry returns the measured encoder to the diagnostic, which
checks =##closure?= before comparing =##closure-code=. Four complete roles
confirmed actual code equality between ordinary, retained and fresh encoders.
The internal primitives are used only for this checked diagnostic, not parser
contracts or unchecked runtime access. Shared-image admission also binds the
factory's selected images in both roles.

Despite entry equality, one role observed substantially higher CPU medians
than the others. Code duplication therefore cannot explain all repeatability
failures. These observations do not establish a specific hardware-frequency,
processor-placement or background-thread cause.

The next fixed contrast examines output scheduling on one retained native
encoder: immediate/deferred/immediate. Immediate mode writes and flushes every
row between timed batches; deferred mode retains the already collected rows
and emits them after all batches. Encoding, semantic validation, 40 samples,
1000 calls per sample, initial GC and natural timed collections are unchanged.
The default remains immediate for request progress. No timeout or CPU threshold
changes. This is a measurement-interference diagnostic; it cannot be admitted
as an ordinary nine-stage receipt.

** Canonical CPU clock intervals

The output-scheduling contrast completed all four roles. Deferred SDK medians
were 6.735000000004043, 6.734000000005014, 6.735000000002489 and
6.760000000004651 milliseconds in reference/candidate/candidate/reference
order. The intended shared endpoint was 6.735 milliseconds, but binary
subtraction of cumulative floating CPU counters separated it numerically.
This is a concrete false separation at a timer tie, independently of the
larger earlier fluctuations. The diagnostic remains a diagnostic.

Gambit's =os_time.c= getrusage path converts integral timeval seconds and
microseconds to floating seconds. The installed Gerbil precise-time library
keeps seconds and subsecond fields integral. The sampler now reconstructs
bounded cumulative CPU timestamps as integral nanoseconds before subtracting
user and system intervals. It publishes both =cpu-ns= and display milliseconds;
summary nanoseconds are independently reconstructed by native admission.

Admission uses these exact intervals and the original exact fractions
=19/20= and =21/20=. Target comparisons remain strict, control comparisons
inclusive, and SDK repeat ranges must still overlap. No tolerance is added.
A Scheme regression checks equal clock intervals with different origins,
separate user/system contributions, and a genuine one-microsecond gap that
must remain separated. Ten Scheme modules pass 109 Cases with the standard
120-second total and five-second idle watchdog.

The ordinary SDK control now defers row output until its unchanged 40 batches
complete. Parser stages retain immediate progress output. Every ordinary
receipt must also contain one checked encoder-entry identity witness; missing
or duplicate witnesses are rejected. All these conditions flow through native
Scheme admission and the existing ASCENT evidence collector, with unchanged
CI lanes. The =parser-sdk-canonical-study= binds engine and shared measurement
sources before fresh sampling. Earlier failed or censored trajectories are
not rounded, pooled or retroactively accepted.


** Fresh ordinary-request admission

The source-bound =parser-sdk-canonical-study= completed the fixed
reference/candidate/candidate/reference sequence. Every ordinary role retained
40 samples of 1000 calls for each of the eight parser stages and the SDK
control, complete artifact equality, a checked shared encoder-entry witness,
and a successful supervised exit. The two reference SDK medians were 7.002
and 7.013 milliseconds; candidate medians were 6.942 and 7.101 milliseconds.
Their intervals overlap and the aggregate candidate/reference ratio is
=14043/14015=, approximately 1.002. This admits the original calibration rule;
it does not establish uniform SDK timing or explain every earlier fluctuation.
