#+title: Canonical LR table admission and staged execution
#+startup: overview

* Prepared capability and request-local layout execution

The table contract derives layout capability from canonical productions. The
execution boundary must preserve that decision: ambient dynamic parameters are
request data, not evidence that a prepared runtime admits layout semantics.
At parent =27f5471=, a plain runtime accepts one =word= token normally, but the
same runtime rejects it inside an outer column table and reference frame. The
old action lookup consults =current-layout-columns= without its own capability,
so an unrelated frame can remove the ordinary shift.

The LR executor now captures its prepared layout capability once alongside
case policy and indexes. Its deterministic loop and both GLR lookups pass that
value to the private action selector. Only a layout-capable runtime consults
dynamic source columns. Existing GLR memo keys and acceptance already use
runtime capability; branch-local layout shifts and closing reductions retain
their existing owners. This fixes capability leakage without changing grammar
declarations or introducing a request-time generic dispatch protocol.

The tokenized source boundary independently binds its own columns and empty
initial frames for every request. Plain requests bind no columns; layout
requests construct columns from their own source. Parameter restoration protects
an enclosing request after acceptance or rejection. Layout ordinary literals
also use the same prepared casefold lookup as plain LR, followed by the existing
guard/column decision; a second whole-string conversion path is removed.

#+begin_src scheme
(def runtime
  (lr-prepare (compile-lr-spec '((root (alias Root (token word)))) 'root)))
(def tokens (list (make-token 'word "x" 0 1)))
;; These values belong to an enclosing source request, not runtime's grammar.
(parameterize ((current-layout-columns (make-layout-columns "x"))
               (current-layout-frames '((100 . "outer"))))
  (let-values (((root rest) (lr-parse/prepared runtime tokens)))
    (null? rest))) ; => #t, matching execution outside the dynamic bindings

;; Source ownership is bound once at the existing request boundary.
(parameterize ((current-layout-columns
                (and (lr-runtime-layout? (parser-machine-runtime machine))
                     (make-layout-columns source)))
               (current-layout-frames '()))
  (parse-tokenized/with machine digest source tokens parse-significant policy))
#+end_src

** Question: why is this design preferable?

The symbolic grammar determines the immutable prepared capability. Dynamic
parameters carry only request-owned coordinates and branch frames. Keeping
these roles distinct lets the same prepared parser run from ordinary code,
callbacks or nested services. The existing Scheme request scope handles binding
and restoration, while named LR algorithms retain explicit prepared arguments.
POO/macro composition continues to select the declaration before lowering;
authors add no layout switch, column builder or cleanup callback to their three
interfaces. The existing casefold index is reused rather than implementing a
second lexical algorithm for layout requests.

** Question: how is the claim scientifically tested?

The matched counterexample changes only ambient parameters around the same
runtime and tokens. Permanent controls compare complete artifacts outside and
inside those bindings, under both requested semantic preferences, with a plain
grammar and a dynamic-precedence fork grammar. The independent materialized GLR
entry exercises its fast and memoized lookups; a streaming driver checks token
callbacks. Separate source controls execute success/rejection/success and require
the original outer parameter identities after each request. ASCII and Unicode
casefold controls check row identity, case-sensitive token fallback, primary
shift and blocked-shift reduction fallback. They do not prove every possible
layout grammar balanced or every compiler-generated fallback equivalent.

The [[https://small.r7rs.org/attachment/r7rs.pdf][R7RS-small report]], Section 4.2.6, specifies temporary dynamic parameter
values and restoration. The installed Gerbil =2591dcd= runtime
=src/gerbil/runtime/control.ss= delegates =call-with-parameters= to Gambit's
=##parameterize1=. This is the existing language mechanism, not a replacement
scheduler or private dynamic-binding implementation. The report motivates the
scope boundary; actual Gerbil controls qualify the implemented request behavior.
No CPU, allocation or concurrent actor performance benefit is inferred.

** Checkpoint and contextual execution admission

Request isolation alone does not establish resumability. At parent =36c9f84=,
=lr-initial-checkpoint= accepts a layout runtime, although =lr-checkpoint= and
its prefix snapshot carry neither source columns nor branch reference frames.
The contextual executor uses this checkpoint record and likewise admits a
self-consistent layout product. The native baseline explicitly constructs both
objects; it does not claim that a particular continuation corruption was
observed. Its terminal catalog contains the fixture's actual =word= token, so
the counterexample is independent of a mismatched scanner declaration.

The LR owner now defines =require-lr-checkpoint-runtime!= and applies it before
semantic backend selection or checkpoint construction. Contextual preparation
uses that same requirement before building positions or a scanner plan. The raw
contextual entry delegates to prepared admission and execution, eliminating its
separate validation/indexing/scanner path. Both entries consequently own their
published digest strings; mutation of the caller's product cannot rewrite a
previously published raw artifact. These are execution requirements derived
from the existing continuation representation, not new language author slots.

#+begin_src scheme
;; A continuation must own every value needed to resume execution.
(def (require-lr-checkpoint-runtime! runtime)
  (when (lr-runtime-layout? runtime)
    (error "LR checkpoints require a runtime without layout")))

(def (lr-initial-checkpoint runtime tokens)
  (require-lr-checkpoint-runtime! runtime)
  (lr-initial-checkpoint/selected
   (lr-runtime-for-current-semantic-backend runtime) tokens))

;; Raw and prepared calls share product admission and private plan ownership.
(parse-source/contextual/prepared
 (prepare-contextual-parser machine product) source)

;; Full source layout parsing retains its GLR owner. The high-level incremental
;; entry returns a complete artifact and no reusable checkpoint for this runtime.
(let-values (((artifact tokens modes snapshots)
              (parse-source/checkpoints layout-machine source 1)))
  (and (parse-artifact-valid? artifact)
       (not tokens) (not modes) (equal? snapshots '#())))
#+end_src

*** Question: why is this design preferable?

The symbolic production capability is checked by the owner of continuation
state. Plain checkpoint, contextual preparation and full layout execution
therefore have explicit, consistent requirements. Scheme procedures reuse one
admission algorithm and one owned contextual plan; POO/macro declarations still
lower through the same machine without duplicated author configuration.
Supporting layout continuations later requires an owned coordinate/frame
representation with branch semantics, rather than an ambient parameter switch.

*** Question: how is the claim scientifically tested?

snapshots for single-line success, multiline success and rejected layout input.
The contextual identity control mutates the original product without freezing
the reference artifact; ordinary HCL, Unicode and rejection paths must still
agree with prepared execution. This establishes the tested capability and
ownership boundary. It does not implement layout continuation capture,
contextual GLR branch state or prove arbitrary layout grammars balanced.

* One boundary from productions to executable tables

This completes the structural table boundary identified in
[[file:prepared-lr-action-plans.org::*Complete production admission before execution products][the production admission study]]. Production semantics and LR table structure
are related obligations with distinct owners. =src/compiler/lr.ss= admits
production declarations. =src/compiler/lr-table.ss= admits the resulting action
and goto vectors before indexes or executable products are published.

The source audit at parent =5a6a70b= found that preparation indexed rows without
checking target ranges or uniqueness. A valid terminal key could conceal an
out-of-range shift/reduce reference, a singleton fork or duplicate row entries.
The old association/index helpers selected the first duplicate; that utility
behavior did not establish canonical table legality.

The shared gate establishes:

- Nonempty action vectors and equally sized goto vectors, with proper rows.
- Canonical terminal keys, symbolic goto keys and no repeated key within a row.
- Shift and goto targets within the state domain; reduce targets within the
  admitted production domain. Numeric references are nonnegative Fixnums.
- Three-element shifts with the existing precedence contract, two-element
  reductions, EOF-only acceptance and matching nonassociative terminal metadata.
- Flat forks with at least two atomic alternatives. Layout guards contain a
  shift and a reduction or flat reduction fork. Request-generated layout-shift
  actions are not a published table declaration.
- Layout guards and layout terminal keys require layout capability derived from
  admitted productions. Preparation uses the same predicate to enable source
  columns and request-local frames; table shape alone cannot enable that protocol.
- Action keys belong to the canonical production terminal catalog (including
  EOF); goto keys name a declared production LHS. Marked operands retain their
  base-symbol membership and unused declared rules remain admissible.
- The graph from state zero has a reachable EOF acceptance. Shift edges in
  forks/guards and goto edges all participate. Conflict resolution may leave
  disconnected states; admission preserves their existing identities.

Standalone LR compilation, prepared execution, fused Scheme strategy admission
and raw-IR Rust publication consume this gate. The source build catalog discovers
the new production module through the existing PackageSpec. The action validator
captures state and production domains once per admission; queries retain their
existing indexes and captured executors. Row and entry objects are returned
unchanged. As with prepared productions, callers must not mutate admitted IR.

(let ((productions '((0 root ((terminal token word)) concat #f)))

      (gotos '#(((root . 0)))))

  (validate-lr-tables productions '#((((terminal token word) fork (reduce 0)))) '#(())))

(validate-lr-tables '((0 root ((terminal token word)) concat #f))

** Question: why is this design preferable?

The Scheme DSL states grammar meaning; users do not configure table validation,
index storage or backend dispatch. Structural matching expresses the closed
action algebra, while a shared row traversal owns domain and uniqueness checks.
POO strategies inherit the same canonical admission rather than supplying their
own definition of a legal table. These mechanisms implement the staging boundary
of the [[file:engine-reduction-generation.org][integrated reduction study]]; they add no author slots or compatibility path.

Layout capability is declared by canonical production meaning: a layout-end
action or a layout-start/layout-next operand, including marked operands. One
structural matching function now serves table admission and runtime preparation.
This uses Scheme's symbolic action algebra to move a protocol obligation into
the engine, rather than asking grammar authors to duplicate an enable flag.

The table gate preserves original entries, including the identity required by
GLR receipts and checkpoint execution. Generic association helpers still support
first-match duplicate lookup as utilities; a canonical parser table cannot use
that behavior to bypass admission. Each responsibility has its own control.

** Question: how is the claim scientifically tested?

For s states and p productions, every admitted shift/goto target is in [0,s)
and every admitted reduction is in [0,p). Matching each atomic branch extends
that invariant to flat forks and guarded reduction alternatives. Uniqueness
is checked with a preparation-owned equality table, independently for each row.
These are structural invariants, not a proof of LR conflict resolution or that
the table recognizes its declared grammar.

Falsifiers include an admitted out-of-range reference or malformed wrapper,
changed original-entry identity, modified valid artifacts, or a Rust output file
published after admission failure. Focused index controls test boundaries and
malformed rows; existing utility controls retain first-match behavior. Full
generated/GLR artifacts, layout closure and ten-language ABI fixture bytes provide
independent valid-product controls. Raw Rust publication has separate failure
controls for target bounds and duplicate keys.

Layout falsifiers additionally include a guard or layout key admitted with plain
productions, or loss of capability through an operand's field/alias wrapper.
Positive controls cover end actions, bare start markers and marked next markers;
the source layout suite exercises actual request columns and frame transitions.

Validation adds a row traversal and per-row equality hash tables; lookup cost
and hashing literal keys contribute to preparation work. No worst-case total
cost bound or measured preparation/request benefit is claimed. Reachable
acceptance is checked below; it does not certify goto completeness, conflict equivalence, lexical
realizability. Layout correspondence here is a necessary capability condition,
not proof that markers are balanced or that every guard has the correct fallback.
Backend-specific capability admission retains its existing owners.

* Production-relative vocabulary and reachable acceptance

This follows the same admission boundary through all four consumers, rather
than adding a language-specific validator. The =0c46a44= baseline gate admits
an undeclared token key, an undeclared goto symbol and an isolated cycle with no
acceptance reachable from state zero. Their numeric offsets and row shapes are
valid; structural shape alone cannot establish the production/table relationship.

The implementation reuses =production-terminal-catalog= from the LR owner.
Its index includes EOF at offset zero; Scheme's truth semantics correctly treat
that zero as present. A separate equality set admits production LHS symbols.
No second terminal-normalization policy is introduced. Operand actions are
projected by the existing canonical catalog, so field and alias annotations do
not change terminal membership. Dead declared rules remain legal composition
inputs; absent table symbols do not become implicit declarations.

#+begin_src scheme
(def productions '((0 root ((terminal token word)) concat #f)))
(def actions '#((((terminal token word) shift 1 #f))
                (((terminal eof) reduce 0))
                (((terminal eof) accept))))
(def gotos '#(((root . 2)) () ()))
(validate-lr-tables productions actions gotos) ; same vectors and entries

;; An accepting row does not legalize an undeclared grammar symbol.
(validate-lr-tables productions
                   '#((((terminal token unknown) reduce 0)
                       ((terminal eof) accept))) '#(())) ; rejected
;; An isolated accepting cycle cannot be entered from the initial state.
(validate-lr-tables productions
                   '#(() (((terminal token word) shift 1 #f)
                          ((terminal eof) accept))) '#(() ())) ; rejected
#+end_src

** Question: why does this exploit Scheme and keep complexity in the engine?

The symbolic IR supplies the vocabulary directly. Structural matching traverses
the closed shift/fork/layout algebra without another opcode registry or author
configuration. POO-selected strategies consume one canonical gate before
execution or publication. The graph worklist uses the installed Gerbil SDK's
=:std/struct/queue= implementation: typed final queue storage, enqueue/dequeue
operations and a state-sized visited vector. Each discovered state is enqueued
at most once. Graph traversal is bounded by states plus action/goto alternatives;
symbol hashing and terminal-catalog construction remain separate admission costs.
These mechanisms execute during preparation/publication, not token lookup.

** Question: what does the research prove, and what falsifies this contract?

Knuth's [[https://doi.org/10.1016/S0019-9958(65)90426-2][On the Translation of Languages from Left to Right]] (1965), definitions
and Section II, separates grammar symbols, derivations and recognizer
construction. The [[https://harrymoreno.com/assets/greatPapersInCompSci/2.5_-_On_the_translation_of_languages_from_left_to_right-Donald_E._Knuth.pdf][primary paper scan]] is the research source. Our vocabulary check
and reachable-acceptance check are necessary artifact conditions derived from
that separation; they do not decide the LR(k) property or prove table/grammar
equivalence. A reachable goto is an abstract graph edge, not proof of a viable
runtime reduction stack. No accepted input string is inferred from this graph.

An initially stronger proposal rejected every disconnected state. Actual GQL
qualification falsifies it at state 1001: static conflict resolution removes
shift edges while retaining the original state identities. That implementation
is withdrawn. The final contract checks reachable acceptance and preserves
disconnected state rows; it neither trims nor renumbers the automaton.

Independent falsifiers include an undeclared key admitted despite an otherwise
reachable accept, an isolated accepting cycle admitted from state zero, missing
second-fork or layout-primary edges, and lost marked-operand membership. Positive
controls retain unused declarations, cycles, goto-only paths and disconnected
rows beside a reachable acceptance. Runtime rejection and Rust publication use
the same malformed inputs; publication must neither create a missing file nor
overwrite an existing sentinel. Existing compiler, layout, fused execution and
ten-language ABI controls qualify the complete consumer boundary.

* Rust target representability after canonical admission

The next audit follows the same staged contract to the actual Rust model.
=engine/model.rs= represents syntax aliases as =u16=, state/production references
as =u32= and each production's dynamic precedence as =i32=. Canonical Scheme
precedence accepts Integer. The emitter previously printed that integer directly,
so canonical legality could produce Rust source with an out-of-range literal.

=validate-rust-lr-capability= now runs after shared production/table admission
and before the output-string buffer. It checks kind/reference domain capacities,
rejects production-derived layout capability unavailable in the Rust model,
and checks dynamic precedence against the inclusive signed 32-bit bounds.
Layout uses the shared production predicate, including marked operands and unused
rules; it is not a second DSL interpretation or an author-configured feature flag.

#+begin_src scheme
;; Canonical Scheme legality does not inherit a consumer's fixed-width limit.
(validate-production-semantics
 '((0 root () concat (dynamic 1267650600228229401496703205376))))

;; The target owner applies this additional obligation before source emission.
(let (precedence (production-precedence production))
  (when (and precedence (eq? (car precedence) 'dynamic)
             (not (<= -2147483648 (cadr precedence) 2147483647)))
    (error "Rust LR dynamic precedence exceeds i32 capacity" production)))
#+end_src

** Question: why does this preserve the Scheme design advantage?

Symbolic productions carry meaning independently of a target's machine widths.
The engine admits this meaning once; each publication target owns its additional
representation obligations. Scheme matching and first-class traversal keep that
boundary explicit without expanding grammar.ss/parser.ss author configuration.
Both raw IR publication and descriptor publication use the same Rust entry, so
both paths enforce the target capacity gate. Descriptor policy admission keeps
its separate owner.

** Question: what evidence establishes the target claim?

The falsifier is Rust source emitted with an out-of-range production precedence.
Controls cover both exact endpoints, zero, each adjacent overflow and a bignum.
The same rejected target IR must still prepare under Scheme. An existing output
file must retain its contents after target rejection; an oversized kind catalog
must create no file. Layout controls include end actions, start operands and
marked next operands. Existing ten-language ABI bytes and deterministic source
controls establish that currently supported products retain their output.

The u32 domain bound is inspected directly against the Rust model; no test
allocates billions of states or productions. Admission of an individual i32
precedence alone did not close accumulated branch scores. The runtime obligation
identified here is addressed by the following checked accumulation contract.
This is target publication correctness, not a runtime performance claim or
proof of complete Rust/Scheme semantic equivalence.

** Checked cumulative precedence and global failure

The Rust configuration, completed candidate and public receipt now carry i64
scores. Individual generated productions retain their admitted i32 representation.
Reduction computes checked i64 addition before draining values or truncating
states. Capacity failure returns =dynamic-precedence-overflow= at the current
source boundary and leaves the configuration unchanged. The same reduction owner
serves deterministic, contextual and selective GLR execution.

Selective GLR treats this diagnostic as a global failure, like its existing
artifact and branch-budget failures. Discarding an overflowing branch as a normal
parse rejection could admit an incorrect lower-scoring winner. Both branch orders
must fail even when another branch has already completed.

#+begin_src scheme

(+ -2147483648 -2147483648) ; => -4294967296
(+ 2147483647 -2147483648) ; => -1
;; Rust accumulation preserves these values; target capacity failure is explicit,
;; never a wrap, clamp, panic or silently discarded GLR alternative.
#+end_src

*** Question: why is this an engine responsibility?

Grammar declarations state precedence meaning. Configuration arithmetic and
candidate comparison implement that meaning; grammar authors should not configure
integer widths, exception handling or branch-discard policy. One shared reduction
operation checks the target's capacity before mutation, and one GLR owner classifies
the resulting failure. The receipt reports the same wider score that selected the
winner, with no legacy narrow-score alias.

*** Question: what closes the numerical claim?

Full parser controls cross both i32 limits, preserve branch ordering and retain
equal-score ambiguity after positive/negative cancellation. Seeded i64 boundary
controls verify failure before state/value/cursor/score mutation. Internal GLR
controls put a completed branch before and after an overflowing branch, for both
positive and negative overflow. Existing complete parse/event/contextual controls
qualify the shared owner. This closes checked accumulation and propagation within
the explicit Rust target domain; it does not claim arbitrary-precision Rust scores
or successful execution of every canonical Scheme Integer grammar.
