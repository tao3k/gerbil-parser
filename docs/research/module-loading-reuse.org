#+title: SDK module loading reuse and source admission

* Ownership

Gerbil's =runtime/loader.ss= owns module dependency initialization, its loaded
module table, concurrent waiters and cached initialization failures.
=expander/module.ss= owns expansion contexts and delayed module evaluation.
=import-module= takes a =reload?= flag followed by an =eval?= flag; unconditional
=#t #t= reconstructs the imported context rather than reusing it.

The parser delegates these responsibilities to the SDK. This work changes build
and test preparation. It does not change scanning, LR parsing, GPA1 publication
or the steady-state Tokio/FFI parse algorithm.

* Source admission

[[file:../../src/language/module-input.ss][language-module-descriptor]] records only SHA-256 source identities, not
module contexts or evaluation results. For file inputs, it reads the complete
source and normalizes the path. First admission, changed content, or an explicit
=reload?: #t= request uses official expander reload. Unchanged content reuses the
SDK context. Export selection and descriptor admission still execute on every
request. The identity is recorded only after successful evaluation and selection.

This does not depend on file size or timestamp. Missing files, invalid syntax,
failed initializers and missing descriptor exports remain errors. Failed source
admission does not establish a successful identity. A subsequent corrected file
can be admitted normally.

Library inputs beginning with =:= reuse the SDK's library snapshot. A caller
editing such an input explicitly requests reload. Reloading a module does not
recursively invalidate imported dependencies: changing imported helpers requires
an appropriately refreshed build host or explicit SDK admission of those changed
modules. Inputs must remain stable during each generation request.

[[file:../../src/ffi/rust-runtime-aot.ss][rust-runtime-source]] reuses its installed grammar-support module. File
content admission applies to the supplied grammar path, including calls through
the build C ABI. No per-parse content hashing is added to runtime language handles.

* Test preparation

[[file:../../t/fixtures/tla-sany-differential/preload.ss][The test preloader]] delegates initialization to official =load-module=.
The official =list-modules= state decides whether dependency inspection is
needed. Known entries, including cached failures, go straight to the SDK;
warm admission does not read compiled wrappers or traverse their graph.
There is no second persistent table claiming runtime modules loaded successfully.

Cold entries retain wrapper inspection solely to report actual dependency
admission under the existing silence gate. A request-local traversal guard bounds
cycles and disappears on return or exception; it is not a module success cache.
Interface admission uses =import-module= without forced reload, retaining the
real nested expander trace. Logging reports actual starts and completions, with
no synthetic heartbeat. Total and idle-timeout gates remain unchanged.

The source import scanner remains because FFI tests need compiled dependencies
before source evaluation. Its in-progress marker prevents cyclic source walks;
exceptions clear that marker, so malformed source can be fixed and retried.
Official runtime initializer failures remain cached until =reload-module!=;
the preloader propagates those failures on every attempt.

* Controls and reproduction

#+begin_src sh
just test-module-loading
just benchmark-module-loading generation
just benchmark-module-loading preload
#+end_src

[[file:../../t/benchmarks/module-loading/controls.ss][Scheme controls]] exercise unchanged descriptor identity, content edits,
real DSL edits with changed generated Rust, explicit/automatic generation parity,
missing files/exports, failing initializers, repeated failure propagation,
official runtime reload recovery and malformed-source retry. CI executes them
in both Scheme platform semantic lanes.

[[file:../../t/benchmarks/module-loading/benchmark.ss][The Scheme CPU benchmark]] uses process user plus system CPU from
=##process-statistics=. Complete generation compares production admission against
forced support/grammar reload, retaining identical Rust output checks. The
preload experiment compares official runtime admission against the
[[file:../../t/benchmarks/module-loading/reference-preload.ss][frozen former preloader]], with fresh local preparation state and an already
loaded SDK closure. It measures repeated diagnostic preparation, not a cold
startup or a complete parse request.

Both variants receive the same output handling. Logging completed batches is
outside measured CPU intervals. Warmup, before-reference/reference, candidate
production/reference and after-reference/reference are explicit. Every leg and
group contributes; no outliers are discarded. Control P10 must be at least 0.90,
control P90 at most 1.10, and candidate P90 below 0.95. Execution remains bounded
by 90 seconds and 5 seconds without real progress.

Increasing generation to 16 calls per leg still failed: before
=0.775688/1.138560= and after =0.924308/1.138511=, despite candidate
P90 =0.039524=. The initial unreported warmup also triggered the unchanged
5-second idle gate; completed-batch reporting subsequently made the actual work
visible. These negative observations are retained rather than treated as passes.

The eight-leg generation group also failed: before P10/P90
=0.922577/1.116147=, candidate P90 =0.058664=, after
=0.936217/1.115300=. The final sampler distributes the same number of generation
calls across more alternating legs to balance natural collection ownership.

The 32-leg, ten-group generation run remained rejected: before P10/P90
=0.871094/0.992500=, candidate P90 =0.058020= and after
=0.813078/1.280293=. Final groups aggregate twice as much measured
work while retaining the same total calls and order balancing. With five
groups, nearest-rank P10/P90 are the minimum and maximum: every control group
must satisfy the unchanged stability interval, and every candidate group must
satisfy the CPU threshold. No observation is removed.

The final Scheme run on macOS arm64, using the installed Gerbil SDK and GCC,
completed 3,840 timed generation calls in 80.920 seconds. Each output matched the
complete expected Rust module. Five groups per phase contain 64 alternating
legs, four calls per leg; all groups passed the unchanged controls and CPU gate.

The worst production group used 95.30% less CPU than the matched forced-reload
control. This is complete repeated Rust source generation from an unchanged
records grammar, including source hashing, descriptor selection, emission and
output comparison. It does not establish cold-start acceleration, changes in
Rust execution, or steady-state parsing gains. The driver exited zero with
=MODULE-LOADING-CPU-PROOF-OK= and no missing receipt.

The pure direct-load preloader triggered the 5-second idle gate during cold
initialization. That design was rejected. Cold dependency diagnostics were
retained while warm traversal was removed using official module state.
A subsequent 16-call preload batch measured approximately 0.19 CPU seconds;
its total planned calls exceeded the 90-second budget, so the owned child was
stopped early. The final preload experiment uses four calls per leg; neither
termination is an admitted CPU result.

* Final correctness and cold-host qualification

Final content/failure controls exited zero in 5.166 seconds. The real compiled
ABI probe used the final cold diagnostic path, parsed 1,000 requests, verified
three complete generated Rust results and exercised invalid handle/input/build
requests. It exited zero in 7.349 seconds with =NATIVE-ABI-OK= and
=MODULE-COLD-HOST-OK=. The probe uses the existing disposable native-child exit
contract after all assertions; it does not qualify library teardown.

The ordinary source FFI Suite printed all six successful cases and final =OK=
but stalled during exit. The frozen original preloader reproduced the same
post-Suite stall. Both runs failed the unchanged idle gate and are not admitted
process-success receipts. The repository's existing native-child exit contract
is used separately to qualify the returned Suite result without claiming a
teardown repair.

The two CPU workloads are independent Ubuntu jobs in the existing manually
triggered matrix. They reuse exact-head prepared Scheme products and the
existing processor-affinity policy. Ordinary PR CI runs source/failure controls
on both Scheme platforms; existing FFI jobs own the real host assertions.
