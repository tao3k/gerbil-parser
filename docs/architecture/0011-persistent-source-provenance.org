#+title: RFC 0011 — Persistent source provenance through certified recognition
#+startup: overview

* Decision and scope

This extends RFC 0010's existing deterministic capture pipeline. The connected
path is source token/mode storage -> recognition certificates -> original
production replay -> canonical ParseArtifact publication. This implementation
changes storage and provenance while preserving grammar productions.

The implementation uses an eager, chunked AVL rope. It remains explicitly experimental: matched whole-edit measurements reject
default admission for the current complete-artifact API. Normal sessions
still pass capture? =#f= and allocate neither this index nor a grammar forest.
The parameter =current-lr-source-index-enabled?= independently controls captured
sessions. The vector control uses the same compiled scanner, LR runtime,
grammar cursor, certificates and artifact publisher.

The papers suggest distinct seams, not interchangeable implementations. Source
sequence balancing is lawful because token order and additive measures are
preserved. Rebalancing a recognition repeat changes a production fold unless
its sequence origin and original reduction order are retained. Arithmetic's
nested reductions therefore remain unchanged. A balanced token tree does not
close the repeat semantic contract in RFC 0010.

* Storage and provenance contract

=source-index.ss= stores paired token/mode vectors in leaves of at most 64
slots. Internal nodes cache token count, byte span, character span and height.
A relative position view wraps shared storage; nested adjacent translations
collapse and zero translation returns the underlying piece. This uses UTF8 byte
positions for edits and character counts for scanner movement separately.

Leaves and published nodes never mutate during parser operation. Fresh builder
buffers and request cursors mutate only before publication. This follows the
existing token-vector ownership convention; it is not defensive deep immutability
against callers mutating private token objects.

The parser's private source-stream observer records fresh scanner tokens,
successful nonterminal transfers and ordinary lexical convergence. Accepted old
source ranges coalesce before tree slicing. Rejected candidate cursors are
copies and cannot consume the owner. Prefix storage is sliced from the previous
index. The next index is assembled from provenance while parsing; there is no
post-parse whole-token traversal to reconstruct it.

Certificate scanning can hand a boundary token directly to the source driver.
The observer reconciles that token with the old source only outside the changed
byte interval, after exact kind, lexeme and shifted byte-span checks. This is
storage provenance for an already scanned token, not recognition admission.
Its actual captured mode must be retained even when the old token's mode differs.
Sorted sparse mode patches copy one bounded mode vector per touched leaf while
retaining token backing vectors. Adjacent source spans still coalesce.

Certified event-window edits splice this index too, even when their grammar
forest is dropped. Resumed deterministic parses can capture a new forest later.
Failure, layout parsing and GLR without a complete deterministic source origin
do not publish a partial index. Source-index modes are checked against the
actual captured stream. Independently fresh parsing verifies token contents and
coordinates; historical/normalized modes need not equal those of a fresh path.

* Why the first representation failed

Sharing grammar fragments alone left scanned boundary newlines classified as
fresh input. On 400 sibling declarations, this made 401 small fresh token chunks
for a first insertion; 800 declarations made 801. Each boundary split the old
origin, causing tree joins and bounded leaf work repeatedly.

Matching mode IDs as a condition for token sharing did not remove that pattern:
the scanner boundary path can record a different mode for the identical token.
The correction separates token provenance from mode updates, without dropping
the mode check during future lexical reuse. The source-index tests include an
actual mode 0 override across the 63/64 leaf boundary and prove the old version
is unchanged and token backing vectors are physically shared.

A second locality issue was a root-based byte seek at every nearby declaration
boundary. The cursor now advances within its current chunk, using the tree
search only when the target lies beyond that chunk. Both experiments are
reported as intermediate failures, not qualified speedups.

* Cost model and evidence boundary

Let N be source tokens, C reachable chunks, F fresh tokens, R disjoint reused
origin ranges, P changed mode positions, and L touched mode chunks.

- Indexed count and height use cached measures; byte seek outside the current
  chunk descends a balanced tree and scans at most one bounded leaf.
- Slice and join copy boundary paths and bounded leaf descriptors. An unchanged
  accepted source interval retains token backing storage.
- The builder assembles coalesced ranges rather than flattening all N old tokens
  into two vectors for each edit. Fresh token chunks contain only F new entries.
- Sparse mode relabeling traverses affected paths and copies at most 64 slots
  per touched mode chunk. P or L can still scale with the unchanged suffix.
- Certificates and flat publication still enumerate accepted tokens. Relative
  token materialization allocates absolute tokens for published artifacts.
  Counters describe builder storage operations, not total heap allocation.
- Source patching, checkpoint prefix lists, absolute event publication, complete
  reused-ID receipts and whole-source SHA256 remain linear. Whole-edit time is
  not logarithmic.
- Sliced backing vectors retain up to a bounded leaf's unused slots. Repeated
  edits can fragment leaves; tree balance alone does not prove a live-heap bound
  independent of edit history. No heap/resident-memory win is claimed.

* Validation and matched experiment

The source-index unit suite checks empty input, UTF8 translation, cursor trials,
sliced storage identity, coalesced sources, sparse modes and 180 deterministic
splices against an independently rebuilt flat reference. The integrated snapshot
suite checks real sequential edits, complete fresh artifacts, independent
production projection, captured mode equality, retained old versions, event
windows and the same-head vector control.

The existing =t/benchmarks/incremental-session/benchmark.ss= now supports explicit
=source-index= and =no-source-index= switches. Topology workloads retain first,
middle and last insert/delete scenarios. History workloads apply six edits to
successive sessions; validation and index audits run outside measured calls.
Each timed call publishes complete artifacts. The history timing is the complete
six-edit chain, not a per-edit distribution.

** Implications for the next algorithm change

The experiment falsifies the assumption that persistent token storage alone
makes this complete-artifact edit path faster. It does not isolate CPU time among
cursor access, mode patches, token relocation and publication. Their separate
phase timings must be measured before claiming a dominant cause.

There are two concrete compiler/runtime seams to study next:

1. Mode provenance: normalized grammar transfers can change boundary modes on
   unchanged text. Exact numeric mode certificates are conservative and simple,
   but source locality is not mode-update locality. Factoring lexical behavior
   into compiler-proved equivalence classes could avoid some churn. Any such
   quotient must account for literal priority, longest-match behavior, trivia,
   accepted terminals and scanner closure; equal token contents alone are not
   a universal mode certificate. Opaque scanners and contextual repeat vetoes
   remain counterexamples until proved otherwise.
2. Recognition/publication: the current injector builds flat token segments and
   binds absolute token instances even for reused grammar interiors. A future
   local-recognition operation must retain certified token ranges and replay the
   original semantic fold only at the required boundary. Generated scanners also
   consume flat source strings today. Source-rope scanning, fragment range
   binding and an explicit materialization operation therefore form one path;
   hiding a flattening pass in any of them would invalidate local-update claims.

The current API still publishes the complete authoritative ParseArtifact, with
whole-source SHA256. A private retained snapshot or local query is not a second
canonical artifact. Changing this boundary must preserve exact published events,
current token identities, original production folding and invalidation behavior.

* Following the full optimization path

1. Admit persistent source storage only at an explicit measured boundary. Treat
   source/token sharing, mode copying and complete edit CPU as separate facts.
2. Retain sequence origins in grammar repetition and replay the original fold;
   test the context-dependent veto before balancing recognition ancestry.
3. Expose local persistent recognition queries separately from complete flat
   publication. Keep ParseArtifact v1 digest, token identity and event order as
   authority, and measure the remaining whole-source work explicitly.

This sequence keeps source storage, LR context, semantic folding and publication
connected. It cannot be completed by renaming the flat artifact or merely adding
a tree beside a later full rebuild.
