#+title: Parser model and implementation evidence chain

* One optimization chain

The architecture has four connected owners: papers, Quint, Lean and executable
implementation. Measurements are implementation evidence. The command-review
adapter below uses four narrower evidence claims for a scoped change; these
claims do not certify completion of the architecture model.

The optimization unit is an engine change with four distinct obligations:

| Evidence layer | Owner | Qualified claim |
|----------------+-------+-----------------|
| Algorithm semantics and counted operations | Lean + LeanPoo | =lean-model= |
| Finite publication protocol | Quint | =quint-protocol= |
| Implementation/product conformance | Existing Scheme suites | =scheme-conformance= |
| Complete-request matched measurements | Existing Scheme benchmark admission | =matched-performance= |

Python transports observations and content identities into native Scheme
ASCENT. ASCENT derives usable receipts, missing requirements and transitive
invalidity. It neither implements the parser nor proves Lean theorems or
computes new performance statistics. The evidence adapter is verification-only.
The production grammar.ss / parser.ss / parser-test.ss interfaces are unchanged.

This extends [[file:parser-engine-formal-model.org][the reduction and sequence model]]. The existing
[[file:parser-execution-evidence.org][measurement admission]] remains authoritative for actual requests.
Passing a model does not establish implementation conformance or improvement.
The [[file:parser-engine-formal-model/objective-and-evidence-boundary.org::*Architecture alignment audit and qualification order][architecture alignment ledger]] is authoritative for missing model coverage.
The four command-claim receipts below are evidence layers for a scoped change,
not a completeness test for the paper program or the full engine. In particular,
=lean-model= plus =quint-protocol= may pass while grammar/table, scanner, branch,
projection, transfer and ABI correspondence remain unmodeled. Source hashes do
not discharge any of those semantic obligations.
The [[file:lr-owned-stack.org][request-owned LR stack study]] applies the chain to execution storage and
immutable-frontier publication.

* Protocol model and its limits

=Publication.qnt= models a prepared request's source generation, cancellation
and publication. A result can become public only while its basis matches the
current generation and it has not been cancelled. Editing withdraws an old
published result. Rejected results remain private.

Seven deterministic tests cover successful publication, stale requests,
cancellation, edit withdrawal, and mutation witnesses that omit admission.
The closure test evaluates every state in the explicit 360-state domain:
source/basis generations 0--2, five phases, two cancellation values and four
output-generation values. It checks one-step preservation from every valid
state for each admitted transition. This is finite evaluation, not Apalache
verification, an unbounded temporal proof, a liveness theorem, or conformance
of the current actor/session implementation. The exact test command and domain
are included in the observation's bound inputs.

* Receipt admission and traceability

=parser_evidence.py= records command arguments, working directory, deadline,
exit code, expected markers, output digest, executable digest and declared
input-file digests. Commands execute without a shell. Nonzero exits, missing
markers, timeouts and input changes do not produce passed facts. Source/input
paths are repository-relative and cannot escape through parent components or
symlinks. Tool versions, dependency locks and relevant source closures must be
included by the caller; a launcher fingerprint alone does not identify all
interpreter or imported dependency contents.

Each immutable observation has a content ID derived from its full record.
Its raw output and record are stored under that ID. Review rechecks current
source/executable/output/metadata contents. Deleted or changed inputs invalidate reuse.
Receipt dependencies identify those same content IDs. Upstream Scheme ASCENT
rejects absent, failed, stale and circular dependencies, including transitive
invalidity. The review packet contains the exact input facts, observations,
native result and reviewer identities for subsequent inspection.

Host observations are trusted local observations, not signed attestations.
The host still owns input-set completeness, checker selection and claim scope.
The optional =required= argument supports scoped reviews; the model collector
uses the complete four-layer requirement set. Even a complete set produces
=REVIEW_REQUIRED= rather than execution authorization. No result packet is a
substitute for inspecting its assumptions and the actual benchmark admission.

Python's deadline covers its direct checker child. It is not a replacement for
the existing Scheme descendant-process supervisor. Scheme qualification calls
must retain their own established process-control owner.

* Executable Scheme witness and design questions

This is the upstream review's relational pattern, not a new parser DSL:

#+begin_src scheme
;; CurrentInput and ReceiptInput are supplied observations.
;; Recursive ReceiptPath keeps transitive dependency identity explicit.
((ReceiptPath R D) <-- (ReceiptDepends R D))
((ReceiptPath R D) <-- (ReceiptPath R X) (ReceiptDepends X D))
((Unusable R (lit 'circular-justification)) <-- (ReceiptPath R R))
((Unusable R (lit 'stale-or-missing-input))
 <-- (ReceiptInput R K V) (not (CurrentInput K V)))
#+end_src

** Question: why does this exploit Scheme's strengths?

The parser retains its higher-order prepared functions and engine-owned
representations. A second Scheme engine supplies declarative relational review
and retained derivation components through its C ABI. Python supplies bytes and
observations; it does not duplicate Scheme inference with imperative rule loops.
This preserves producer ownership and keeps language authors free of verification
or storage machinery. Component reuse may reduce repeated review work, but no
review-time speedup is claimed without measurement.

** Question: how is this scientifically checked?

Lean proves properties of its algorithms; Quint evaluates a named finite
transition domain; Scheme tests compare semantic products; benchmarks preserve
matched measurement controls. Each observation binds the relevant source,
tool/lock context and raw output. Mutation and negative controls test whether
invalid evidence is rejected. The combination exposes missing proof and
measurement obligations instead of converting one successful layer into a
whole-engine claim.

* Reproduction and CI boundary

From the repository root:

#+begin_src sh
just formal
npm ci --ignore-scripts --prefix formal/quint
just formal-protocol
uv sync --project formal/evidence --locked
#+end_src

Select an upstream-built native ABI artifact and its adjacent JSON receipt
through =ASCENT_ENGINE_LIBRARY=. With the prepared environment:

#+begin_src sh
uv run --project formal/evidence --locked python -m unittest discover -s formal/evidence -v
uv run --project formal/evidence --locked python formal/evidence/collect_models.py
#+end_src

The collector executes real Lean and Quint commands and sends their saved
observations to native ASCENT. Its expected result establishes the two model
claims and explicitly reports =scheme-conformance= and =matched-performance=
as missing. Success qualifies that model-layer experiment only.

Eleven host/native controls cover nonzero exits despite success markers,
missing markers, source mutation during execution, retained timeout, changed
source/log/metadata rejection, dependency cycles, failed transitive dependencies,
partial bundles, measurement without CPU admission, and absent execution authority.

CI adds locked Quint tests and Python host controls to the existing contracts
lane. The native ASCENT integration is locally exercised against an upstream
artifact; CI does not rebuild an unrelated Scheme dependency or pretend that
host tests qualify native inference. A future native CI gate needs an immutable
upstream artifact provisioned by that project's build owner.

* Complete engine observation entry

=just evidence-engine= executes the four evidence layers in one review. It
uses the same locked uv project as =evidence-controls= and =evidence-models=.
The model-only entry remains useful for diagnosing missing runtime evidence;
it does not substitute for this entry.

The sequence is:

1. Execute Lean and Quint against their declared source and dependency inputs.
2. Build production Scheme, the standard test driver, FFI test owners and the
   composed benchmark owner. These are =scheme-build= prerequisite receipts,
   not semantic evidence. Native =std/make= and =gxc= own compilation.
3. Execute seven Scheme suites covering prepared reductions, fused actions,
   persistent sequences, publication costs, the GQL stage controls and native
   language admission. Require process success, the exact suite count and
   the test driver's final =OK=.
4. Execute the existing GQL stage sampler and the matched GQL, FHIRPath and
   arithmetic request backend sampler. Both retain their existing semantic
   artifact checks and sampling/admission rules.
5. Submit source-bound observations and receipt dependency edges to native
   Ascent =EvidenceReview=. Conformance depends on every build receipt;
   measurement depends on those receipts and conformance. Failed preparation
   stops dependent execution and leaves both runtime requirements missing.

The production declarations, Scheme source closure, tests and workloads are
hashed before and after each command. Runtime observations additionally bind
prepared library products. Logs and metadata have content identities and
are checked again by the review host. This supplies finite provenance for
explicitly chosen inputs; it is not a proof that the supplied closure includes
all external compiler, operating-system or hardware influences.

Build supervision uses the existing 240-second / 30-second inactivity
budgets. Runtime tests and measurements use the existing 120-second /
5-second inactivity budgets. The Python direct-child deadline exceeds the
Scheme supervisor's budget; Python adds no descendant-process supervisor.
The previous five-second exploratory build failures remain failures.

=matched-performance= means that the matched measurement executed and its
output is available for review. It does not mean that an optimization won.
The Scheme sampler's =LR-BACKEND-PERFORMANCE-ADMISSION= output remains the
owner of control stability and complete-request benefit admission. Ascent
establishes receipt dependency validity, not CPU improvement or a
Scheme-to-Lean refinement theorem. No new CI job or compiler is introduced.

* Scheme dependency boundary

The parser package no longer imports =gerbil-scheme-rust= from Scheme. Native
language admission uses SDK UTF-8 decoding, a Unicode scalar predicate and
canonical SDK re-encoding. This rejects surrogate encodings as well as
noncanonical byte encodings without foreign admission allocation. Existing
ASCII admission, Unicode boundary and malformed-input controls remain in
=language-abi-test.ss=. No Unicode throughput benefit is claimed from the
dependency removal. Rust code generation still has its separate Cargo IR
consumer; deleting a Scheme package dependency does not remove that Rust
contract.

* Input-set transport and local admission results

Each observation retains its complete sorted =(relative-path, SHA256)= input
manifest. For native review, the host transports one SHA256 commitment of the
canonical manifest as =ReceiptInput= and recomputes the same commitment as
=CurrentInput=. Missing files omit the current commitment; changed file
contents change it. Ascent owns the equality and dependency inference. This
reduces repeated relational input rows without weakening per-file mutation
checks or introducing Python inference.

The local upstream artifact still rejects requests beyond its ABI transport
limit. The earlier expanded-input request returned status =-4=; it is retained
as a failure, not hidden by increasing an engine limit. Compact commitments
allow the existing source-bound review to execute under that same artifact.
The ten native/host controls include a complete runtime bundle and rejection
of both semantic and measurement receipts through a failed build prerequisite.

The CI at =77d13f7= completed successfully. Its configured CPU/diagnostic skips
are not benchmark qualification. New local engine observations apply to their
recorded source and prepared-product manifests, including any local study
changes; they do not retroactively qualify that CI revision.

* Executed complete-chain qualification

The complete local entry passed both model checks, all four Scheme build
prerequisites, six semantic suite owners and the composed request workload.
Native Ascent returned =Missing = []= and =executionAuthorized = false=.
The six semantic owners executed 15, 10, 8, 10, 11 and 17 Cases respectively.
Their source manifests include local study edits; these counts qualify that
recorded local manifest rather than an unchanged Git head.

Preparation uncovered two separate admission failures: stale helper
interfaces, and a generated Scheme phase body without its compiled test-helper
object. The standard benchmark build owner now owns the required arithmetic
and HCL test helpers as well as the sampling workload closure. Compilation
uses =std/build-script= / =std/make=; Python no longer lists compiler targets.
The completed source harness uses the existing disposable-child exit owner
only after its =main= returns successfully. Earlier =OK= output followed by
an inactivity failure remains a failed observation.

The matched workload also exposed an asymmetric diagnostic catalog: the
recognition semantic replay has no event-program counterpart for eligible
FHIRPath and arithmetic machines. Such diagnostic pairs are explicitly
reported as =LR-BACKEND-PAIR-UNSUPPORTED=. A missing =full-source= pair still
raises an error. Sampling counts, ABBA/BAAB order, negative-control admission
and the five-percent decision margin are unchanged.

The latest complete workload reported =control-stable = false= and
=complete-request-benefit-admitted = false=. Those negative decisions remain
in its receipt. Completion of all evidence layers is not an optimization win.
The representative GQL stage experiment identifies prepared LR as the next
cost investigation: one completed local run reported CPU P50 of 6.712 ms per
100 prepared parses, versus 9.058 ms per 100 complete requests. Lexing and
publication controls reported 0.763 and 0.836 ms per 100 calls. These are
independent prepared controls, not an additive source-execution decomposition
or a portable performance target. No parser backend default changes.

* Independently admitted engine CPU change

The optional =--record-study= entry additionally requires
=record-cpu-improvement=. A =matched-performance= receipt cannot establish it.
The new claim is produced only by the Scheme =record-evidence.ss= checker,
whose strict repeated CPU, tail and unchanged-SDK control checks consume four
independently loaded complete-request receipts. Native Ascent rejects the
missing or failed admission even when the ordinary measurement layer passed.
A native negative control checks this distinction explicitly.

CPU admission depends on all build receipts, semantic conformance and the
ordinary request measurement. Its input closure additionally includes the
reference products, reference source/product manifest and all four raw logs.
The host's detailed manifests and the upstream ABI identity remain separate
from a proof of the compiler or the completeness of the supplied inputs.
See [[file:engine-record-access.org][the engine implementation study]] for the workload scope and conservative
results. CI retains the existing contracts and native semantic lanes.
