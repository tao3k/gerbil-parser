#+title: Dense dotted-position ownership across LR construction

* Research obligation and scope

The [[file:dsl-effective-grammar-admission.org::*LR suffix facts: compositional reverse evaluation][prepared suffix study]] removes repeated RHS suffix scans but explicitly leaves
production-count times maximum-width padding unresolved. This implementation
closes that representation obligation in the compiler, before LR(0), lookahead,
canonical LR(1), partition refinement and conflict-source publication diverge.
It changes no language declaration, request executor, ABI or CI job.

The staging argument in the parent study connects grammar-only facts to
Krishnaswami and Yallop's static Null/First analysis and Sperber and Thiemann's
Scheme LR specialization. Those papers motivate preparation ownership. They do
not prove this particular representation correct or supply its measured speedup.
The argument below is a separate bijection over the admitted production table.

* Representation and invariant

For production i with RHS width w_i, define o_0 = 0 and
o_(i+1) = o_i + w_i + 1. The dotted position (i,d), where 0 <= d <= w_i,
has core ID o_i + d. The domain size M is sum_i(w_i + 1), rather than
P times (1 + max_i w_i). Every production owns one completed position, including
epsilon productions. There are no holes or overlapping production intervals.

The private =lr-item-layout= record owns terminal count, production offsets and
a dense inverse owner catalog. Prepared owner lookup is constant time; dot
lookup subtracts that owner's offset. Storage and preparation are O(P + M).
This does not make arbitrary big-integer bitset operations constant time.
It bounds the core-ID domain on which those operations run.

Order by production then dot is preserved. Advancing a noncompleted core by one
stays inside its production. Completion, FIRST suffix lookup, prediction,
action masks and shift-origin diagnostics consume the same layout functions.
Public production IDs, state discovery order and rule origins are unchanged.
There is one representation; no padded-layout compatibility branch remains.

#+begin_src scheme
;; Independent fixture: widths 1, 3, 0, 1, including augmented start.
;; Every completed item is retained, and the epsilon interval has width one.
;; Expected IDs are explicit rather than reconstructed through the decoder.
'((0 0) (0 1) (1 0) (1 1) (1 2) (1 3) (2 0) (3 0) (3 1))

;; Engine consumers inspect logical coordinates, never numeric packing details.
(core-item-production-id item layout)
(core-item-dot item layout)
(make-core-item production-id dot layout)
#+end_src

** Question: why does this exploit Scheme beyond S-expression notation?

The canonical grammar remains inspectable data. A named preparation algorithm
derives one immutable layout; a private named record makes ownership explicit;
dense vectors implement its finite domain. Consumers share named coordinate
operations rather than copying arithmetic conventions. POO continues to own
extensible grammar composition and hygienic DSL rules own declaration lowering.
This fixed numeric representation needs neither a public extension slot nor
generic dispatch in bitset traversal. Authors express rules, not allocation
strides or packed-item decoding.

** Question: how is the design scientifically justified?

Disjoint intervals establish injectivity, every valid dot lies in an interval,
and their concatenation covers exactly [0,M). Ordering and successor preservation
establish the representation obligations used by existing LR algorithms.
Independent coordinate and suffix controls falsify boundary errors; canonical
reference and origin tests falsify altered construction and diagnostics.
Complete original/candidate LRSpecs test publication equivalence separately
from CPU and allocation observations. A reduced domain is a deterministic
storage result, not evidence of complete-request latency improvement.

* Source-admitted construction and physical storage proof

The paper/model/code obligation now includes complete source declarations.
The existing reader adapter extracts =make-item-layout= and all four native
coordinate procedures into =formal/ParserEngine/SourceData.lean=. The separate
=ItemLayout.lean= kernel checks every expression in the two-pass constructor
and the coordinate declarations. Changing a loop guard, owner vector, increment
or terminal-count publication rejects admission. Reader data contains no proof
program or generated theorem.

The staging boundary follows the grammar-analysis/execution separation in
[[https://www.cl.cam.ac.uk/~nk480/parsing.pdf][Krishnaswami and Yallop, section 6]]. That paper's predictive parsing results
apply to its typed grammar calculus. This dense LR representation has its own
project-specific construction and storage obligations. The author-maintained
[[https://www.s48.org/essence/][Essence]] work supplies the related Scheme LR specialization context.

| Layer | Obligation | Executable owner |
|-------+------------+------------------|
| Paper/research | Grammar-owned preparation; production/dot intervals include completion | This representation study |
| Lean | Arbitrary widths; sentinel; termination; generated write addresses; physical updates; coordinate inverse | =formal/ParserEngine/ItemLayout.lean= |
| Quint | Index/fill/publication scheduling; empty and epsilon cases; mutation witnesses | =formal/quint/ItemLayout.qnt= |
| Scheme | Extracted complete body agrees with actual native coordinates and vector contents | =t/event-walk-source-test.ss= |

The general proofs derive index and offset counters together. The index pass
writes exactly P+1 slots, including the final sentinel for an empty table.
The fill pass derives its own bounded work from each RHS width, and its actual
write addresses cover exactly [0,M). Replaying those writes initializes every
valid owner slot independently of arbitrary previous contents. The proofs do
not replace physical writes with an assumed map of values. A separate offset
store proof covers every prefix and the final sentinel. Their composition
connects physical owner/offset lookup to the production/dot roundtrip.

The Scheme matrix executes the reader-extracted constructor with its two
external operations supplied explicitly: the real production-RHS projection
and a record publication adapter. Its actual vector reads/writes remain intact.
It compares complete offset/owner arrays and public native coordinate APIs for
empty, epsilon, skew and wide tables across three terminal cardinalities.
Existing resolved-grammar and canonical LR reference controls run in the same
qualification group. These finite controls test the implementation relation;
the Lean induction establishes the unbounded arithmetic/storage result.

External premises remain explicit: reader/compiler correctness, successful
fresh vector allocation, record field semantics and the nonnegative exact
integer/vector primitives. Production IDs here denote table positions; their
connection to grammar names/origins belongs to the upstream admitted table
producer. Positive terminal cardinality for packed lookahead operations and
composition through LR state/table publication remain separate obligations.
This closes the dense-layout constructor/storage component, not the entire
parser or host refinement. No runtime optimization or CPU claim is introduced.
