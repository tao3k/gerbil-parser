#+title: Shared parser specialization, source spans and pipeline fusion

* Scope and architecture

The [[file:lr-request-cost-boundaries.org][LR request cost boundary study]] complements this Source-engine study
with public GQL evidence, Scheme-native stage hooks and explicit receipt limits.

This study owns specialization and representation lifetime in the shared engine.
It extends the [[file:scheme-deflanguage-design-synthesis.org][three-interface design]], rather than proposing another
language-author interface. Grammar intent remains in =grammar.ss=; metadata and
entry services remain in =parser.ss=; independent expectations and benchmarks
remain in =parser-test.ss=. Bash is a stress workload, not the implementation
owner of a private scanner or optimization callback.

* Existing measurements and their limits

An independent matched Bash report dated 2026-10-09 records 28,440 UTF-8 bytes
and 1,000 lines. Complete-parse median CPU was 43.320–45.093 ms for Scheme and
3.196–3.203 ms for Tree-sitter, approximately 13.6–14.1 times apart. Its owner is
=tools/benchmarks/bash-matched/results-2026-10-09.org= in a separate experimental
workspace. That uncommitted report is not a product of this implementation
checkout and its measurements have not been repeated by this source study.

Independent diagnostics recorded about 51.930 MB of cumulative allocation for
the complete artifact, 10.915 MB for scanning and 14.464 MB for publication
validation. Complete allocation was roughly 1,826 times the input byte count;
this is allocation traffic, not peak resident memory. Component medians cannot
be added. Allocation across 200/400/1,000-line samples approximately followed
input size; this motivates investigating constant costs but does not establish
linear complexity for arbitrary nesting.

Scheme used GCC16/Gambit -O1; the initial Tree-sitter grammar used clang -O3.
A clang -O1 grammar control still took about 4.016 ms, but its runtime was not
rebuilt. Products and allocators differ. These observations do not isolate a
language implementation effect. Follow-up comparisons keep the Scheme SDK
fixed and preserve complete validation.

* Gerbil source reading: mechanisms and transfer boundaries

The inspected distribution is Gerbil =0.19.2591dcd.patchf5cedd8168cb=.
Paths below are relative to its source tree. This includes distribution patches;
source observations are not assertions that upstream has identical code, nor
proof that a particular parser representation is faster.

| Source owner | Observed mechanism | Parser implication | Required control |
|--------------+--------------------+--------------------+------------------|
| gerbil/compiler/optimize-base.ss | optimizer-info owns separate identity-keyed hash tables and local type contexts | Separate identities, ownership and lifetimes; do not reinterpret structural grammar values as identity keys | Equal-but-distinct grammar values, stable output order, independent compiler invocations |
| gerbil/runtime/hash.ss | Specialized eq/eqv/symbol/string table types coexist with checked interfaces | Select a native collection by its actual key contract; replacing make-table also requires changing its consumer API | Constructor, lookup, missing-value and iteration behavior; complete-call allocation and CPU |
| gerbil/compiler/optimize-call.ss | Known procedure/signature information enables selected call transformations; unknown types retain ordinary calls | Preserve real bindings and make private callable contracts explicit where supported; inspect generated code before attributing a dispatch cost | Checked admission, invalid values, generated calls and end-to-end comparison |
| gerbil/core/contract.ss | Type identifiers are resolved through syntax bindings | Keep DSL syntax objects and binding context through elaboration; do not replace the macro system with datum dispatch | Import renaming, phases, nested declarations and source diagnostics |

The [[https://gerbil.scheme.org/reference/gerbil/runtime/hash-tables.html][official hash-table API]] specifies identity/equivalence choices and its own
operations. It does not promise that changing this parser's Gambit tables to
Gerbil tables will improve complete construction. Public Boolean tables returned
by LR analysis currently have consumers using =table-ref=; a private index can
be studied independently, but changing the public representation is a wider
contract change.

The [[https://gerbil.scheme.org/reference/std/contract][official contract documentation]] distinguishes checked =:= declarations
from =:-= type assertions. Its LRU example checks the external cache and asserts
private nodes whose ownership is already established. The transferable pattern
is checked boundaries plus justified internal facts. Blanket unsafe accessors,
unchecked foreign input and custom substitutes for compiler optimizations are
not implied by this example.

In our scanner, =runtime-scan-rule.executor= currently has an unannotated private
slot. A callable annotation is a testable hypothesis, not an admitted speedup:
first inspect whether the current compiler already knows the returned procedure,
then compare generated calls and complete parse cost. A closure prepared once
still incurs a call per candidate; preparation alone does not imply complete
inlining or lexer/parser fusion.

Existing =compiler-index-set-reachable= and its memoized variant already use
indexed immutable edges, local queues and invocation-owned caches. LR suffix
facts are shared across consumers. This study does not duplicate those kernels
or add a global cache whose validity would depend on another grammar.

* Paper mechanism and its applicability

[[https://arxiv.org/html/2304.05276][Yallop, Xie and Krishnaswami: flap, PLDI 2023]] discusses intermediate token
cost in section 2.2, fusion in section 4 and preparation-time specialization in
section 5.4. The transferable mechanisms are moving grammar-static work out of
requests and removing representations used only between internal stages. The
paper's speed ratios do not predict this engine's gains.

Its deterministic grammar, disjoint regex and single-token lookahead assumptions
are not established for every grammar admitted here. Section 8 treats stronger
LR grammars, state and multiple entries as extensions. Longest match, rank,
conflict diagnosis, contextual modes and delayed markers must retain their
current semantics. Candidate rules cannot simply be discarded.

Lossless token events are public output. Fusion may remove temporary internal
tokens, nodes and lists; it must retain the final artifact and Scheme/C ABI/Rust
semantics. Internal allocation and observable output have different lifetimes.

* Implemented preparation and current cost boundaries

The [[file:../../src/runtime/contextual-scanner.ss][contextual scanner]] retains both a declarative matcher and a prepared
executor. =prepare-matcher= binds static operands after closed-IR admission;
=best-match= supplies the request's source, offset and checkpoint.

- Prefix exclusions and exceptions use prepared literal tries.
- Literal prefix probes compare characters without allocating a substring.
- Unicode, longest match, rank, declaration order and conflicts retain the
  selector's existing behavior.
- Markers, pending FIFO, mode and offset belong to request checkpoints.
- Executors capture plan data, not request state. Language IR cannot supply an
  arbitrary callback. Scheme closures are not serialized into Rust AOT IR.
- Declarative matchers remain available for first-character candidate indexing.

The former per-candidate opcode interpretation has been replaced. The following
remaining locations are visible in source; their individual CPU shares have not
been measured in this study.

| Stage | Current owner | Representation to investigate |
|-------+---------------+-------------------------------|
| Candidate execution | contextual-scanner / best-match | Executor calls and final winning match allocation |
| Whole-source scanning | source-engines / source-scanner-tokens | Accumulated and reversed token lists before recognition |
| Word decomposition | shell-word / prepare-word / recognition-source | Lexeme snapshots, local boundaries and subsequent token slices |
| Projection | result-profile / result-projection-build | Captures, children and tokens across intermediate stages |
| Publication | artifact / recognition-events and validation | Recognition-tree traversal, event construction, reconstruction and encoding validation |

* Scheme witness and the two design questions

This block illustrates the existing private literal specialization. It is not
new public syntax or a proposed author-supplied callback. =prepare-matcher= is a
private engine function; the illustration belongs in that module's context.

#+begin_src scheme
(let* ((declaration '(literal "λ"))
       (execute (prepare-matcher declaration)))
  ;; Preparation owns the declaration and static width.
  ;; Each invocation supplies its own source and character offset.
  (values (execute "λx" 0 #f)      ; => 1
          (execute "xλ" 0 #f)      ; => #f
          (execute "xλ" 1 #f)))    ; => 2
#+end_src

** Question 1: Why is this design better for the author and engine?

The author declares a literal once. The engine can inspect and validate that
structure, derive candidate indexes and prepare execution without requiring the
author to write trie builders, dispatch loops or state factories. Scheme gives
us more than parentheses: hygienic macros preserve bindings and source context,
POO composes declared policies, and lexical closures bind admitted static data.
These mechanisms cooperate beneath the existing three interfaces.

** Question 2: What makes the proposal scientifically justified?

The specialization claim has a concrete invariant: matching results and emitted
artifacts are unchanged while static decoding moves to preparation. Existing
controls independently check Unicode, guards, ambiguity and rejection. The
paper identifies a related staging mechanism under stronger assumptions; it
does not prove our LR engine equivalent or faster. Performance requires matched
complete-call evidence including preparation amortization, output validation,
allocation and natural GC. Those observations can reject the proposal.

* SDK lexer reading and winner-only materialization

The SDK binary resolved =:std/text/parser/ll1=,
=:std/text/parser/ebnf/lexer= and =:std/source= through the expander's
=import-module= / =module-context-path=. Source reading then used the matching
installed tree. The lexer module is =ebnf/lexer=; the initially attempted
=:std/text/parser/lexer= is not an installed module.

#+begin_src scheme
(import :gerbil/expander)
(module-context-path (import-module ':std/text/parser/ebnf/lexer))
#+end_src

In =std/text/parser/ebnf/lexer.ss=, =lex1= retains a fallback for the last
accepted extent and invokes the selected reduction only after selection. Its
mutable input stream and declaration-order tie policy are not substitutes for
our immutable checkpoints, rank and ambiguity contracts. The useful lesson is
the lifetime of a result: materialize the public result after deciding which
candidate owns it.

The shared contextual scanner now carries a borrowed rule and an integer end
through its candidate loop. =prefer-rule?= applies the same length/rank/form/action
comparison and raises the same eager conflict. =scan-match= remains the private
result type, but is constructed once after selection instead of once for every
successful candidate.

For a completed step with m successful candidates, m >= 1, the source-level
constructor count becomes 1 instead of m. A no-match step still returns false;
a conflict still raises immediately. This is a source construction bound, not a
measurement of heap bytes: compiler scalar replacement may already remove some
allocations, and executor calls and final token construction still occur.

#+begin_src scheme
;; Engine-private selection: no new grammar callback or author configuration.
(let select ((rules candidates) (current #f) (end #f))
  (if (null? rules)
    (and current (make-scan-match current end))
    (let* ((rule (car rules))
           (candidate-end ((runtime-scan-rule-executor rule) source start state)))
      (if (and candidate-end (prefer-rule? current end rule candidate-end))
        (select (cdr rules) rule candidate-end)
        (select (cdr rules) current end)))))
#+end_src

This answers the existing design questions with an implementation witness:
authors retain the same declarations, while engine-owned lifetime becomes
simpler. The scientific obligation is exact observable selection and diagnostics,
followed by complete-call measurements; fewer source constructors alone do not
establish a throughput improvement.

Unicode byte endpoints, eager conflicts before a longer later match, and the
identity of the first rule retained by an equivalent tie. Both direct IR and
prepared plans execute these controls. The first conflict fixture was rejected
by the duplicate-declaration contract before execution; distinct overlapping
matchers corrected the fixture. That first run was a failure despite its SDK
process returning zero; final =OK= and absence of Case/Harness failures were
required before admitting the rerun.

The corrected scanner/deferred/source/parser run passed 55 Cases. Source-backed

* Native UTF-8 width queries instead of temporary encoding

The SDK binary resolved =:std/string/utf8= to its installed interface. Its source
owner is =std/string/utf8.ss=. The checked =string-utf8-length= procedure validates
string/range arguments and delegates to Gambit's =##string->utf8-length=; it does
not create an encoded byte vector merely to obtain its length.

The [[https://gerbil.scheme.org/reference/std/text/utf8.html][website's UTF-8 reference]] still describes the API under =:std/text/utf8=.
That module was not found in this installed SDK. The implementation imports the
actual =:std/string/utf8= binding established by source inspection; no alias or
legacy fallback was introduced.

Five length-only conversions now use the SDK procedure: each token's extent in
ParseArtifact validation, rejected-source fallback and complete extent in the
shell executor, and both terminated/final line extents in the Scheme event
strategy. Source bytes used for SHA-256 and actual encoding remain materialized
where consumed. The change neither bypasses validation nor borrows mutable
caller text. It adds no language policy, metadata slot or author option.

#+begin_src scheme
(import :std/string/utf8)
(let (text (list->string (map integer->char '(97 955 20013 128512))))
  ;; Four scalars, ten bytes. Query width without constructing encoded bytes.
  (string-utf8-length text)) ; => 10
#+end_src

The existing design questions apply directly. This is better because the engine
expresses the operation it needs, byte extent, through the checked native library
instead of maintaining a custom Unicode loop or an unnecessary encoded product.
It is scientifically testable because byte coverage is observable independently
of the chosen implementation: a token's advertised width must match fixed
Unicode boundary expectations, source reconstruction and the unchanged digest.

New artifact controls cover U+0000/U+007F, U+0080/U+07FF, U+0800/U+D7FF,
U+E000/U+FFFF, U+10000/U+10FFFF with independently specified widths 1/2/3/4.
Every fixture first admits and roundtrips, then changes both token end and
advertised extent to a false but self-consistent width and must reject. A line
control combines all boundaries with CRLF, CR and a final unterminated line;
expected byte ends are 28, 30 and 31. Surrogate integers were refused by this
SDK's =integer->char= during the initial probe and are not valid fixture scalars.

ASCII contained 1,024 characters; mixed input repeated the four scalars in the

* Deferred marker comparison: filter before materialization

The installed SDK binary resolves =:std/string/misc= through
=module-context-path= and =import-module= to its installed =misc.ssi=. The matching
=src/std/string/misc.ss= implements =string== with a length filter, an identity
fast path and =%string-compare= over explicit string intervals. This is a useful
source-level mechanism to study, rather than a reason to assume every call to
the interval API improves this parser.

Both =marker-line-end= and =profile-marker-end= previously constructed a
substring for every body line before checking marker equality. Comparing
character counts first rejects impossible candidates without materializing a
comparison string. This is valid after line-ending removal and optional tab
stripping: equality requires the remaining source interval and marker to have
identical character counts. Equal counts still require content comparison.

#+begin_src scheme
;; Shared private engine operation; no language-facing DSL addition.
(def (marker-slice=? source start end marker)
  (and (= (- end start) (string-length marker))
       (string=? (substring source start end) marker)))
#+end_src

*Why is this preferable?* Length-incompatible body lines avoid their temporary
string copy; equal-length candidates retain Gambit's existing string comparison.
The optimization lives in the shared executor and serves both line-ending
policies without introducing a language callback or new public contract.

*Why is it scientifically justified?* The length condition is necessary for
string equality, not a heuristic about particular languages. The public scanner
controls include equal-prefix, equal-suffix and repeated-marker body lines,
Unicode markers, stripped tabs, a final marker without a line ending, and both
LF and CR profile separators. Existing controls cover CRLF, empty quoted
markers, checkpoints, source ownership and incomplete bodies.

The initially proposed direct SDK =string== interval replacement passed semantic
controls, but the component observations did not justify adopting it. For 1,000
comparisons of ="EOF"=, the copying control observed 0.194/0.196 ms CPU versus
0.609/0.589 ms for the interval API. Long equal Unicode content also favored the
existing comparison. The component fixture normalizes =string=='s truthy result;
Scheme truth is not restricted to =#t=. No API or optimizer defect is inferred
from this result.

The admitted copying/guarded ABBA component control uses identical source and
marker values, nonzero source offsets and five fixtures. For a 1,024-character
Unicode body versus ="EOF"=, copying observed 0.688/0.341 ms CPU and a 4,529,232
allocation-counter delta; guarded comparison observed 0.215/0.210 ms and
385,232. All observations had zero collections. Equal-length candidates retain
the same allocation delta and add the length check: short equal markers
observed 0.262/0.274 ms versus 0.194/0.196 ms for copying. This tradeoff is
retained; there is no universal latency improvement claim. The first probe used
incorrect process-statistics slots and its counter results are excluded. The
admitted probe uses cumulative GC-count slot 6 and allocated-byte slot 7.

The reproducible Scheme component fixture is
=t/benchmarks/contextual-scanner/marker-comparison.ss=. It performs 1,000 calls
per observation, checks every observation's expected match count, collects

* Incremental checkpoint publication: native bounded list operations

The deferred-marker study concerns individual recognition decisions. The next
pipeline stage publishes an incrementally scanned prefix and certified suffix.
Previously, that stage converted every old checkpoint into a list and discarded
the prefix with =list-tail=. It also joined both reversed token and checkpoint
prefixes using =append= after =reverse=, allocating an intermediate prefix list.

The installed SDK provides a direct solution. =src/gerbil/builtin.ssxi.ss=
declares one-, two- and three-argument =vector->list= forms; the latter two accept
fixnum interval bounds. Binary evaluation confirmed =(vector->list #(0 1 2) 1 3)=
yields =(1 2)=. The native =append-reverse= binding is exposed through
=gerbil/core/runtime.ss= and used by the official C3 implementation in
=gerbil/runtime/c3.ss=. These existing primitives avoid a custom traversal API.

#+begin_src scheme
;; Preserve fresh rebinding while materializing only the certified suffix.
(map rebind-checkpoint (vector->list old-states (+ index 1)))
;; Copy a reversed private prefix once; retain the freshly created suffix.
(append-reverse tokens reused)
(list->vector (append-reverse states rebound))
#+end_src

*Why is this preferable?* The executor visits the old checkpoint interval it
actually needs. It removes the discarded checkpoint-prefix list and the two
intermediate reversed-prefix lists. Token strings are still copied, suffix
checkpoints still bind the new worker/source, and published values cannot mutate
session history. Language grammar, parser metadata and DSL admission stay out of
this internal representation change.

*Why is it scientifically justified?* For a proper reversed prefix, native
=append-reverse= yields the same ordered elements as =append= after =reverse=,
without mutating that prefix. The suffix starts after the converged checkpoint;
the scanned prefix already owns that checkpoint. Omitting that boundary would
lose a state; including it twice would break the one-state-per-token boundary
index. Tests compare complete token traces against fresh scans and replay the
result as history after prefix, middle, tail, EOF and empty-source edits. They
also mutate published tokens and require both old and new histories to remain
unchanged.

An initial SDK =subvector-for-each= plus =with-list-builder= candidate passed
semantic controls, but its callback path increased component costs for long
suffixes. With 4,097 checkpoints and 100 publications, a one-checkpoint prefix
observed about 63.6/65.5 ms CPU and a 133,147,256 allocation-counter delta,
versus 26.9/28.5 ms and 86,027,408 for the original copying control. This
candidate was rejected. The final implementation uses native interval
=vector->list= and native =append-reverse=, with no added library imports.

** LR fragment and GLR fork joins use the same native mechanism

The source-session publication study also exposed four equivalent joins in the
shared LR executor. Fragment reuse joined ordered token/mode segments to reversed
accumulators with =append= after =reverse=. Both streamed and captured directed
GLR forks reconstructed an ordered prefix plus freshly scanned suffix using
=foldl cons=. The installed SDK binary resolved =:gerbil/runtime/c3= to its
installed interface, and the corresponding C3 source uses =append-reverse= for
this same persistent reversed-prefix operation. =builtin.ssxi.ss= declares the
operation's list arguments, list return and allocation effect.

#+begin_src scheme
;; Ordered fragment into a reversed accumulated token/mode chain.
(append-reverse segment tokens-reversed)
(append-reverse segment-modes modes-reversed)
;; Reversed scanned prefix into an ordered complete fork input.
(append-reverse tokens-reversed suffix)
#+end_src

*Why is this preferable?* Fragment joins allocate the reversed segment once
instead of constructing and copying it. Fork joins use the native operation
instead of a general fold invoking =cons=. The existing checkpoint and observer
calls still own admission, capture and GLR fallback; this only replaces private
list assembly. No public DSL, source-byte rule or language-specific shortcut is
introduced.

*Why is it scientifically justified?* For proper input lists, both
=(append (reverse head) tail)= and =(foldl cons tail head)= equal
=(append-reverse head tail)=. The non-destructive operation preserves the input
head and shares the exact retained tail. The existing publication component
fixture now checks those properties at empty-prefix, empty-tail, singleton,
256-element and 1,024-element dimensions, with each control/native pair in ABBA
order and 1,000 joins per observation.

At 1,024 prefix elements and 16 suffix elements, fragment copying observed
14.223/13.811 ms CPU and a 98,465,440 allocation-counter delta, versus
1.365/1.356 ms and 49,313,232 for native joining. Copying collected once in each
observation; native joining did not. The fold control observed 5.332/5.328 ms
and 49,457,232 versus 1.382/1.327 ms and 49,313,232 for native joining, all with
zero collections. These are interpreted SDK component observations, including
the observed collection differences, not a stable native-parser speed ratio.
The fixture ended with =PARSER-JOINS-OK= and =CHECKPOINT-PUBLICATION-OK=.

The production executor passed 54 Cases across runtime, recovery/incremental,
incremental-suffix benchmark controls and GQL parsing, with final =HARNESS-OK=
and =OK=, no Case/Harness errors and exit zero. SDK optimized expansion ended
with =SDK-PARSER-JOINS-OPTIMIZE-OK= using =invoke-gsc: #f=; this does not qualify
native C linking or execution.

* Dependency order for further implementation

1. *Shared source spans.* Own one admitted source and its character/byte boundary
   mapping. Internal captures carry owner/start/end; decomposition reuses that
   owner. Materialize public strings at the artifact boundary. Preserve rejection
   of caller mutation, cross-source spans, non-scalar Unicode and stale checkpoints.
2. *Demand-driven scanning.* Reuse immutable step/checkpoint semantics to provide
   lookahead without whole-source token/remaining/emitted list duplication.
   Rejected sources must still obtain a complete covering fallback artifact;
   edit restoration and heredoc obligations remain intact.
3. *Projection and event fusion.* Compile the closed projection plan into event
   emission. Keep recognition nodes where consumers require them. Field order,
   identities, trivia, diagnostics, offsets and complete artifacts remain equal.
4. *Static AOT specialization.* Generate Scheme and Rust execution from the same
   admitted plan. Prepared closures are not yet grammar-specific generated
   character branches. Checkpoint equivalence, IR identity and the common ABI
   constrain both backends.

Each step first establishes ownership and semantic controls, then uses the
existing benchmark owners for matched complete-product ABBA measurements under
the same GCC SDK. Hold input, output validation, natural GC, destruction, timing
boundaries and worker count constant. Record complete CPU, allocation per input
byte and GC. Include ordinary text, Unicode, nesting, overlapping delimiters,
dynamic markers, rejection and edit restoration across Bash, HCL, HL7, FHIRPath
and contextual LR. Component timings cannot replace complete-product timing.

** Paper interpretation and bounded lowering obligations

[[https://arxiv.org/html/2304.05276][flap sections 2.5, 2.7 and 2.8]] distinguish three mechanisms:
deterministic single-token branch selection, lexer/parser fusion eliminating an
internal token representation, and staging away statically known dispatch.
Its generated parser still permits allocation introduced by semantic actions.
Our required lossless artifact is such an observable semantic product. Removing
an internal token stream does not authorize removing lexemes, field events,
trivia coverage, diagnostics or public identities.

A generic lowering must be derived from admitted engine IR. It must establish:

1. Branch selection and lexical priority preserve the original recognition
   language, including maximal-munch behavior and negative lookahead. A FIRST
   set alone is insufficient to prove scanner/parser fusion.
2. Skipped characters remain publishable lossless trivia. A recognizer that
   discards them does not satisfy the complete artifact contract.
3. Deferred delimiters, source modes and speculative branches establish explicit
   commit boundaries. A speculative event cannot escape into canonical output.
4. Source intervals retain byte/character agreement and input ownership through
   Unicode and relocation. A borrowed interval cannot silently outlive its
   request or become a mutable shared input view.
5. ResultPlan field order, token spelling and failure diagnostics remain equal
   to the current public product. The existing event-program and raw-event-tape
   publication mechanisms are the targets; a new language callback protocol is
   unnecessary.

The current shell execution chain still creates scanner tokens, recognition
values and projected word token sequences, then flattens those sequences at
component boundaries, copies them into the parser's emitted stream and finally
publishes canonical events. Some of this storage is transient, but canonical
output is required. Word source preparation already uses an ASCII fast path and
lazily prepares region caches; those mechanisms must not be proposed again as
new work. The earlier generated projection experiment removed interpreter
operation dispatch without establishing a complete-entry allocation or speed
win. That negative result argues for changing producer/consumer representation
and ownership, rather than another wrapper around projection execution.

The next experiment should account for scanner and recognition construction
separately, then lower an admitted deterministic producer/consumer boundary to
existing publication instructions. Request-local source intervals and a single
committed semantic stream are candidate representations, not implemented
capabilities. They require whole-product controls for quoting, substitutions,
here-documents, malformed input, Unicode and another applicable grammar before
any default-path promotion. An implementation should be retained only if it
reduces complete native allocation without a stable runtime regression.

* Rejected dense region-prefix lowering

** Algorithm and source review

This experiment used base =9c4b7635238eeb9f1fc8c8236a345b055589ddea=, the
fixed Gerbil/GCC SDK and unchanged 120-second total / 5-second idle guards.
It investigated the remaining linear walk within a first-codepoint bucket.
The engine's =make-bounded-literal-end-scanner= already follows a character
trie. The experiment adapted that representation to terminals containing the
original owned region rows, preserving cache identity and scope filtering.

The first candidate used a trie for every nonempty bucket. A later candidate
kept buckets of at most eight declarations as lists and compiled larger ones
into tries. The final candidate additionally sorted short buckets by descending
opener length, allowing the first admitted match to commit immediately.
A unique-prefix admission rule ensures that two different terminals of the
same width cannot both match the same source position. A rejected terminal
cannot stop traversal: a longer descendant might still be admitted.

Trie preparation uses memory proportional to its distinct prefix nodes.
Lookup follows the source prefix with expected constant-time hash edge access;
scope membership remains a list search at terminals. This improves dense
first-codepoint collision scaling, but adds representation discrimination and
edge lookups to small catalogs. It does not remove word captures, intermediate
recognition nodes or final token publication.

This distinction agrees with the materialized-token cost discussed in
[[https://arxiv.org/html/2304.05276][flap: A Deterministic Parser with Fused Lexing]], Sections 2.2 and 2.8.
This experiment is static prefix lookup specialization, not lexer/parser
fusion, and does not establish the paper's deterministic grammar assumptions
for this engine.

* Literal-run invariant staging and bounded source admission

The current Scheme design documents already describe checked public boundaries,
known private calls, and compile-time ownership. Reading the pinned Gerbil SDK
revision =2591dcd=, =src/gerbil/runtime/util.ss= (=string-index= and
=__string-index/char=), provides a concrete example: validate the source range
once, retain invariant input and endpoint, and advance only the cursor. This
change transfers that structure without copying unchecked primitives or type
assertions. The emitted Scheme for the previous parts scanner called the full
context matcher on every character; its context index was not hoisted there.

The shared =part-context-literal-end= now retains the prepared ASCII vector and
Unicode character hash for the entire literal run. Empty initial buckets bypass
rule matching. Candidate initials call the named =match-part-rules= helper also
used by direct matching. Declaration order, prefix bounds, guard rejection,
shorter-prefix overrides, and Unicode keys therefore retain the same matching
algorithm. No extra index, callback, language declaration, compatibility path,
schema version, or FFI surface is introduced.

Range admission requires exact integer endpoints with
=0 <= start <= end <= string-length=. Empty intervals return =end=. The previous
loop started at =start + 1= and stopped only at equality with =end= or a successful
match. With =start = end=, matching returned false beyond the endpoint and the
cursor kept increasing. This nontermination follows from the source; the old
infinite loop was not executed as a benchmark. Tests cover empty intervals,
negative, reversed, escaping and fractional ranges, independent direct-matcher
comparison at every start position, and truncated Unicode guards.

* Request-owned region counters instead of replacement frames

The pinned Gerbil SDK revision =2591dcd=, =src/std/struct/queue.ss=, updates
queue links and length under an imperative ownership contract. Its
=queue->list= explicitly copies the externally returned spine. The transferable
mechanism is ownership-directed mutation, not blanket unchecked access. The
current parser design documents likewise require explicit source and execution
ownership. This change uses ordinary checked vector operations.

The region matcher previously rebuilt a pair-frame vector and its top stack
cell whenever a bare delimiter increased or decreased the active pair depth.
These are counter transitions within one region, not new independently
addressable region entries. The matcher now changes only the depth slot in the
active frame. Named nested openers and quote entries still allocate their own
frames. Prepared declaration rows remain immutable.

All callers create initial frames for one invocation. Frames never escape the
match, and completed boundary caches retain numeric endpoints, not frames.
A failed match abandons its local frames. Independent scans sharing a plan
therefore share no mutable depth. This does not grant concurrent-write authority
to one shared source cache. Regression tests exercise deep counter nesting with
other pair kinds and quotes, repeat calls, independent source caches, four
concurrent scans of the same plan, failure followed by reuse, and existing
5,000-frame cache endpoint checks.
