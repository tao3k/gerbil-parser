#+TITLE: Compiler Granularity and Complete Native Product Publication

* Contract

The standard Gerbil build graph owns dependency ordering, compiler workers and
in-place compilation. The admission owner holds an exclusive writer lock,
withdraws the completion receipt before writing, and publishes only a small
receipt after successful compilation with unchanged inputs. Readers hold a
shared lock and verify the source catalog and production products before and
after execution. Newly added sources invalidate admission as well as changed
or removed sources. Language-support declarations belong to that catalog.

A failed or killed build leaves an unadmitted generation. The next root build
uses the standard clean operation and removes this package's remaining native
variants before retrying. There is no directory copy, root exchange, backup
generation or alternate GERBIL_PATH. Tests and extension owners must start
from an admitted root generation; failed extensions withdraw admission too.

Standard clean owns its declared outputs. Supplemental cleanup covers only
=lib/gerbil-parser= loadable products and =lib/static/gerbil-parser__*=.
Content-addressed grammar artifacts and receipts retain their existing digest
validation; they are not loadable native module versions. Dependency packages,
source checkouts and historical diagnostic logs are outside cleanup ownership.

Filesystem locks, receipt rename, compiler semantics and SDK runtime behavior
are external premises. This is not a theorem about Gambit or machine code.
No Gambit or SDK source is modified or built.

* Algorithmic cause and code-generation law

The arithmetic LR backend previously emitted the same reduction handler at
many state/terminal decision sites. Its generated C translation unit measured
2,436,679 bytes. A per-procedure C host alone does not split a single large
Scheme procedure, so compiler host flags cannot eliminate that duplication.

The shared decision generator selects an immediate action identifier while
retaining ordered predicates, then emits each distinct handler once. The Lean
[[file:../../../formal/ParserEngine/ActionCodeSharing.lean][action-code sharing law]] proves first-match selection, predicate state
effects, catalog decoding, fallback and arbitrary handler results for arbitrary
rows. The Scheme test owner compares execution with an independently generated
unshared decision tree, including false results and action identifier zero.
This theorem does not prove the complete LR generator or Scheme evaluator.

The original arithmetic generator produces a 27,312-byte Scheme backend after
sharing, compared with approximately 57 KB before sharing. The isolated cold
backend compiles with the same GCC and optimization policy in 16.07 seconds,
with natural exit zero under the unchanged 90-second total and five-second idle
limits. This is build qualification, not parser-request CPU evidence.

* Compiler front-end work and scheduling

The installed SDK protects Scheme optimization with one driver mutex. Its
std/make worker count therefore does not represent parallel CPU execution of
all Scheme optimizer passes. External GSC/GCC jobs can execute concurrently.
The previously captured interval with no external compiler and an active GXI
identifies a front-end interval, not proof of an idle linker.

The detailed cold log contains 234 optimizer-interface loads with 234 distinct
paths. The SDK retains optimizer information across batch compilation and
forces each module evaluation promise. Repeated evaluator entry diagnostics
therefore do not establish repeated module execution. No replacement module
cache is introduced.

The concise declaration matcher's shared success graph causes repeated type
analysis of the same local bindings. The isolated original module emits
33,644 type declarations, with some bindings revisited 513 times. Merely moving
normalization into another module leaves CPU unchanged (9.06 versus 9.37
user-plus-system seconds); that split is withdrawn. Changing private optional
arguments alone also fails to eliminate the repeated graph traversal.

The implementation instead admits one section at a time, retaining the reader's
syntax objects, then calls one named elaboration worker. The worker owns the
per-declaration source maps and publishes through the existing canonical
compiler. Admission and elaboration have separate physical module bodies;
large elaboration code is not captured in the matcher's success continuation.
The same two-module isolated build now passes under the 180-second total and
five-second idle limits. It emits 12,220 type declarations, with a maximum
repeat count of seventeen. One observation records 7.64 user-plus-system
seconds versus the original 9.06. Wall time increases from 18.01 to 30.98
seconds, so neither a wall-clock speedup nor full-library completion follows.

The compiler, its mutex, module promises and code generation remain external
premises. This source transformation changes declaration compilation structure;
it is not a runtime parser CPU optimization or a proof of the host compiler.

* Base package and extension input direction

The package input policy Suite runs through the source test runner and remains
included in CI's =--remaining-conformance= discovery. Its SDK package-registry
operations require =gerbil/tools/gxpkg= and =gerbil/tools/env=; the SDK does not
distribute a static object for the latter. These build-tool controls therefore
do not belong in the closed native parser runtime image. The test-plan control
checks this ownership without removing or reducing the policy scenarios.

A registered base package uses the SDK's =pkg-dependents*= graph to identify
reverse consumers. Their declared namespace outputs are excluded from the base
compiler footprint, and attempted compiler imports of those namespaces or source
roots are rejected before expansion. All dependency and unclassified foreign
inputs remain covered, including effective =.oN= runtime generations. Ambiguous
namespace ownership refuses. Registry metadata is itself captured and checked
against the SDK's cached projection; metadata drift requires a fresh process.

The base request retains =(package-build owner)= as its input purpose. Reader
admission recomputes that same scope and refuses another source owner. Extension
and unregistered development writers keep the existing whole-environment view.
This prevents Parser -> Orgize -> Parser invalidation cycles without treating
loadable foreign generations as inert compiler outputs or relaxing extension
review. =just test-package-inputs= runs six SDK-backed controls with the existing
1-GiB / 120-second fence, without bootstrapping Parser to test its own installer.

An extension can explicitly cross from a current package-scoped base to the full
environment view. Source support, native products and the exact compiler
options/environment must still match before execution; base source support is
rechecked on return. Source or PATH drift refuses before the builder runs. The
resulting extension record owns the full view, so later consumer changes once
again invalidate it. This is a purpose handoff, not a bypass of input admission.

The SDK local environment's current Project also participates through its existing
="."= package node. It is read from the SDK local =<project>/.gerbil= layout,
queried in the same reverse graph and included in metadata support. A custom or
global prefix gets no inferred Project owner. The Project's filesystem envelope
excludes its dependency environment: containment under the repository must not
transfer registered dependency ownership to the Project. Both cached registered
metadata and uncached local-Project metadata are compared with their captured
values before compiler imports. A fresh-process fixture checks this exact native
SDK path, import refusal, environment ownership and local metadata drift.
